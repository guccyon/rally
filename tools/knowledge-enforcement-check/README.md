## 項目

`enforcement.solutions` の各項目に書く。

| 項目 | 値 | 意味 |
|---|---|---|
| `wired` | `true` / `false` | CI（`.github/workflows/`）や Engine の呼び出しから実際に走るか。ひな形（`ci/*.yml`）を置いただけ、テストを書いただけは `false` |
| `wired_by` | `{workflow, job, runs}` の列 | `wired: true` のときに必須。`workflow` は `.github/workflows/` の直下のファイル、`job` はその `jobs` の id、`runs` は呼ぶ検査の道（リポジトリの根から。例: `tools/sendback-check/order.mjs`）。`wired` が `true` でなければ見ない（議決 `D-0021`、Issue #986） |
| `requires_check` | 検査の道か、道か `{runs, workflow, env}` の列 | 書いた解決策を `wired: true` にするとき、pull_request でも走るジョブから呼ぶことを求める検査（リポジトリの根からの道。例: `tools/knowledge-enforcement-check/test_check.py`）。`workflow`（`.github/workflows/` の直下のファイル）を書いた検査は、そのワークフローのジョブを指す `wired_by` だけを数える。`env`（環境変数の名前 → 値の文字列。例: `{CONFLICT_SQL_REQUIRED: "true"}`）を書いた検査は、その値を渡して呼ぶ手順を指す `wired_by` だけを数える（議決 `D-0135` の ci_check の案、Issue #1344。下の「PR ごとのひな形のジョブで走らせる試験」）。形の誤りと、挙げた検査がリポジトリにないことは `wired` を問わず落とす（議決 `D-0077`（起票時の番号は `D-0075`）、Issue #1216。下の「PR ごとの配線の必須」）。`wired: true` にする解決策は、`requires_schedule` を書いたもの・`REQUIRED_RUNS` に挙げたものを除いて書くのが必須（例: `requires_check: tools/knowledge-enforcement-check/test_engine_patch.py`。議決 `D-0080`（起票時の番号は `D-0078`）、Issue #1227）。`kind` が `ci_check`・`test` の解決策では必須の欄で、PR ごとに走らなくてよいものは空の列 `[]` を明示する（`[]` は形の誤りに数えないが、`wired: true` の解決策では挙げる検査がないので書いていないのと同じに数える。議決 `D-0116`、Issue #1304。下の「ci_check・test の解決策の requires_check の必須」） |
| `requires_schedule` | 検査の道か、道か `{runs, workflow}` の列（`requires_check` と同じ形） | 書いた解決策を `wired: true` にするとき、schedule でも走り `continue-on-error` が真でないジョブから呼ぶことを求める検査（例: `- runs: tools/pr-body-check/patch.mjs` と `workflow: .github/workflows/pr-body-patch.yml`）。`workflow` を書いた検査は、そのワークフローのジョブを指す `wired_by` だけを数える。形の誤りと、挙げた検査がリポジトリにないことは `wired` を問わず `requires_schedule_invalid` で落とす（議決 `D-0130`（PR #1334）の schema の案、Issue #1335。前は `check.py` の `REQUIRED_SCHEDULE`・`REQUIRED_SCHEDULE_WORKFLOW` に知見と issue の名前で組を並べていて、足し忘れると黙って通っていた。下の「定期の配線の必須」） |
| `verified` | `true` / `false` | 本物の記録（実際の PR やイベント列）で、外れたときに落ちる・正しいときに通ることを確かめたか。写しや作った入力だけで確かめたものは `false` |
| `verified_by` | `case`・`pr`・`event` の参照の列 | `verified: true` のときに必須。確かめた本物の記録を、`evidence` と同じく 1 項目に 1 つの参照で書く（例: `- case: C-0001`・`- pr: 395`・`- event: case.analyzed:40376`）。`case` を 1 件以上含め、その事例記録が `.factory-config/knowledge/cases/` にあること。`verified` が `true` でなければ見ない（議決 `D-0034`、Issue #1059） |

書いていない項目は落とさず `false`（未記入）として数え、表示も `未配線` 側に倒す（`K-0002` の `config` のように実際は効いているかもしれない解決策も、書くまでは配線済みと出さない）。未記入の件数は出力の「未記入」に別に出すので、書いていないのか `false` と書いたのかは見分けられる。項目を書くのは足したり直したりした知見から順に（2026-11-08 の時点ですべての解決策に書いたのは `K-0001`・`K-0002`・`K-0004`・`K-0005`・`K-0006`・`K-0010`・`K-0011`・`K-0012`・`K-0014`・`K-0015`・`K-0016`・`K-0025`。`K-0009` の未記入の解決策は次にその知見を直す変更セットで書く。書かずに直すと下の「直した知見の記入の必須」で落ちる）。この 2 つの一覧は `test_check.py` が `check.py` の数えた結果（解決策があって未記入が 0 件の知見と、未記入が 1 件以上の知見）と照らし、合わなければ落ちる（議決 `D-0035`、Issue #1062）。`.factory-config/knowledge/README.md` の同じ 2 つの一覧（「すべての解決策に書いたのは …」「… には未記入の解決策が残っていて」）も同じく順まで照らす（議決 `D-0052`、Issue #1138）。知見に項目を書き足したら、同じ変更セットで両方の一覧を直す。

## 落とすもの

- `wired` か `verified` が真偽でない（`"true"`・`yes` など）
- `wired` が `true` でないのに `verified` が `true`（配線してから本物の記録で確かめる）
- `verified` が `true` なのに、`verified_by` がない・空・列でない、項目が 1 つの参照でない・種類が `case`・`pr`・`event` でない、`case` が `C-NNNN` でないか `.factory-config/knowledge/cases/` にない、`pr` が正の整数でない、`event` が `<種類>:<id>` でない、`case` が 1 件もない（`pr`・`event` は手元で本物か照らせないので、事例記録に辿れることを求める）

## 配線先の照合

`wired` は書き手の申告なので、配線していないのに `true` と書かれても見抜けなかった（議決 `D-0021`、Issue #986）。`check.py` は `wired_by` の job の手順（`run`）が `runs` を呼んでいるかを、`tools/sendback-check/order.mjs` と同じやり方で照らす。

- shell の注釈を落とし、行末の `\` でつないだ行を 1 行にして見る
- 道は手順の `working-directory`（なければ job の `defaults.run.working-directory`）と、手順の中の `cd` の下か根から引く。`$GITHUB_WORKSPACE`・`${{ github.workspace }}` は根にする
- ワークフロー・job・手順の `env` と shell の代入の変数（`$NAME`・`${NAME}`・`${{ env.NAME }}`）は値に置き換える
- `npm`・`pnpm` の `run`・`run-script`・`test` は、そのディレクトリ（`--prefix` も）の `package.json` の scripts の中身を辿る。シェルのラッパー（`.sh`・`.bash`）は中身を読んで辿る（どちらも 3 段まで）
- `runs` がテストのファイル（`test_*.py`・`*.test.mjs` など）のときは、そのディレクトリで `python3 -m unittest discover -s <ディレクトリ>` や、ファイルを名指ししない `node --test` を走らせる形も呼び出しに数える
- `order.mjs` は取りこぼすと見張れないので迷う形を呼ぶ側に数えるが、ここで見逃すと配線していない担保を配線済みと読ませるので、逆に迷う形は呼んでいない側に数える（scripts にない名前・読めないラッパー・別の job の手順・`uses:` の手順・別のワークフローを呼ぶ job は数えない）。字面で偽の `if:`（`false`・`${{ false }}`）の job と手順も走らないので数えない
- Engine の呼び出しだけで走る解決策は今の `wired_by` では書けない。書けるようになるまで `wired: false` のまま置く（Engine の呼び出しとワークフローの両方で効く `K-0012` の pr-body-check は、`wired_by` にワークフローのジョブを書き、Engine の側は下の「Engine の merge_step の照合」で確かめる）

## Engine の merge_step の照合

知見 `K-0012` の担保の pr-body-check（`tools/pr-body-check/ci/pr-body-check.yml`）は、必須のチェックにしただけでは、本文の直しのジョブが終わってから `edited` のチェックが始まるまでの間に前の本文で通ったチェックのままマージできる。待つのは Engine の supervisor の `merge_step`（`tools/pr-body-check/engine/pr-body-recheck.patch` で足す `body_recheck_pending`）で、Engine の呼び出しは上の「配線先の照合」の `wired_by` では書けない。ワークフローを写しただけで `wired: true` にすると、Engine が待たないままでも配線済みと読ませてしまう（議決 `D-0100`（起票時の番号は `D-0071`）、Issue #1196）。

`check.py` の `REQUIRED_ENGINE_WAIT` に挙げた解決策（今は `K-0012` の issue 1122・1196・1281）は、`wired: true` にするとき、`.github/workflows/pr-body-engine.yml` の `ENGINE_REF` の版の Engine の `orchestrator/dispatcher/supervisor.py` で、`merge_step` が `body_recheck_pending` を呼び、その関数がモジュールの直下に定義されていることを構文木で照らす（取り込まない）。Engine は `--engine` か `ENGINE_DIR` の全履歴のチェックアウトから版のファイルを取り出す。

- 呼んでいなければ `engine_unwired` で落とす（関数がない・`merge_step` から呼ばない・別の関数でだけ呼ぶ）
- 呼んでいれば、その版の Engine を `git archive` で取り出したチェックアウトを `ENGINE_DIR` にして、`.github/workflows/pr-body-engine.yml` の `engine-test` が走らせる `tools/pr-body-check/engine.test.mjs` の (12) を `node --test --test-name-pattern='^\(12\) '` で走らせ、`engine.test.mjs` にある (12) のテストがすべて `ok`（`# SKIP`・`# TODO` なし）でなければ `engine_wait_failed` で落とす（`body_recheck_pending` を呼んでいても何も待たない中身、構文木の照合だけでは通っていた。議決 `D-0105`、Issue #1281）。`PR_BODY_RECHECK_ENGINE_ONLY=1` を渡すので、(12) は差分を当てた写しに頼らず、Engine に `body_recheck_pending` がなければ落ちる。`node` がない・走らせられないときは `engine_unverifiable（node_unavailable）`
- Engine のチェックアウトがない・`.github/workflows/pr-body-engine.yml` がないか `ENGINE_REF` が 40 桁の SHA の 1 行でない・その版や `supervisor.py` がない・構文として読めないときは、照らせないとして `engine_unverifiable（<種類>）` で落とす

`wired` が `true` でない間は見ない。`test_check.py` の `PrBodyRecheckWiringTest` は、差分の足す行で組んだ待つ Engine で通り、`merge_step` から呼ぶが何も待たない Engine で `engine_wait_failed`、差分の入っていない Engine で (12) がすべて通らない側に数えられることを確かめる。手元の Engine を `ENGINE_DIR` に渡すと、`test_check.py` の `PrBodyRecheckWiringTest` が、その `supervisor.py` が差分を当てる前は待たず、当てると待つと読めることも確かめる（渡さなければ飛ばす）。

## 直した知見の記入の必須

「項目」の決まりでは、未記入の解決策は次にその知見を直す変更セットで書く。ただ、`K-0006` の issue 906 の解決策の `what` を直した PR で `wired`・`verified` を書き忘れ、委員会の票で初めて気づいた（議決 `D-0071`、Issue #1193）。手の注意に頼ると繰り返すので、`check.py` に `--base` を渡すと次を照らす。

- `--base` と `HEAD` の分かれ目（`git merge-base`。PR の差分の起点）の版の `.factory-config/knowledge/K-*.yaml` と、作業ツリーの中身を比べる。違うか、その版にないファイル（足した知見）を、PR の差分で変わった知見とする。分かれ目と比べるので、分岐のあとで base の側だけが直した知見は数えない

## ci_check・test の解決策の requires_check の必須

`requires_check` は書いた解決策しか照らさないので、PR ごとに走るべき新しい解決策で欄を書き忘れると、`check.py` に名前の組を並べていたころの足し忘れと同じく黙って通っていた（議決 `D-0116` の enforcement と dissent の票）。`check.py` に `--base` を渡すと次を照らす（議決 `D-0116` の schema の案、Issue #1304）。

- `kind` が `ci_check` か `test` の解決策では `requires_check` を必須の欄にする。PR ごとに走らせる検査があればその道を書き、PR ごとに走らなくてよいもの（定期だけの見張りなど）は空の列 `requires_check: []` を明示する
- `--base` と `HEAD` の分かれ目の版の同じ `K-*.yaml` に、同じ中身の解決策がないもの（足した解決策と、`what`・`wired` などを直した解決策。並べ替えただけは数えない）を、PR の差分で足したり直したりした解決策とする。そのうち欄がないものを、項目ごとに `K-NNNN.yaml: enforcement.solutions[i]（…）: requires_check_missing: …` で落とす
- 欄のない対象の解決策がない知見は、分かれ目を求めない。分かれ目を求められない（base がない・浅い取り出し）か、その版の知見を読めないときは、照らせないとして `requires_check_unverifiable` で落とす

- `what` に PR ごとのひな形（`tools/*/ci/*.yml` のうち、リポジトリにあって `on.pull_request` のあるもの）を挙げた解決策は、空の列 `[]` でも同じに `requires_check_missing` で落とす。そのひな形のジョブで走らせる検査の道を書く（議決 `D-0139` の ci_check の案、Issue #1344。`K-0014` の issue 1295・1297 は PR ごとのひな形のジョブで走る試験なのに `requires_check` を書かずに足された）。`requires_schedule` を書いた定期の解決策は、`schedule` と `pull_request` の両方で走るひな形を挙げても見ない

変えていない解決策は欄がなくても見ない（既存の `ci_check`・`test` の解決策は、次に直す変更セットで書く）。`--base` を渡さない手元の実行でも見ない。`test_check.py` の `RequiresCheckDeclaredTest` が、一時の git リポジトリで、足す・直すと欄がなければ落ち、`[]` や検査の道を書けば通り、ほかの種類・変えていない解決策・並べ替え・base の側だけで足した解決策は見ず、分かれ目を求められない・その版を読めないときは落ちることを確かめる。

### 差分が古くなっていないか（`patch_stale`）

`test_engine.py` は Engine のチェックアウトの今の中身に差分を当てるので、製品の CI が使う版（`knowledge-check.yml` の `ENGINE_REF`）と違う版を渡すと、その版では当たらないことに気づけない（議決 `D-0024`、Issue #1014）。`test_engine_patch.py` は `.github/workflows/knowledge-check.yml` の `ENGINE_REF`（`env` に `ENGINE_REF` の行があればその値、なければ `knowledge-check.yml` が読む `.factory-config/engine.lock` のコメントと空行を除いた最初の行。どちらも 40 桁の SHA でなければ落とす。`engine_ref()` の 1 か所で読み、`test_engine.py`・`test_ci.py`・`test_ci_head.py` も同じものを使う。議決 `D-0080`、Issue #1225）を読み、`ENGINE_DIR` のチェックアウトからその版を名指しで取り出して `git apply --check` で差分を当て、次のときに `patch_stale` で落とす（GitHub Actions では `::error` も出す）。

- 差分が当たらず、しかも Engine 側にまだ入っていない（`git apply --reverse --check` も通らず、`core-gates/knowledge_check.py` に差分で足した `enforcement_label`・`check_wired_by`・`check_verified_by` もない）

差分で足した関数（`enforcement_label`・`check_wired_by`・`check_verified_by` のどれか）はあるのに `git apply --reverse --check` が通らない版（差分の一部だけが入った・入れたあと変わった）は、もう入っているとは数えずに `patch_partially_applied` で落とす（GitHub Actions では `::error` も出す。議決 `D-0036`、Issue #1077）。関数の名前があるだけでは、一部だけ入った版や名前だけが別の中身で入った版でも通ってしまうため。落ちたら差分を今の Engine に合わせて作り直す（全部入れて `ENGINE_REF` を上げたなら差分を消す）。

見る関数の名前は手で書かず、`added_functions()` が差分の `core-gates/knowledge_check.py` に足す行（`+def ...`）から取り出す（議決 `D-0054`、Issue #1149）。手で書いた一覧では、差分に関数を足したときにそれが漏れ、その関数だけが入った版を `patch_stale` と取り違えるため。差分に関数を 1 つ足した作った版で、その関数だけが入った Engine が `patch_partially_applied` で落ちることもテストで確かめる。

当たるか、もう入っていれば（`git apply --reverse --check` が通るときだけ）通る。チェックアウトに `ENGINE_REF` の版がないときは飛ばすが、`ENGINE_DIR` を渡したときと CI では落とす（`ci/knowledge-enforcement.yml` の `ENGINE_REF` が `knowledge-check.yml` とそろっていないとこれで落ちる）。判定そのものは、作った git の版（当たる・入っている・一部だけ入った・入れたあと変わった・どれでもない）で Engine なしに確かめる。`ci/knowledge-enforcement.yml` の `engine-test` のジョブで `test_engine.py` と一緒に走る。

## CI のひな形（`ci/knowledge-enforcement.yml`）

ジョブは 2 つ。

- `engine-test`: `ENGINE_REF` の版の Engine を取り、`python3 -m unittest discover -s tools/knowledge-enforcement-check`（`test_engine_patch.py`・`test_engine.py` を含むすべてのテスト）を `CI=true`・`ENGINE_DIR` を渡し、pytest を入れて走らせ、出力を `knowledge-enforcement-unittest.log` に残す。差分が `ENGINE_REF` に当たらない（`patch_stale`）か一部だけ入っている（`patch_partially_applied`）か、差分で足したテストや担保の表示の比べが落ちれば、どの PR でもジョブが落ちる。次の手順（`飛ばしたテストがないか`）が、その出力の要約の `skipped=` が 1 件以上か、走らせたテストの件数（`Ran N tests`）が出ていなければ `tests_skipped`・`unittest_not_run` で落とす（飛ばす条件の取りこぼしで緑にしない。議決 `D-0037`、Issue #1080）。写したらこのジョブを branch protection の必須チェックに入れて PR を止める（議決 `D-0035`、Issue #1063）
- `enforcement`: Engine の要らないテスト（`test_check.py`・`test_ci.py`）と `check.py` を走らせる。`check.py` の結果で落とすのは、PR が `.factory-config/knowledge/` か `tools/knowledge-enforcement-check/` を変えたときと、配線先（`.github/workflows/`）か `check.py` が呼ぶことを求める検査の置き場（`tools/conflict-check/`・`tools/sendback-check/`・`tools/pr-body-check/`・`tools/judge-input-check/`）を変えたとき。記録を変えない PR でも、`wired: true` の解決策の配線先のジョブから検査を外す（`conflict-check.yml` から `test_watch.py`・`test_engine.py` を外すなど）と「呼ぶ検査の必須」などが落とすので、それを止められるようにした（議決 `D-0066`（起票時の番号は `D-0062`）、Issue #1173）。`test_ci.py` の `EnforcementScopeTest` が、ひな形の範囲の手順を偽の `git` で動かして、`check.py` の `REQUIRED_RUNS` に挙げた検査、`K-*.yaml` の `requires_check`・`requires_schedule`（前の `REQUIRED_SCHEDULE`・`REQUIRED_SCHEDULE_WORKFLOW`。議決 `D-0130`、Issue #1335）の検査とワークフローと `wired_by` の `workflow`・`runs` のどれを変えても範囲に入り、ほかの道だけなら入らないことと、`K-0010` の issue 1034 を `wired: true` にした一時のリポジトリで、ひな形の `conflict-check.yml` の写しなら落とす手順が通り、`test_policy.py` だけを呼ぶ形に変えると範囲の中では落ち、範囲の外では落とさないことを確かめる。検査の置き場を `check.py` の一覧に足したら、この範囲にも足す（足さないと `EnforcementScopeTest` が落ちる）。挙げた道そのものだけでなく、`check.py` の `REQUIRED_*` の一覧（`REQUIRED_RUNS` と、名前で並べた一覧を足せばそれも。前の `REQUIRED_PR` は `requires_check` に、`REQUIRED_SCHEDULE`・`REQUIRED_SCHEDULE_WORKFLOW` は `requires_schedule` に移った）と `K-*.yaml` の `requires_check`・`requires_schedule` が指す検査とワークフローの置き場（ディレクトリ）を導き、その置き場の新しいファイルや下のディレクトリを変えた PR も範囲に入ることを確かめる。名前で並べた一覧や `requires_schedule` に別の置き場（`tools/changelog-check/` など）の検査を足して範囲に足し忘れた形を見分けられることも対照で確かめる（議決 `D-0090`（Issue #1259 の起票時の番号は `D-0089`））。その範囲の PR では Engine を全履歴で `.engine` に取り、`check.py` に `--base "origin/<PR の base>" --engine .engine` を渡す（上の「review_by の先送りの照合」）。`check.py` には Issue #948 のコメントを取って `--head-comments` で渡す（上の「engine-head の記録の照合」）。

`unittest discover` は既定の `-p test*.py` に合わないファイル（`check_x.py`・`x_test.py`・`test-x.py`）と、`__init__.py` のない下のディレクトリのファイルを黙って拾わないので、テストを書き足しても走らないまま緑になりうる（議決 `D-0057`、Issue #1154）。`test_ci.py` の `DiscoveryTest` が、このディレクトリ（下も含む）で `unittest.TestCase` を継ぐクラスを定義する `.py` がすべてその形に合うかを照らす。`engine-test` は飛ばした件数の手順のすぐ後で `python3 -B tools/knowledge-enforcement-check/test_ci.py --log knowledge-enforcement-unittest.log` を走らせ、拾われないファイルか、出力に（飛ばさずに）走ったテストが 1 件もないファイル（読み込めずに `_FailedTest` になった・`setUpClass` で落ちた・すべて飛ばした）があれば `::error`（`tests_not_discovered`）を出して落とす。この手順があることも `test_ci.py` の形の検査で見る。

`test_ci.py` がひな形（写してあれば写しも）の `engine-test` の形を見て、外れたら落とす。絞り込みのない `pull_request` だけで走る、ジョブと手順に `if:`・`continue-on-error:`・`needs:` がない、`ENGINE_REF` がワークフローの `env` に 1 行だけあって `knowledge-check.yml` と同じ版、最初の手順で 40 桁の SHA かを確かめる、Engine を `ref: ${{ env.ENGINE_REF }}`・`path: .engine` で取る、テストの手順が `CI: "true"`・`ENGINE_DIR` を渡して pytest を入れ、`unittest discover -s tools/knowledge-enforcement-check` を `-p`・`-k` で絞らずに走らせて 2 つのテストを（`check.py` の配線先の照合で）呼び、`shell: bash`・`set -o pipefail` で出力を `tee knowledge-enforcement-unittest.log` に残し、失敗を `|| true` などで握りつぶさない。そのすぐ後に、その出力の `skipped=` を見て落とす手順が bash で 1 つある。写しは `ENGINE_REF` の行のほかがひな形と同じであること（`ENGINE_REF` も `knowledge-check.yml` とそろえるので、実際は同じ中身）。ひな形を 25 とおりに書き換えた写しで、それぞれ外れることも確かめる。`ENGINE_REF` は、形の検査とは別のテスト（`EngineRefTest`）でも、ひな形と（あれば）写しの `ENGINE_REF` の行が `knowledge-check.yml` の `ENGINE_REF` と同じ版の 1 行かを字面で照らし、片方だけ上げた PR を落とす（写しがなくても飛ばさない。議決 `D-0053`、Issue #1143）。`knowledge-check.yml` だけ・ひな形だけ・写しだけを上げた組で落ち、3 つをそろえて上げた組で通ることを一時ディレクトリに置いたファイルで確かめる。`knowledge-check.yml` の版は、`knowledge-check.yml` が `.factory-config/engine.lock` を読む形と `env` の `ENGINE_REF` の行の形の両方で上げて確かめる（議決 `D-0080`、Issue #1225）。`skipped=` を見る手順は、作った出力（`skipped` なし・あり・失敗と一緒・テストが 0 件・出力がない）を渡して、飛ばしたかテストが走っていないときだけ落ちることを確かめる。この手順はひな形から走らせたときしか効かないので、飛ばす条件そのものも別のテスト（`NoSkipTest`）で照らす。`test_engine.py`・`test_engine_patch.py` を、Engine のない一時の置き場（隣の `../engine` もない）に写して子のプロセスで走らせ、`CI=true`・空のディレクトリかないディレクトリの `ENGINE_DIR`・Engine のファイルはあるが `ENGINE_REF` の版のない `ENGINE_DIR`（`CI=true` と一緒も）のどれでも、飛ばさずに Engine のチェックアウトの文で落ちることと、どちらも渡さないときだけ飛ぶこと（対照）を確かめる（議決 `D-0037` の ci_check の案を議決 `D-0055` で採り直したもの、Issue #1152）。`REQUIRED` から `CI` か `ENGINE_DIR` を外す・版がないときに飛ばす・`skipUnless` から `REQUIRED` を外す・チェックアウトがないときに黙って抜ける改変で落ちることを手元で確かめた。pytest がないときに落ちるかは Engine の本物の中身が要るのでここでは見ない。

写し（`.github/workflows/knowledge-enforcement.yml`）がないとき、`test_ci.py` は CI（`CI=true`）か、`K-*.yaml` の `wired: true` の解決策が `wired_by` に写しを書いているときは飛ばさずに落とす（建設者が写したあとで写しを消した・名前を変えた PR を止める。`engine-test` は `CI=true` で走るので、そこでも飛ばして緑にならない。議決 `D-0053`、Issue #1144）。どちらでもない手元では、まだ写していないとして飛ばす。写しがある・CI・記録が写しを書いている・どれでもないときの振る舞いは `test_ci.py` 自身が確かめる。

### Engine の先頭で定期に見る（`ci/knowledge-enforcement-head.yml`）

`test_engine_patch.py` は `ENGINE_REF` の版だけを見るので、`ENGINE_REF` が古いまま Engine の既定のブランチの先頭だけが進んで差分が当たらなくなっても気づけない（議決 `D-0036`、Issue #1076）。環境変数 `ENGINE_PATCH_REF` に版を渡すと、`test_engine_patch.py` は `ENGINE_REF` の代わりにその版に差分を当てる（`patch_stale` の文も `ENGINE_PATCH_REF <版>` と出す）。

`ci/knowledge-enforcement-head.yml`（`tools/sendback-check/ci/sendback-engine-head.yml` と同じ形）は、PR では走らせず 1 日 1 回と手動で、Engine を `ref` なしで既定のブランチの先頭から取り、`ENGINE_PATCH_REF` を先頭の版にして `test_engine_patch.py` を走らせる。

- 通ったら記録しない
- `patch_stale` なら `::error` を出し、Issue #968 に先頭の版・その時の `knowledge-check.yml` の `ENGINE_REF`（`test_engine_patch.py` の `engine_ref()` で読む。読めなければ「読めなかった」と書く）・実行の URL・当たらなかったところを記録する。最初の行の印（`<!-- knowledge-enforcement-head: <先頭の版> patch_stale -->`）が #968 にすでにあれば足さない。これまでの記録が読めなければ足す側に倒し、記録に失敗したらジョブを落とす
- `patch_stale` でない落ち方（Engine を取れなかった・テストが壊れた）は `::error`（`head_check_failed`）を出してジョブを落とすが、#968 には記録しない

`test_ci_head.py` が、ワークフローの形（定期と手動だけ・`ref` なし・`issues: write`）と、作った Engine と偽の `gh` で手順を動かした振る舞い、`.github/workflows/` の写しがあればひな形と同じことを確かめる。

```sh
  python3 -m unittest discover -s tools/knowledge-enforcement-check -p test_engine_patch.py
```
