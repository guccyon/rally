# ADR 0008: 運営会社の管理システム（backoffice）をプロダクトから分ける

- 状態: 見送り（2026-10-27 建設者）。Gen1 は同居のまま（A に近い。本部の既存の画面はそのまま残す）。rally は工場建設のためのデモアプリなので分離は実装しない。Gen2 で作るかも未定で、作るなら別の工場でフルスクラッチの v2 になる見込み。この ADR は将来の v2 の設計の参考として残す
- 関係: `specs/context-map.yaml`、`specs/contracts/README.md`（5 アプリの枝）、`specs/contracts/events/asyncapi.yaml`、`specs/contracts/api/admin-web/openapi.yaml`（`getSlotSupply` / `getCoachReviewSummary` / `listCoachReviews`）、ADR 0002 Q3（コーチの操作は admin-web に同居）、ADR 0003（層）、ADR 0004（スキーマ）、ADR 0005（境界間イベントの購読）

## 背景

いまの admin-web には、コーチの操作（予約枠の登録・添削の返却・通話）と、運営会社（本部）の画面（予約枠の需給・コーチの評価）が同じアプリ・同じバックエンド・同じ DB に同居している。

建設者の方向性（2026-10-27）:

- 運営会社側の画面は CRM のように育つことが予想されるので、プロダクトと同じシステムに乗せない
- 運営会社側からプロダクトのデータを変えるときは、プロダクトの API を呼ぶ
- レッスンなどプロダクト側のデータは、非同期で管理システム側に連携する
- 予約枠の需給は数だけでは決まらない。時間帯（ゴールデンタイムなど）や、スポーツごとの年齢層（若年層が多い・大人が多い）を加味しないと判定できない。数だけの結果は参考情報としてはよい
- 運営会社側のトップはメニューではなく、よく見る数字が並ぶダッシュボードがよい

## 設計（案。見送り）

### 1. 境界

- 運営会社の業務を新しいコンテキスト **backoffice**（運営管理）にする。持つもの: 運営会社の担当者のアカウント、プロダクトから写した読み取り用のデータ（投影）、需給・コーチの評価などの集計、今後の CRM（生徒・コーチとの接点の記録、施策）
- backoffice は**別のシステム**にする。別のアプリ（`apps/backoffice-web`）、別のバックエンド（`apps/backoffice`）、別の DB。プロダクトの DB は読まない・書かない
- プロダクト（いまの `apps/backend`）が生徒・コーチ・予約・レッスン・評価の正本であり続ける。backoffice のデータはすべて写し（投影）で、食い違ったらプロダクトが正
- admin-web は**コーチの画面**に戻す（ADR 0002 Q3 の同居はコーチの操作だけ）。プロダクトの identity から本部の役割を外す
- context-map.yaml に `backoffice` を足す。契約は `specs/contracts/api/backoffice-web/openapi.yaml`（backoffice-web が呼ぶ API）と、`specs/contracts/api/product-admin/openapi.yaml`（backoffice がプロダクトを呼ぶ API）を足す

### 2. プロダクト → backoffice: 境界間イベントの非同期連携

- プロダクトは境界間イベント（`asyncapi.yaml`）を外に出し、backoffice が購読して投影を作る。同期の問い合わせで backoffice の画面を作らない（プロダクトが止まっても backoffice の画面は見られる。プロダクトの負荷に影響しない）
- 取りこぼさないため、プロダクトは**トランザクションアウトボックス**で出す（業務の保存と同じトランザクションでイベントの行を書き、別の処理が送る）。購読側は `event_id` で重複を捨てる（少なくとも 1 回届く前提）
- 送る経路（メッセージ基盤）は Gen1 では選ばない。最初はアウトボックスを backoffice が HTTP で順に取りに行く形（`GET /events?after=<cursor>`）で足りる。本物の基盤（SNS/SQS など）に変えても購読側の作りは変わらない
- 足りないイベントを足す: `SlotPublished` / `SlotClosed`（需給の分母）、`AccountRegistered`（生徒・コーチの台帳）、`LessonReviewSubmitted`（評価）。いまの `BookingConfirmed` などはそのまま使う。個人情報はイベントに載せる最小限（ID と、判定に要る属性だけ。氏名・連絡先は載せない）
- 行動イベント（`specs/analytics/events.yaml`）とは別物のまま。行動イベントは分析基盤へ、境界間イベントは backoffice へ

### 3. backoffice → プロダクト: API で実行

- 運営会社がプロダクトのデータを変える操作（コーチの停止・表示の変更・返金の起票など）は、プロダクトの `product-admin` API を呼ぶ。backoffice は自分の投影を書き換えて済ませない（結果はイベントで戻ってくる）
- 認証は利用者のトークンではなく、backoffice のサービス用の資格情報（サービス間の認証）。誰が操作したかは `operator_id` として必ず渡し、プロダクト側で監査の記録に残す
- 書き込みの操作は冪等キー（`Idempotency-Key`）を受ける（backoffice が再送してよいように）
- Gen1 の範囲では書き込みの操作はまだない（読むだけ）。枠だけ契約に置く

### 4. 予約枠の需給の判定

- 判定は backoffice の集計に移す（プロダクトの `getSlotSupply` は backoffice ができたら廃止。expand → contract）
- 切り口を 3 つにする: **スポーツ × 時間帯 × 年齢層**
  - 時間帯: 曜日（平日 / 休日）× 時間帯の区分（例: 朝・昼・夕方・夜。夜 19〜22 時をゴールデンタイムとする仮置き）。区分は設定で変えられる
  - 年齢層: 生徒の年代（例: 〜12・13〜18・19〜29・30〜49・50〜）。プロダクトに生徒の生年（または年代）がまだないので、identity に足す必要がある（個人情報の追加。登録時の任意項目、年代だけを外に出す）
- 画面では**判定（足りている / 足りない）を断定しない**。数（公開した枠・予約しようとした生徒・埋まった割合）を切り口ごとに並べ、目安の色付けは「参考」と明記する。判定の式は、実データで切り口ごとの傾向が見えてから決める
- 数の取り方（公開した枠・予約しようとした生徒の定義、期間 30 日）は `getSlotSupply` の定義を引き継ぐ

### 5. 運営会社側のトップはダッシュボード

- トップにはメニューではなく、毎日見る数字を並べる。最初の候補（すべて投影から集計）:
  - 今日・今週の予約の数と、確定・キャンセルの内訳
  - 完了したレッスンの数（同期・非同期）と、返却待ちの添削の数（納期が近い順）
  - 新規の生徒・月額契約の開始の数
  - 予約枠が足りないスポーツ × 時間帯の上位（参考）
  - 評価の平均が下がったコーチ・評価の件数が少ないコーチ
- 各数字から詳しい画面（需給・コーチの評価など）へ移れる。メニューは横に置く
- 数字の定義は `specs/analytics/` のセマンティック層（kpi）に 1 か所で置き、ダッシュボードと週次のレポートで同じ定義を使う

## A と B（2026-10-27: どちらも採らず見送り。記録として残す）

| | A: Gen1 は同居のまま設計だけ残す | B: いま分ける |
|---|---|---|
| Gen1 でやること | 本部の画面をこれ以上増やさない。この ADR と context-map・契約の枝だけ足す | 下の「B のチケット」を工場に流す |
| 本部の既存の画面 | admin-web にそのまま残す（凍結） | backoffice-web に移し、admin-web から消す |
| 需給の切り口・ダッシュボード | Gen2 で backoffice として作る | backoffice で作る |
| 費用 | ほぼなし | チケット 5〜8 本＋アウトボックスと取り込みの基盤 |

### B のチケット（下書き。依存の順）

1. 契約: context-map に `backoffice`、`asyncapi.yaml` に不足のイベント、`backoffice-web` と `product-admin` の OpenAPI の枝
2. プロダクト: トランザクションアウトボックスと `GET /events?after=`（サービス間の認証つき）
3. backoffice のバックエンドの雛形（同じ層の構成。ADR 0003）と、イベントの取り込み（重複を捨てる・カーソルを持つ）、投影（予約・枠・レッスン・評価）
4. backoffice の担当者のアカウントとログイン
5. 需給（スポーツ × 時間帯）の集計と画面。年齢層は 6 の後
6. identity: 生徒の年代（任意項目）を足し、`AccountRegistered` に年代を載せる（スキーマの expand）
7. ダッシュボード（トップ）
8. 移行: admin-web から本部の画面と、プロダクトの `getSlotSupply`・本部の役割を外す（contract。建設者の承認）

## 選ばなかった案

- **同じバックエンドの中でモジュールとして分ける（DB も同じ）**: 作るのは早いが、CRM が育つほどプロダクトの DB とリリースに引きずられる。建設者の方向性（システムを分ける）と合わない
- **backoffice がプロダクトの DB を直接読む（読み取り専用のレプリカなど）**: 連携の作りは要らないが、プロダクトのテーブルの形が backoffice との契約になり、スキーマを変えにくくなる（ADR 0004 の expand → contract が backoffice まで広がる）
- **backoffice がプロダクトの API を同期で呼んで画面を作る**: イベントの基盤は要らないが、集計のたびにプロダクトに負荷がかかり、プロダクトが止まると backoffice も見られない。時間帯・年齢層の集計にはプロダクトにない形の読み取りが要る

## 未決（v2 を作るときに決める）

- 生徒の年代を持つか（個人情報の追加。B の 6、A なら Gen2）
- 時間帯の区分とゴールデンタイムの定義（仮置き。実データで見直す）
