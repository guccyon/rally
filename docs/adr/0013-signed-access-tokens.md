# ADR 0013: アクセストークンをサーバーの鍵で署名する（実利用者が入る前に）

- 状態: 提案（工場）（2026-11-14、Issue #1593）
- 関係: ADR 0003（層。実装は infra、選ぶのは server）、ADR 0011（coach-app・admin-web の入口とログイン）、ADR 0012（確認コードでのログイン）、`apps/backend/README.md` の「認証と認可」「staging でトークンを作る」

## 文脈

本番の backend は、本部・コーチ・生徒のどの機能も署名なしの `MockTokenService`（`mock.<役割>.<アカウント ID>`）でトークンを発行・検証していた。生徒に見えるコーチの ID から `mock.coach.<ID>` を作ればコーチになりすませ、`mock.headquarters.<任意の UUID>` で本部の読む操作が通る（#1552 の設計書の「気をつけること」）。本番の DB はまだ空で、事業主の判断（2026-11-14）は「実利用者が入る前に塞ぐ。今すぐ本番は止めない」。

署名の鍵は秘密情報で、工場は作らず、リポジトリに置かない。配り方は人（提供元）が用意する。

## 決定

1. **トークンはサーバーだけが持つ鍵の HMAC-SHA256 で署名する**（`infra::SignedTokenService`）。形は `v1.<役割>.<アカウント ID>.<署名>`（署名は前の 3 つの HMAC を base64url）。契約の `bearerAuth` はもともと不透明な文字列なので、契約もクライアントも変えない。鍵を知らなければ作れず、役割・ID を書き換えると検証に通らない（401）
2. **鍵は環境変数 `ACCESS_TOKEN_SIGNING_KEY` から読むだけにする**。あれば署名付き、ないか空なら今までの署名なしのモック（`infra::AccessTokenBackend`）。32 バイトより短い鍵では起動しない（黙ってモックに倒さない）。`deploy/compose.yaml` は shipper の環境変数をそのまま渡し、値は置かない
3. **本部・コーチ・生徒は同じ 1 つの実装で発行・検証する**。server の組み立て（`Ports::tokens`）がどの機能にも同じものを渡す。確認コードでのログイン（coach-app の `/login-codes`・`/sessions`、#1416）と本部のログイン（#1418）も、発行はここから受け取る
4. **期限と失効は持たない**（今のモックと同じ）。鍵を替えると発行済みのトークンはすべて通らなくなる
5. **staging のトークンはサーバーと同じ鍵を持つ backend のコンテナの中で作る**（`access-token --hints` / `--account <ID>`。同じイメージに同梱）。触れる環境のログインの手がかり（`.factory-config/ship.yaml` の `touch.accounts`）もこれに替え、鍵を backend のコンテナの外に出さない。合成シードはユースケースを直接呼ぶのでトークンを使わない
6. **権限の体系（どの役割が何をできるか）は変えない**。変わるのはトークンを誰が作れるかだけ

## 結果

- 鍵を入れた環境では、手で作った `mock.` のトークンと改ざんしたトークンはどの役割の操作でも 401（`crates/server/tests/it/signed_access_tokens.rs`）
- 鍵を入れるまでは本番も staging も今までどおりモックで動く（起動時に `access tokens are unsigned mock tokens` と書く）。**本番と staging に鍵を配る（置き場を用意して shipper に渡す）のは人の作業で、それが済むまでなりすましは塞がらない**。運用 operating の前に済ませる
- 本番と staging は別の鍵にする（staging のトークンで本番に入れないように）
- 期限がないので、漏れたトークンは鍵を替えるまで使える。期限・更新・失効（coach-app の `revokeCoachSession`）は、ログイン（#1416・#1418・ADR 0012）を backend に入れるときに別に決める

## とらなかった案

- **JWT（ライブラリ）**: 役割と ID の 2 つしか載せず、検証するのも自分だけなので、アルゴリズムの選択（`alg`）やヘッダーの扱いを持ち込む利点がない。外部 IdP と組むときに改めて考える
- **鍵がなければ起動しない（本番だけ必須）**: 鍵の置き場がまだないので、入れた時点で本番と staging が止まる（「今すぐ本番は止めない」に反する）。鍵を配る段で、本番の設定で必須にするかを人が決める
- **DB にセッションを持つ（不透明な乱数のトークン）**: 失効はしやすいが、テーブル（expand）と毎回の照会が増える。今はなりすましを塞ぐことが目的で、失効はログインのチケットで扱う
