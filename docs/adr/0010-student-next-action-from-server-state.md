# ADR 0010: 生徒アプリの次の操作はサーバーの状態から出す

- 状態: 提案（工場）（2026-11-13、Issue #1437。#1436 の t1）
- 関係: ADR 0003（backend の層と依存の向き。API はこれに従って足す）、ADR 0005（ビデオ通話の枠の消費の決まりは変えない）、ADR 0006（初回の判定と完了の記録はサーバーの記録に従い、アプリで数え直さない）、`specs/contracts/api/student-app/openapi.yaml`（`getMyNextActions`・`NextAction`）、`specs/stories/student-resumes-next-action.yaml`、`specs/stories/student-subscription-persists.yaml`、`specs/ux/issue-1436.yaml`

## 文脈

生徒アプリは「登録 → 予約 → 確定 → レッスン → 完了 → 契約」をアプリの中の 1 本の段（FlowStep）として持ち、次の操作をその段の画面にだけ置いている。ホーム・自分の予約・お知らせは読むだけの脇の画面で、段に戻る道がない。そのため、続きの画面を一度離れる・アプリを開き直すと、次の操作に戻れない不具合が繰り返し出た（#1425・#1430 予約の確定、#1424・#1429 入室前チェック・ビデオ通話、#1423 完了の記録、#1431 月額契約）。#1432 はアプリを開いている間の状態で直しただけで、開き直すと同じだった。段の状態は端末の中にしかないので、端末側の状態からは復元できない。

## 決定

1. 生徒の次の操作は、サーバーの状態（予約の状態と時刻、通話セッションの終了、動画の添削の状態、完了したレッスンの記録の有無、受講権の有無）から決め、student-app の `GET /me/next-actions`（`getMyNextActions`）で返す。返すのは `NextAction` の並びで、並びがそのまま優先の順（3 件まで）。決め方は契約の `getMyNextActions` の説明に置き、そこを 1 つの定義にする
2. アプリはサーバーが返した次の操作を、返った順のまま入口（ホームの「次にやること」など）に出す。アプリの中の段（FlowStep）や端末の状態は、次の操作を出す根拠にしない。並べ替え・数え直しもしない（ADR 0006 と同じ考え）
3. 続きの画面（予約の確定待ち・予約が確定しました・レッスンの完了・添削結果）は、`NextAction` に載る ID で今の操作（`listMyBookings`・`getVideoReview`・`getMyEntitlement` など）からサーバーの記録を読み直して開く。新しく足す API は `getMyNextActions` の 1 つだけにする
4. 契約は足すだけにし、既存の操作は変えない

## 結果

- 状態の正本がサーバーに一本化され、画面はそれを読むだけになる。どの画面から離れても、アプリを開き直しても、同じ次の操作に届く
- 次の操作の種類を増やすときは、API（`NextActionKind` と決め方）と入口の画面の両方を変える。`NextActionKind` に値を足すのは互換を保つ変更で、アプリは知らない値を出さない
- 「どの状態の利用者がどこから次の操作に入るか」を `specs/stories/student-resumes-next-action.yaml` に書き、QA の判定で通す

## 選ばなかった案

- **アプリ側で状態を保持して復元する（段の状態を端末に保存する）**: 端末ごと・ログインし直しで食い違い、サーバーの記録（確定・キャンセル・添削の返却）と二重の正本になる。コーチが添削を返したようにアプリの外で状態が変わると追えない
- **画面ごとに個別の API や当て布で直す**: #1432 のように段ごとの直しでは開き直すと戻れず、同じ型の不具合が段を足すたびに出る
