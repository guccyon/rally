# ADR 0009: ドメインの区分（コア・支援・汎用）とプロフィールの切り出し

- 状態: 承認（方針は 2026-10-28、仮決め 3 点の答え合わせは 2026-10-29 オーナー）
- 関係: specs/context-map.yaml、specs/product-context.md、Golden Set 0013（評価の境界を変えた負例）

## 文脈

Golden Set の答え合わせで、オーナー が rally のドメインの捉え方を示した。ドメインでも代表的なファーストクラスのもの（コアドメイン）と、支援・汎用のサブドメインは分けて考えたい。ファーストクラスは生徒アプリでタブとして切り出す主業務で、レッスンの選択・予約、ライブレッスン、チャット、プロフィールがタブになる。評価（レビュー）は支援サブドメインで、なくてもオンラインレッスンは成り立つ。評価はコーチに付けられるが、評価した生徒のものでもあり、レッスンの一部でもある中間の概念。アカウントや権限は汎用サブドメイン。

今の context-map は区分を持たず、gen1_core（identity / scheduling / entitlement）は実装の順を表すだけだった。プロフィールは identity の中にあった。

## 決定

1. context-map の各コンテキストに subdomain（core / supporting / generic）を持たせる
2. プロフィール（profile）を identity から切り出し、コアにする。identity はアカウント・認証・権限（汎用）。コードの移動（表示名・自己紹介文など）は後の段で行い、それまで実装は identity にある
3. 区分: コア = catalog・matching（レッスンの選択）、scheduling、live-lesson、async-lesson、messaging、profile。支援 = review、entitlement、billing。汎用 = identity、notification、analytics

## 答え合わせ（2026-10-29 オーナー）

- **async-lesson はコア**。非同期レッスンと捉えるとコアで、競合と比べた優位性にしたい部分。見せ方はコーチとのチャットの中にインラインで展開したい。スポーツのコーチングは継続して一定期間たってから効果が出る遅効性のもので、「2 回前の添削で伝えた通り」のようにやり取りの時間軸と履歴が大事になる。ただし添削したことや回数は管理したいので、チャットのメッセージの 1 つとして動画を上げるのではなく、添削依頼の形で動画を上げさせる。チャットはレッスンのログでもあり会話でもある
- **catalog・matching はコア**。このアプリではコーチとレッスン内容のセットが商品で、事業成長のもっとも重要なパーツ。商品の選択としてもコア
- **課金まわりはプランとライセンスに分ける**。プラン（ワンショット、課金、過去の状況からの補講、期間集中など、他のサービスで再利用できない概念）はこのサービスにべったりなので支援。ライセンスは権限と同じく汎用で、認可と強く連携する。同じ会社が別のサービスを出したらアカウントは共有したい（Gmail と Google Calendar）ので、アカウントは横断のサービスとして切り出すのが自然で、ライセンス（Google One の契約のような）も同じく切り出したくなる。境界を分けておくと後から自然な設計になる
- ただし最初から大きく作らず、小さく作って後から分離する判断はある。汎用にすると機能を足すたびに「汎用の概念か」と考えて足枷になる

## 決定（答え合わせの反映）

- context-map に license（ライセンス、汎用）を足し、境界だけ引く。Gen1 の実装は entitlement の中に小さく置き、別サービスへの切り出しは後で行う（足枷にしないため、汎用の作り込みはしない）
- entitlement は「プラン（受講権）」として支援のまま
- billing は支援のまま（プラン側の課金）
- async-lesson の結果をチャットにインラインで出し、動画は添削依頼として上げる形は、製品の機能として次の段で扱う

## 結果

- 検査・判定は、コアの変更を重く、支援・汎用は軽く見られる（重さの物差し）
- 境界の変更（あるコンテキストの持ち物を別のコンテキストに移す）は、区分をまたぐときに特に人に確かめる
