- 人の判断待ちが約 4 時間 19 分（10:06:59〜14:26:10）続いた。人の答えは「推奨どおり（PR のまま）」で、judge の推奨がそのまま採られた

## 観点ごとのなぜなぜ

### spec（確からしさ low）

1. なぜ人に回ったか: 仮決めのうち aesthetic（見た目）の 1 件を、judge が自動では採れないと判断したから
2. なぜ自動で採れなかったか: その仮決めは確信度が一番低く（provisional 0.5、judged 0.55）、根拠が self_report ではなく track_record（過去の実績）だったから
3. なぜ見た目を実装役が仮決めしたか: チケット #515 か specs/ に、画面の見た目の決まりが無かったからと見られる（推測。チケット本文と handoff/ が材料に無い）
4. なぜ見た目の決まりが無かったか: 記録が無く確かめられない（推測）

- 真因: チケット #515 の入口に、画面の見た目（aesthetic）の決まりや既存の型への参照が足りなかった。そのため実装役が仮決めし、それが人の判断に回ったと見られる（推測）

### communication（確からしさ mid）

1. なぜ PR 本文が直されたか: rubric と judge が、本文に「## 背景」「## 問題」が無いことと、見出しが二重になっていることを欠陥としたから
2. なぜ見出しが二重になったか: 衝突を解いた job 1439 が、自分の報告を「## 既定ブランチの取り込みと衝突の解消（job 1439）」として本文の末尾にそのまま足したから
3. なぜそのまま足したか: 同じ PR を続きの job が触るときに、本文をどう更新するか（上書きか、追記か、要約か）の決まりが実装役に伝わっていなかったから（推測）
4. なぜ状態が食い違ったか: job 1439 が「コミットしていません」と書いたが、10:03:06 に head が更新されている。報告を書いた時点と最終の状態がずれたまま、確かめずに渡したから

- 真因: 続きの job（continue）が PR 本文を更新するときの型と、本文の必須の見出し（背景・問題）が実装役に伝わっていなかった。そのため、検査役と判定役に渡る本文が二重で、状態も食い違っていた

### inspection（確からしさ mid）

1. なぜ本文の欠陥がマージ前まで残ったか: rubric の gate が shadow のモードで動いていて、欠陥を見つけても止めなかったから
2. なぜ実装役の段階で止まらなかったか: 実装役が PR を開く前に、本文を必須の見出しと照らし合わせる仕組みが無かったから（推測）
3. なぜ停止が要ったか: judge が aesthetic の 1 件を escalate したから。ただし人は推奨どおりに答えており、結果から見ると止める必要は無かった

- 真因: 本文の型の検査が shadow で、実装役の側に事前の照合も無かった。また judge の escalate のしきい値が、aesthetic について実績が無いだけで人に回す設定になっている

### process（確からしさ mid）

1. なぜ停止が 4 時間 19 分続いたか: aesthetic の 1 件だけのために、PR 全体が人の判断待ちになったから
2. なぜ待ちの間に状況が悪くなったか: 10:09:21 に PR がまた main と衝突したのに、衝突を解く continue が判断の後（14:28:59 に enqueue）まで起きなかったから
3. なぜ起きなかったか: supervisor が判断待ちの停止を優先し、衝突の検知を新しい停止として起こさなかったからと見られる（推測。14:27:11 に ci の停止が開いたのは判断の直後）
4. なぜ衝突が繰り返したか: 依存先の #497（D148）の周りで main が速く進んでいて、PR が長く開いていたから（推測）

- 真因: 人の判断待ちと衝突の解消が、並列ではなく順番に処理された。そのため、待っている間に起きた衝突への対応が、判断の後まで遅れた

## 真因

- aesthetic の仮決めに判断の材料（入口の見た目の決まり・実績）が無く、judge が推奨を持っていても escalate のしきい値で人に回した。人は推奨どおりに答えた
- 続きの job が PR 本文を更新する型と、本文の必須の見出しが実装役に伝わっていなかった。rubric の検査も shadow で止めなかった
- 人の判断待ちの間に起きた衝突への対応が判断の後まで動かず、待ちと手戻りが順番に重なった

## 学び

1. テーマ 4（役割間の言葉と伝達）→ K-0003: 続きの job が自分の報告を PR 本文に追記すると、見出しが二重になり、状態も食い違う
   - 作用先の候補: role_line_engine。提案: continue（conflict）の job への指示に「PR 本文は追記せず、全体を最新の状態に書き直す。取り込みとコミットの状態は head を確かめてから書く」を加える。繰り返しそう: はい
2. テーマ 6（工程の進め方）→ K-0004: 人の判断待ちの間でも、衝突のような機械的な手戻りは並行して解かないと、判断の後で待ちが重なる
   - 作用先の候補: monitoring_runbook。提案: 判断待ち（factory:needs-judgment）の停止中に pr.conflicted を検知したら、すぐに continue（conflict）を enqueue する。停止の記録にも衝突中と書き足す手順にする。繰り返しそう: はい
