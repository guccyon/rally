## 観点ごとのなぜなぜ

### spec（確からしさ mid）

1. なぜ ARCH-004 が出たか: 片方の日付だけのときの省き方を、`list_announcements.rs` に `listCancelledBookings` の写しとして新しく書いたから
2. なぜ写したか: Issue の「listBookings と同じ 1 か所の規則を使う」は、期間の規則（BookingPeriod・31 日・422）を指すと読めたが、省いた側をどう補うかは決めていなかったから
3. なぜ補い方が決まっていなかったか: listBookings 型（from を省けば今日）と過去を引く型（listCancelledBookings の 7 日）の 2 つの省き方があるのに、名前も置き場所も定義されていなかったから。過去を引く型の規則は `list_cancelled_bookings.rs` の execute の中にしかなかった
4. なぜ定義が無かったか: `calendar_day` に `period`（listBookings 型）が入ったのは作業の途中（job 3040 の取り込み）で、過去を引く型の関数はどこにも無く、仕様や用語集にもその区別が書かれていなかったから（用語集を確かめたかは記録に無いので推測）

- 真因: チケットと specs が「同じ 1 か所の規則」の範囲（期間の規則か、省き方まで含むか）を決めておらず、過去を引く一覧の省き方も共有の場所に定義されていなかった

### communication（確からしさ high）

1. なぜ差し戻しのあとも本文の指摘（job 3317 の PR-002）が残ったか: job 3316 は差分を直したが、PR 本文の本体の「対応内容」と job 3040 の節に「start/end だけを使う、period は通さない」という古い説明が残ったから
2. なぜ古い説明が残ったか: 続きのジョブは、自分の要約を新しい節として本文に足すだけで、本体を今の差分に合わせて書き直していなかったから
3. なぜ足すだけになったか: 衝突の解消 23 回と review_fix のそれぞれが、`## 概要`・`## 対応内容` などを本体と同じレベルの見出しで書いた要約を出し、それがそのまま本文に積まれる流れになっていたから
4. なぜその流れを誰も止めなかったか: 本文の組み直しは body_fix（tier-small）に任されていた。body_fix は「## 本文の読み方」「（補足）」を足して取り繕うだけで、指示役も実装役も本文の構造を直す責任をはっきり持っていなかったから
5. あわせて: 最初の実装（impl-1）の仮決めの「規則を写さない」という言葉と、実際の写しのコードが食い違っていた。言葉の「1 か所」と実装の「1 か所」がそろっていなかった

- 真因: 続きのジョブの報告がそのまま PR 本文に足される流れで、本体を今の差分に合わせて書き直す役割と手順が無かった。仮決めの言葉（1 か所の規則）とコードを照らし合わせる習慣も無かった

### inspection（確からしさ mid）

1. なぜ ARCH-004 はもっと早く止まらなかったか: 記録にある検査は job 3313 だけで、写しのコードは job 2367 から約 14 時間残っていた
2. なぜ早く見つからなかったか: 衝突が 23 回続いて head が変わり続けたので、検査が最後まで回らなかったか、shadow のルーブリックが毎回同じ所を見ていなかったと考えられる（以前の head の検査の記録が無いので推測）
3. なぜ衝突を直すジョブでも気づかなかったか: job 3040 で `calendar_day` に「ここだけを通して決める」という約束が入ったのに、取り込みの検査は fmt・clippy・テストと衝突の印だけで、共有モジュールの約束が変わったことと自分の差分を照らし合わせる検査が無かったから
4. なぜ本文の食い違いがマージ直前まで残ったか: body_fix（job 3319）のあと、もう一度検査せずに 5 秒後にマージされた。inspector_approved の根拠は「採用した指摘は続きのジョブか差し戻しで直す」で、直したことを確かめる段が無かったから

- 真因: 取り込みで共有モジュールの約束が変わっても、差分の設計をもう一度検査する決まりが無かった。仮決めの主張（規則を写さない）と差分を突き合わせる検査が、最初の実装のときに働かなかった。body_fix のあとに確かめないままマージできた

### process（確からしさ mid）

1. なぜ差し戻しの前に PR が約 14 時間開いたままで、本文が崩れたか: conflict による continue が 23 回続いたから
2. なぜ衝突が続いたか: どの PR も CHANGELOG.md の `[Unreleased]`「追加」の先頭に行を足すので、既定ブランチに何かがマージされるたびに同じ所で衝突したから
3. なぜ毎回マージされずに次の衝突を待ったか: merge_decided は executed=false で、マージは人が行っていた。承認からマージまでの待ちの間に、ほかの PR が先に入った（待ちの長さは記録に無いので一部推測）
4. なぜ途中で止めなかったか: conflict の continue に回数や費用の上限が無く、エスカレーションも無かったから。同じ会話を引き継ぐ形で費用が積み上がり（job 3316 の時点で 14.4 USD、3.2M tokens）、本文の見出しも増え続けた

- 真因: CHANGELOG の決まった 1 か所に行を足す運用が並行する PR どうしの衝突を必ず生み、continue に上限もエスカレーションも無いまま、人のマージを待つ間に衝突の解消が繰り返された

## 真因

- チケットと specs が「同じ 1 か所の規則」の範囲を決めておらず、2 種類の省き方（listBookings 型と過去を引く型）も用語として定義されていなかった。そのため実装役は写しのコードを書き、仮決めでは「写さない」と説明するという食い違いが生まれた
- 続きのジョブの要約がそのまま PR 本文に足される流れで、本体を今の差分に合わせて書き直す役割も、body_fix のあとに確かめる段も無かった。そのため本文の構造が崩れ、本文と差分が食い違った
- CHANGELOG の決まった場所への追記が衝突を繰り返し生み、conflict の continue に上限もエスカレーションも無かった。そのため 23 回の取り込みの間に、共有モジュールの約束の変化が設計として見直されなかった

## 学び

1. テーマ 6（工程の進め方）→ K-0009: conflict の continue に回数の上限もエスカレーションも無いと、同じ形の衝突の解消が繰り返され、費用と本文の追記が積み上がり、その間に入った共有モジュールの約束の変化も設計として見直されない
   - 「並行する PR が CHANGELOG.md の同じ場所に追記すると衝突を必ず生む」という部分は既存の K-0002 と同じ因果なので、新しい知見にせず K-0002 の根拠に足した（下の「既存の知見の扱い」）。断片方式（changelog.d/）は K-0002 の enforcement に入っている
   - K-0009 は K-0002 に無い「continue に上限が無いこと」と、その結果として起きることに絞る
   - 作用先の候補: improvement_ticket。提案: conflict の continue に回数の上限（例: 5 回）を設け、超えたら人にマージを促すかエスカレーションする。繰り返しそう: はい
2. テーマ 4（役割間の言葉と伝達）→ K-0010: 差分の設計を変える続きのジョブ（review_fix）が PR 本文に自分の要約を足すだけで本体を書き直さないと、本体に古い説明が残り、本文と差分の食い違いが検査でもう一度指摘される
   - 見出しが同じレベルで積まれたこと（K-0001）と、本文を組み直す持ち主がいないこと（K-0006）は既存の知見と同じ因果なので、それぞれの根拠に足した。K-0010 は「本体の中身が今の差分と食い違う」ことに絞る
   - 作用先の候補: role_line_engine。提案: 続きのジョブ（conflict・review_fix）の実装役に、(1) PR 本文の本体（概要〜知見）を今の差分に合わせて書き直す、(2) 取り込みの記録は末尾の「## 取り込みの記録」の下に ### の小見出しでだけ足す、を指示する。Engine 側は、要約を本文に足すときに ## の見出しを 1 段下げる。繰り返しそう: はい

提案（作用先への変更）はこの記録では実装しない。spec の観点の真因（「同じ 1 か所の規則」の範囲と、過去を引く一覧の省き方が定義されていない）は、製品の仕様と用語集の欠けで、工場の知見ではなく specs/ の Issue で扱うものなので、知見にはしていない。inspection の観点の真因（取り込みのあとに設計を検査し直さない、body_fix のあとに確かめずにマージできる）は事例 1 件の推測が多く、K-0009・K-0010 の結果の側に書くにとどめた。

## 既存の知見の扱い

- K-0001（続きのジョブの報告が PR 本文の末尾に足され、見出しの組が二重になって差し戻しになりやすい）: 直す（amend）。この事例の 23 回の衝突の解消と review_fix が `## 概要`・`## 対応内容` を同じレベルで積み、PR-002 の指摘になったのは K-0001 と同じ因果なので、C-0005・PR #656・case.analyzed:274365 を evidence に足し、verified_at と review_by を更新した。statement と確かさ（hypothesis）は変えない
- K-0002（CHANGELOG.md の同じ場所への追記で衝突が起き、重い続きのジョブが走る）: 直す（amend）。この事例の 23 回の衝突は CHANGELOG.md の `[Unreleased]` の先頭への直接の追記によるもので、K-0002 と同じ因果。断片方式の後も CHANGELOG だけの衝突が続いた（invalidate_when）例ではないので、C-0005・PR #656・case.analyzed:274365 を evidence に足し、verified_at と review_by を更新した。statement・確かさ・enforcement は変えない
- K-0003（judge の verdict「adopt」が 2 つの意味で使われる）: そのまま（keep）。この事例の adopt は 2 件とも欠陥を直す対象で、数え方の食い違いは起きていない
- K-0004（supervisor が差し戻しを adopt の件数で起こすと、直すもののない差し戻しが記録される）: そのまま（keep）。この事例の差し戻しには直っていない採用欠陥（ARCH-004・PR-002）があり、K-0004 の線でも起こすべき差し戻しだった
- K-0005（PR 本文の見出しの定義が 3 つの場所で揃っていない）: そのまま（keep）。この事例の PR-002 は見出しの欠けや定義の割れではなく、同じ見出しの積み重ねと本体の古い説明によるもので、K-0001・K-0010 の側の因果
- K-0006（本文を末尾への追記だけで直し、全体を組み直す持ち主がいないと崩れる）: 直す（amend）。この事例の body_fix は「## 本文の読み方」「（補足）」を足して取り繕うだけで、組み直す持ち主がいなかった。K-0006 と同じ因果なので、C-0005・PR #656・case.analyzed:274365 を evidence に足し、verified_at と review_by を更新し、related に K-0010 を足した。statement と確かさは変えない
- K-0007（続きの job が head を確かめずに状態を書くと、本文に食い違いが残る）: 再確認（recheck）。K-0007 の根拠の C-0004 は「本文の全体は書き直さず、続きの job の節だけを最新にする」という直し方の向きを書いていて、K-0010 の提案（本体を今の差分に合わせて書き直す）とぶつかる。差分の設計を変えない衝突の解消と、設計を変える review_fix とで向きを分ければ両立すると見るが、どちらを正にするかは委員会が決めるべきなので、statement は変えず related に K-0010 を足すだけにした
- K-0008（判断待ちの停止中に起きた衝突の解消が判断の後に回る）: そのまま（keep）。K-0009 も衝突の continue を扱うが、K-0008 は判断待ちとの順番、K-0009 は continue の回数の上限の話で、因果が別。矛盾もしないので、K-0009 の related に K-0008 を書くだけにした
