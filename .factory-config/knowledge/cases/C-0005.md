# C-0005: 続きのジョブの追記が重なり、採用済みの本文の指摘が残ったままマージされた差し戻し（PR #659）

- 出来事の種類: 差し戻し
- 分析の記録: 制御プレーンの events `case.analyzed`（id 274379）。事例型の分析役（Engine ADR 0023）
- 対象: PR #659（Issue #648、コーチの様子に返却待ちの件数を足す変更）
- 記録日: 2026-11-05
- 知見: K-0009（テーマ 4）、K-0010（テーマ 6）。既存の K-0001・K-0002・K-0005・K-0006 に根拠を足した

## 出来事

PR #659 は、コードの判断 6 件がずっと採用されていたのに、検査の PR-002（本文の構成）で採用の指摘が 10 回近く出続けた。

- main の取り込みで衝突が起きるたびに、続きのジョブ（conflict が 20 回、ci_failed が 1 回）の summary が「## 概要」「## 対応内容」…の見出しを丸ごと持ったまま PR 本文に足された
- 本文を直す body_fix（tier-small）も、本文を書き直さずに「整理の節」を足すだけだった
- そのため同じ名前の見出しが 7〜8 組重なり、冒頭の「型引数 `P` を足した」も最新の差分（`D` の共有）と食い違ったまま残った
- 衝突のほとんどは `CHANGELOG.md` の `[Unreleased]`「追加」の同じ場所で、並行して動く別チケットとの間で 13 時間に 20 回起きた（ci_failed の 1 回は、別の PR との 13 ファイルの衝突のあとの CI 落ち）
- 続きのジョブはセッションを引き継ぎ（agent_resumed=true）、1 回ごとの cost_usd が 1.95 から 10.36 へ増えた。作業は毎回 2 ターンで終わっていた
- 最後は採用済みの指摘が残り、本文直し（job 3308）も終わる前の 20:08:43 にマージされた（本文が直されたのは 20:08:50）

## 観点ごとのなぜなぜ

### spec（確からしさ high）

1. なぜ PR-002 の指摘の一部が判定役に退けられたのか: rubric のテンプレートは「背景」「問題」を求めるが、リポジトリの CLAUDE.md の見出しにはそれがなく、PR は CLAUDE.md に従っていた
2. なぜ食い違いが残っていたのか: rubric（工場の側）と CLAUDE.md（製品の側）が別々に見出しを決めていて、どちらを正本とするかが決まっていなかった
3. なぜ正本が決まっていないと問題になるのか: 検査役は rubric で、実装役は CLAUDE.md で書くので、毎回同じ指摘が出て判定役が毎回退ける、という無駄が続く

- 真因: PR 本文の見出しの正本が、rubric（PR-002・OV-001）と CLAUDE.md で揃っていない。また、続きのジョブの記録を本文のどこにどう書くかの決まりがない

### communication（確からしさ mid）

1. なぜ本文に同じ名前の見出しが 7〜8 組重なったのか: 取り込みのたびに、続きのジョブの summary.md が本体と同じ H2 の見出し一式で書かれ、それがそのまま本文に足された
2. なぜ続きのジョブは本体と同じ見出しで書いたのか: 実装役は、summary を本体の PR と同じ形式で書くよう求められていた（推測）。自分の summary が本文に追記されることも、検査で出た PR-002 の指摘も、続きのジョブに渡されていなかった
3. なぜ指摘が渡らなかったのか: judge は採用した指摘を body_fix ジョブ（本文だけ直す役）に回し、続きの implement ジョブ（continue reason=conflict）の入力には指摘が入っていなかった
4. なぜ body_fix でも直らなかったのか: body_fix は本文を書き直さず「（この節は検査の指摘を受けて工場が本文に追記した）」という整理の節を足すだけで、「以降は ## を足さない」という約束も、次の続きのジョブには伝わらなかった
5. なぜ約束が伝わらないのか: 本文の形を決める役（body_fix）と本文に足す役（Engine が summary を追記する仕組み）が別々で、間で決まりを受け渡す仕組みがない

- 真因: 検査の指摘と本文の書き方の決まりが、本文を書き足す側（続きのジョブの summary とその追記）に渡らない。そのため、本文を直す役（body_fix）が直しても、次の取り込みでまた崩れる

### inspection（確からしさ high）

1. なぜ PR-002 は採用され続けたのに本文が直らなかったのか: 検査と判定はマージの前に毎回指摘を出したが、直すのは軽い body_fix に任され、本文の作り方そのもの（追記のしかた）は検査の対象の外だった
2. なぜ採用済みの指摘が残ったままマージされたのか: supervisor.inspector_approved の基準が「採用した指摘は続きのジョブか差し戻しで直す」で、重さがマイナー（process）の指摘はマージを止めなかった
3. なぜ body_fix が終わる前にマージされたのか: merged（20:08:43）は、body_fix 3308 が終わって本文が直される（20:08:50）のを待たずに実行された
4. なぜもっと前で止められなかったのか: 同じ rubric の指摘が何回続いたかを数えて、やり方を変える（本文を丸ごと書き直す、人に上げる）仕組みがなかった。判定役の解釈には「追記で整理する方法はすでに 3 回失敗」とあるのに、工程は変わらなかった

- 真因: 同じ指摘が繰り返し採用されても、それを数えてやり方を変える仕組みがない。また、マイナーな採用済みの指摘と進行中の body_fix を待たずにマージできる

### process（確からしさ high）

1. なぜ続きのジョブが 21 回も走ったのか: main の取り込みで、ほぼ毎回 `CHANGELOG.md` の `[Unreleased]`「追加」の同じ場所が衝突した（job 2852 は別の PR との 13 ファイルの衝突のあとの CI 落ち）
2. なぜ毎回 `CHANGELOG.md` で衝突したのか: 並行して動く多くのチケットが、同じ getCoachOverview・async_lesson の周りで、同じ CHANGELOG の行の末尾に 1 行ずつ足していた
3. なぜ衝突のたびに重い工程が走ったのか: 衝突を見つけると supervisor が tier-large の implement ジョブを積み直し（attempt 20 まで）、上限も、CHANGELOG のような機械的な衝突の自動解消もなかった
4. なぜコストが増え続けたのか: 続きのジョブはセッションを引き継ぐ（agent_resumed=true）ので、1 回ごとの cost_usd が 1.95 から 10.36 へ増え、作業は 2 ターンで終わるのにコストは毎回増えた

- 真因: `CHANGELOG.md` の `[Unreleased]` という 1 か所に、並行するチケットが書き込む構成になっていた。衝突のたびに上限なしで、セッションを引き継ぐ tier-large の続きのジョブを積み直す工程だった

## 真因

- PR 本文が、続きのジョブの summary を本体と同じ H2 の見出しで追記していく作りで、検査の指摘（PR-002）と本文の決まりが追記する側に渡らない。body_fix で直しても次の取り込みでまた崩れる
- 同じ rubric の指摘が繰り返し採用されても、数えてやり方を変える仕組み（本文の全面的な書き直し、人に上げる、マージを止める）がない。採用済みの指摘と進行中の body_fix を残したままマージできる
- `CHANGELOG.md` の `[Unreleased]` に並行するチケットが書き込むため衝突が続き、上限なしでセッションを引き継ぐ続きのジョブが 20 回走って、本文の重なりとコストを増やした

## 学び

1. テーマ 4（役割間の言葉と伝達）→ K-0009: 検査の指摘と本文の決まりは、直す役（body_fix）だけでなく、次に本文を書き足す役（続きのジョブ）にも渡さないと守られない
   - 続きのジョブの summary が本体と同じ ## の見出しで本文に足されて重なること自体は K-0001 と同じ因果なので、K-0001 の根拠に足した。末尾への追記だけで直して全体を組み直す持ち主がいないことは K-0006 と同じなので、K-0006 の根拠に足した
   - K-0009 は、そのどちらにもない「直す役が決めた決まりと採用済みの指摘が、次に書き足す役の入力に入らないので、直しても次の取り込みで崩れる」に絞る
   - 作用先の候補: role_line_engine。提案: continue（conflict/ci_failed）の implement ジョブの入力に、未解消の採用済みの指摘と、body_fix が決めた本文の決まりを入れる。実装役への指示に「PR 本文に追記される前提で ## を足さない」を書く。繰り返しそう: はい
2. テーマ 4（役割間の言葉と伝達）→ K-0005 に根拠を足した: 工場の rubric とリポジトリの開発ガイドで PR 本文の見出しが違うと、同じ指摘が毎回出て毎回退けられる
   - K-0005 の statement と同じ因果なので、新しい知見にせず K-0005 の evidence に C-0005・PR #659・case.analyzed:274379 を足した（下の「既存の知見の扱い」）
   - 作用先の候補: term_alignment。提案: PR-002・OV-001 のテンプレートを CLAUDE.md の見出し（概要・対応内容・影響範囲・互換性・動作確認・補足・仮決め・知見）に寄せる。背景・問題は「概要」に含めてよいと書く。繰り返しそう: はい
3. テーマ 6（工程の進め方）→ K-0010: 衝突のたびに上限なしで、セッションを引き継ぐ tier-large の続きのジョブを積み直すと、作業が小さくても 1 回ごとのコストが積み上がる
   - 衝突が起きる原因（並行するチケットが `CHANGELOG.md` の同じ場所に足す運用）は K-0002 と同じ因果なので、K-0002 の根拠に足した。K-0002 は changelog.d/ の断片方式ですでに担保されている。この事例はその担保が入る前の PR
   - K-0010 は、衝突が起きたあとの積み直し方（上限なし・セッションの引き継ぎ・tier-large）に絞る
   - 作用先の候補: improvement_ticket。提案: CHANGELOG だけの衝突は tier-small か機械的に解消し、conflict の続きのジョブには上限とセッションの引き継ぎの打ち切りを設ける。繰り返しそう: はい

提案（作用先への変更）はこの記録では実装しない。inspection の観点の真因（同じ指摘の繰り返しを数えてやり方を変える仕組みがないこと、採用済みの指摘と進行中の body_fix を待たずにマージできること）は、分析役が学びの候補に挙げておらず、K-0004（差し戻しを起こす条件）とも線引きを確かめる必要があるため、この記録では知見にしていない。

## 既存の知見の扱い

- K-0001（続きのジョブの報告が PR 本文の末尾に足され、見出しの組が重なって差し戻しになりやすい）: 直す（amend）。この事例の 21 回の続きのジョブの追記は同じ因果なので、evidence に C-0005・PR #659・case.analyzed:274379 を足し、verified_at と review_by を更新した。statement・確かさ・担保は変えない
- K-0002（CHANGELOG.md の同じ場所への追記で衝突が起き、重い続きのジョブが走る）: 直す（amend）。この事例の 13 時間に 20 回の衝突は同じ因果なので evidence を足し、verified_at と review_by を更新した。この PR は断片方式（changelog.d/）が入る前のもので、担保が効かなかった反例ではない。statement・確かさ・担保は変えない
- K-0003（judge の verdict「adopt」が 2 つの意味で使われる）: そのまま（keep）。この事例の adopt はどれも本文の欠陥か仮決めの承認で、数え方の混同は分析に出ていない
- K-0004（supervisor が差し戻しを adopt の件数で起こすと、直すもののない差し戻しが記録される）: そのまま（keep）。この事例は直っていない採用欠陥が残ったままマージされた側で、K-0004 の線（直っていない採用欠陥があれば起こす）と矛盾しない
- K-0005（PR 本文の見出しの定義が rubric・CLAUDE.md・報告の型で揃っていない）: 直す（amend）。学び 2 と同じ因果なので evidence を足し、verified_at と review_by を更新した。statement と確かさは変えない
- K-0006（末尾への追記だけで直し、本文全体を組み直す持ち主がいないと崩れる）: 直す（amend）。body_fix が整理の節を足すだけだったことは同じ因果なので evidence を足し、verified_at と review_by を更新した。K-0009 は K-0006 の「持ち主がいない」の先にある「決まりが書き足す役に渡らない」なので、related で互いに指す
- K-0007（続きの job が head を確かめずに状態を書くと食い違う）: そのまま（keep）。この事例の冒頭の記述と最新の差分の食い違いは、状態の書き方ではなく本文の冒頭が直されなかったことによるもので、別の因果
- K-0008（判断待ちの間の衝突の解消が判断の後に回る）: そのまま（keep）。この事例に人の判断待ちはない
