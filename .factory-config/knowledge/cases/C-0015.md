## 観点ごとのなぜなぜ

### process（確からしさ high）

1. なぜ 14 チケットで 19 回も衝突したか: admin-web を触る複数のチケットが並列で動き、同じ README の同じ場所に追記していたから
2. なぜ同じ場所に追記したか: チケットごとに README や CHANGELOG へ変更点を書く運用があり、追記先が 1 か所に集まっているから
3. なぜ並列のままだったか: 同じ領域やホットスポットのファイルを触るチケットを順番に流す・件数に上限をかける設定がないから（推測）
4. なぜ 1 回 4〜5 USD か: 文書だけの衝突でも tier-large と factory-worker:rust で、セッションを丸ごと続ける continue ジョブとして解いているから
5. なぜ 9 回繰り返されたか: continue の回数に上限も段階を上げる仕組みもなく、マージまでの待ちの間に既定ブランチが進むたび同じ流れになったから

- 真因: 共有の文書ファイルへ追記する規約と、同じ領域のチケットを並列に流す投入順が組み合わさって、衝突が構造的に繰り返される。解消を文書だけの衝突でも高いモデルで回数の上限なしにやり直すので、件数と費用が膨らむ

### inspection（確からしさ mid）

1. なぜ衝突を検査や CI で減らせなかったか: CI は 9 項目すべて通り検査役も承認していたが、衝突は承認の後に既定ブランチが進んで起きたから
2. なぜ承認の後で衝突したか: judge の終了から inspector_approved まで約 90 分待ち、承認の 38 秒後に pr.conflicted となった。その間に別の PR が同じファイルを変えていた
3. なぜ前もって止められなかったか: 投入やマージの前に「同じホットスポットのファイルを触る PR がほかに開いているか」を見る検査がないから（推測。記録にそうしたイベントは見当たらない）

- 真因: 衝突は検査の対象外で、CI と検査役は通過する。共有の文書ファイルを同時に触る PR を投入やマージの前に検知する仕組みがなく、承認からマージまでの待ちが長い

### communication（確からしさ mid）

1. なぜ検査役は毎回同じ本文の欠陥を指摘したか: 本文に「## 既定ブランチの取り込みと衝突の解消（job 833）」などの節が足され、「## 概要」「## 対応内容」などの見出しが何度も重なったから
2. なぜ重なったか: 衝突を直す continue ジョブが、そのたびに取り込みの記録を PR 本文へ追記したから
3. なぜ本文へ追記したか: 衝突の記録の置き場（PR 本文・handoff・コメント）が実装役と検査役の間で決まっていなかったと見られる（推測）
4. なぜ決まっていなかったか: 実装役は本文を作業の記録として、検査役は読み手向けの決まった構成として扱い、同じ「PR 本文」を違う目的で使っていたから

- 真因: 「PR 本文」を読み手向けの決まった構成の文書と見るか作業記録と見るかが、実装役と検査役でずれている。衝突を直すたびに本文が崩れ、body_fix が増える

## 真因

- 製品の規約として、チケットごとに共有の文書ファイル（apps/admin-web/README.md・CHANGELOG.md など）の同じ場所へ追記させているため、並列の PR どうしが衝突する
- 同じ領域のチケットを並列に投入し、承認からマージまでの待ち（約 90 分）が長く、その間に既定ブランチが進んで衝突の解消が繰り返される（例では 9 回）
- 衝突の解消を文書だけの衝突でも tier-large で丸ごとやり直し、その記録を PR 本文に積み上げるので、1 回の費用が高く本文の崩れから body_fix の手戻りも生む

## 学び

1. テーマ 6: 並列のチケットが共有の文書ファイルの同じ場所に追記する規約は、件数に比例して衝突を生む → K-0033
2. テーマ 6: 同じ領域を並列に流し承認からマージまで長く待たせると、衝突の解消が何度も繰り返される → K-0034
3. テーマ 4: PR 本文は読み手向けの決まった構成の文書で、衝突解消の作業記録を足していく場所ではない → K-0035
