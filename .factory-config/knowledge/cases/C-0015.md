## 観点ごとのなぜなぜ

### communication（確からしさ mid）

1. なぜ差し戻されたか: PR 本文に、テンプレートの見出し（概要・対応内容・影響範囲・動作確認）がなかったから（judge の PR-002 の adopt）
2. なぜ見出しがなかったか: 実装役が書いた本文のうち、「## 補足」の見出しより前と見出しそのものが、handoff の summary.md に入っていなかったから
3. なぜ入らなかったか: 実装役の最後の文から本文を取り出す受け渡しの処理が、前半を落とした。もしくは、いくつかの段落に分けて書かれた文の最後の段落だけを拾った（推測。処理の中身は記録にない）
4. なぜ誰も気づかなかったか: 実装役・検査役・判定役が「PR 本文」と呼んで見ていたものが、それぞれ違う文だった。実装役は自分の書いた文、検査役と判定役は summary.md から作られた文を見ていた。食い違いを知らせる仕組みもなかった
5. なぜ仕組みがなかったか: handoff.saved で本文を保存するときに、元の文と比べる確認や、テンプレートの見出しがあるかの確認が Engine の手順に入っていないから（推測）

- 真因: 実装役が書いた PR 本文が、handoff（summary.md）に移る途中で前半を落とした。実装役・検査役・判定役は別々の文を「PR 本文」と呼んでいて、受け渡しで中身が変わっていないかを確かめる段階もなかった

### inspection（確からしさ mid）

1. なぜ CI で止まらなかったか: pr.ci_passed の checks（admin-web・backend・rules など）に、PR 本文の形を見るものがないから
2. なぜ inspect の rubric で止まったのにもっと前で止まらなかったか: 本文の確認が inspect（PR を開いた後）にしかなく、handoff.saved と pr.opened の時点で summary.md を確かめていないから
3. なぜその時点で確かめていないか: 本文は実装役の責任と見なされていて、受け渡しの処理が本文を変えうることが想定されていないから（推測）
4. なぜ実装役も気づけなかったか: PR を開いたのは Engine で（pr.opened は handoff.saved の後）、実装役は開いた後の本文を読み返す手番を持たないから

- 真因: 本文の形の確認がマージ前の inspect にしかない。handoff.saved と pr.opened のときに、保存した本文と実装役が書いた本文の食い違いや、見出しの欠けを機械で見る検査がない

### spec（確からしさ mid）

1. なぜ仮決めが 8 件も出たか: Issue に貼られた正本が 0.3.0 をもとに書かれていて、リポジトリにすでにある 0.4.0（date_field・slot_state）と食い違っていたから
2. なぜ食い違ったか: デザイナー役が正本を書いた後に 0.4.0（#455）が入り、Issue の正本を更新しないまま実装に渡ったから（実装役の解釈「書いた時期のずれ」。推測を含む）
3. なぜ渡る前に気づかなかったか: design_system.handed_off（11-05）から implement（11-06）までの間に、Issue の正本と specs/design/ の現在の版を突き合わせる段階がないから

- 真因: 入口の Issue の正本が古い版（0.3.0）をもとにしていて、リポジトリの今の版（0.4.0）と合っていなかった。差し戻しの直接の原因ではないが、版の番号と範囲を実装役が仮で決めることになった

### process（確からしさ low）

1. なぜ PR が大きくなったか: plan が steps ["design_system"] の 1 段だけで、正本・カタログ・両アプリのテーマと部品をまとめて 1 つの PR に入れたから（62 ファイル・128 ターン）
2. なぜ 1 段にしたか: planner がデザインの正本の変更として小さく見積もり、両アプリに広がる実装の量を数に入れなかったから（plan.outcome の judgment が undersized）
3. なぜそれが差し戻しに関わるか: 本文が長く、いくつもの段に分かれたので、受け渡しで一部が落ちたときの欠けが大きくなった（推測。直接の原因は受け渡し）

- 真因: 見積もりが小さすぎて（undersized、XL）、両アプリにまたがる変更が 1 つの PR に集まった。本文と検査の負担が増えたが、差し戻しへの寄与は間接的

## 真因

- 実装役が書いた PR 本文が、handoff（summary.md）へ移る途中で前半（概要〜動作確認と「## 補足」の見出し）を落とし、欠けた本文で PR が開かれた
- handoff.saved と pr.opened のときに、保存した本文と元の文の食い違いや、テンプレートの見出しの欠けを確かめる検査がない。気づけたのは PR を開いた後の inspect（rubric）だけだった
- 入口の Issue の正本が古い版（0.3.0）をもとにしていた。さらに見積もりが小さすぎて（undersized）大きな PR になり、仮決めと人の判断が増えた

   - 本文の欠けそのものは K-0025（取り出しが報告の一部しか拾わない）と K-0016（本文の先頭を確かめる段がない）が書く。この知見は、その食い違いを判定役が受け渡しの欠陥として分けられるかに絞った
