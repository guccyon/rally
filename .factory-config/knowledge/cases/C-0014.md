# C-0014: 文書だけの衝突（CHANGELOG.md と README.md）を tier-large の続きのジョブで解き、検査・判定・本文の直しまでやり直した束（process:conflict_fix:README.md、2026-10-30〜11-06）

- 出来事の種類: 工程の信号の束
- 分析の記録: 制御プレーンの events `case.analyzed`（id 775818）。事例型の分析役（Engine ADR 0023）
- 対象: 束 process:conflict_fix:README.md（窓 2026-10-30〜11-06）。例はチケット #293 の PR #301（衝突の解消のジョブ 347）
- 記録日: 2026-11-11
- 知見: K-0031（テーマ 6）、K-0032（テーマ 6）。学び 3（テーマ 4）は K-0001 の再現として扱い、新しい知見にしていない（K-0001 の evidence への追記は後の変更セットに回した）
- 材料: case.analyzed の分析だけ。handoff/ と session.txt の中身はなく、job 353 の本文の手直しが要った仕組み（続きのジョブの報告がどう本文に入ったか）は確かめられない。例の PR #301 の衝突（06:02:00）が CHANGELOG の断片方式（changelog.d/。このリポジトリでは 2026-11-03 から）の前か後かも材料にない

## 出来事

- 窓の中で、リポジトリの根の README.md が衝突した衝突の解消（conflict_fix）の束は 10 チケットに 15 件、費用は 21.61 USD だった。窓全体（1225 件・4006.17 USD）から見ると小さい束
- 同じ型の束 process:conflict_fix:CHANGELOG.md は 722 件・2920.35 USD で、窓の費用の約 73% を占める（C-0013 の窓とほぼ同じ数）
- 例のチケット #293（PR #301。deps は #292）:
  - 05:58:29 pr.opened → 05:59:52 pr.ci_passed → 06:00 検査（job 343）→ 06:01 判定（job 346）→ 06:02:00 pr.conflicted
  - 衝突の解消のジョブ 347（continue reason=conflict、tier-large の factory-worker:rust、1.03 USD）→ 06:05 検査をやり直し（job 351）→ 06:07 判定をやり直し（job 352）→ 本文の手直し（job 353、約 0.08 USD）→ マージ
  - 衝突したファイル（conflict.files）は CHANGELOG.md と README.md の 2 つだけで、コードの衝突ではない
  - 元の実装は 0.82 USD。1 回の衝突で、衝突の解消だけでそれを上回る費用が足された
  - 判定役の指摘によると、job 347 の報告が PR 本文の末尾にそのまま足され、「## 概要」などの見出しが 2 回ずつ出ていた。2 回目の概要には「コミットはしていません」とあり、PR 全体の説明と食い違って読めた
- 束のサンプルの費用 0.52 USD は job 347 の 1.03 USD のちょうど半分で、1 本のジョブの費用を衝突したファイルの数（2）で割り、CHANGELOG と README の両方の束に分けて数えているとみられる（分析役の推測。C-0011・C-0013 と同じ読みで、K-0028 が書く）
- job 759 と 761 の 2 つのサンプルが 2 秒差で出ており、1 回のマージで複数の PR が同時に衝突したと読める（分析役の読み。どのファイルで衝突したかは材料にない）
- 記録者の確認（2026-11-11 の main）:
  - README.md の「## 構成」の表で、`apps/admin-web/` と `apps/student-app/` の行は、それぞれ 1 行の表のセルに画面と API の名前を書き足していく作りになっている。機能を足すチケットはどれも同じ 1 行を書き換える
  - `.factory-config/continuation.yaml` の機械的な解消（`conflict.mechanical.paths`）は CHANGELOG.md と changelog.d/ だけで、ほかのファイルも衝突していればエージェント（tier-large）で解く線になっている（Engine はまだこのファイルを読まない）
  - Engine の orchestrator/dispatcher/serialize.py は、よく衝突するファイル（7 日に 3 回以上・解消の費用 5 USD 以上。CHANGELOG.md は除く）に触る見込みのタスクを、投入の時点で順番に並べる。マージの時点で並べる段は見当たらない

## 観点ごとのなぜなぜ

### process（確からしさ high）

1. なぜ衝突の解消のジョブが起きたか: PR #301 は CI・検査・判定を通ったあと、06:02:00 に pr.conflicted となり、job 347 が continue reason=conflict で投入されたから
2. なぜ衝突したか: 開いてから約 3.5 分の間に既定ブランチへほかの PR がマージされ、CHANGELOG.md と README.md の同じ場所が先に書き換わったから（conflict.files）
3. なぜ同じ場所が書き換わるか: 並列に流れるチケットがどれも、共有の追記型の文書（変更履歴や機能一覧）に書き足しているから。plan.outcome の layers に docs が入っていることと、判定の evidence にある「CHANGELOG にも画面は次の D78 で足すとある」がその跡
4. なぜ並列でも避けられないか: supervisor は deps（#292）でしか並べ方を決めておらず、共有ファイルに触ることを依存や衝突の見込みとして扱っていないから。job 759 と 761 が 2 秒差で出ていることから、1 回のマージで複数の PR が同時に衝突したと読める
5. なぜ費用が膨らむか: 中身の判断が要らない文書の衝突を tier-large（factory-worker:rust、1.03 USD）で解き、head が変わるので検査（job 351）と判定（job 352）もやり直しているから。1 回の衝突で、元の実装（0.82 USD）を上回る費用が足される

- 真因: 共有の追記型の文書をどのチケットも書き換える作りのまま並列に流していて、文書だけの衝突も、コードの衝突と同じ重い経路（tier-large の実装役、検査と判定のやり直し）で処理している

### communication（確からしさ mid）

1. なぜ本文の手直しのジョブ（job 353）が要ったか: 判定役の指摘によると、衝突の解消のジョブの報告が PR 本文の末尾にそのまま足され、「## 概要」などの見出しが 2 回ずつ出ていたから
2. なぜそのまま足されたか: continue のジョブの報告と PR 本文の扱いが分けられておらず、衝突の解消の記録も PR の説明と同じ置き場所に書かれたから（推測。session.txt と handoff が残っておらず、確かめられない）
3. なぜ紛らわしいか: 2 回目の概要には「コミットはしていません」とあり、PR 全体の説明と食い違って読めるから

- 真因: 衝突の解消のような付随作業の報告を、PR 本文（全体の説明）と分けて渡す決まりがない

## 真因

- 製品の規約で、どのチケットも共有の追記型の文書（CHANGELOG.md・README.md）の同じ場所に書き足すため、並列にマージすると必ずテキストの衝突が起きる
- 工程の並べ方が deps しか見ておらず、共有のホットスポットのファイルによる衝突の見込みを、並べ方にも衝突の解き方にも反映していない
- 文書だけの機械的な衝突も tier-large の実装役で解き、検査と判定をすべてやり直す一律の経路になっているため、1 回の衝突が元の実装と同じくらいの費用になる

## 学び

分析役は 3 つとも「効く範囲（scope）」を書かなかったので、事例の業務から決めた（1 はチケットの実装 dev.build とコードの PR、2 は実装 dev.build とマージの順番を決める supervisor）。どちらも根拠はこの束 1 つなので、確かさは hypothesis。

この事例の 3 つの学びは、どれも既存の知見と同じ型の出来事の再現を含む（1 は K-0002・K-0022・K-0028、2 は K-0013・K-0024・K-0029、3 は K-0001・K-0030）。新しい知見の主張は、既存の知見が書いていない点に絞った。3 は既存の K-0001 の主張そのものの再現なので、新しい知見にしていない。

1. テーマ 6（工程の進め方）→ K-0031: リポジトリの根の README.md の「## 構成」の表で、アプリの行の 1 つのセルに機能を書き足していく作りでは、同じアプリの行に触るチケットが同時に開いていると、先にマージされた PR のあとに残りの PR が衝突する。CHANGELOG.md だけの衝突を機械的に解く線が効いていれば、README.md が一緒に衝突することでジョブごとエージェント（tier-large）の経路に落ちるとみられるが、線は Engine にまだ配線されておらず仮定の話
   - 「共有の追記型のファイルを 1 つのまま残すと衝突する」は K-0022（apps/backend/README.md など）、CHANGELOG は K-0002、束の費用がファイルの数で割られることは K-0028 が書く。この知見は、根の README.md の表の 1 行という作りに絞った。CHANGELOG の機械的な解消の線（continuation.yaml）を README.md が外させることは、線が配線されていないので仮定として添えるだけにした
   - 分析役の提案のうち .gitattributes の merge=union は、1 行のセルを両方が書き換えた衝突では、行を両方残して表の行が 2 つになるとみられる（記録者の推測。試していない）。README.md には union より、行を分けるか生成にするほうが合う
   - 作用先の候補: improvement_ticket。提案（分析役の案）: CHANGELOG.md は changelog.d/<issue>.md の断片に分けてリリース時にまとめる。すぐ効く手当として .gitattributes に CHANGELOG.md merge=union を入れる。README.md の機能一覧などチケットごとに足す節は、断片から自動生成するか、チケットでは触らない規約にする。見込み: README の束 15 件・21.61 USD はおよそ 8〜9 割減る（残るのは README の本文を書き換える少数のチケット）。同じ手で CHANGELOG の束 722 件・2920 USD もほぼなくなる。job 347 のように両方のファイルで衝突していたジョブは、ジョブごとなくなる。繰り返しそう: はい
   - CHANGELOG の断片方式はこのリポジトリに 2026-11-03 から入っている（K-0002 の担保）。この事例の衝突がその前か後かは材料にない
2. テーマ 6（工程の進め方）→ K-0032: 同じファイルに触る PR が同時にマージを待っていると、1 回のマージで複数の PR が同時に衝突することがあるらしい（観察）
   - 投入の時点の並べ方は K-0024（Engine の serialize.py）、CHANGELOG の衝突を解く時機は K-0013、1 つの PR のマージの判断からマージまでの merge queue は K-0029 が書く。この知見は、すでに同時に開いている複数の PR が 1 回のマージで一斉に衝突したらしい（job 759 と 761 が 2 秒差）という観察に絞った。759 と 761 がどの PR のどのファイルで衝突したかは材料にないので、scope にファイルは書かない
   - 提案の向きには反例がある。同じ 1 行（README.md の表のセルなど）を書き換える PR は、マージを直列にして直前に既定ブランチを取り込んでも同じ行で衝突するので、衝突の解消の回数は減らない。減るのは、同じ PR がほかの PR のマージのたびに解き直される分（K-0013）だけ
   - 作用先の候補: role_line_engine。提案（分析役の案）: supervisor のマージの順番に「共有のホットスポットのファイルに触る PR は 1 本ずつ直列にマージする。マージの直前に自動で rebase する」ルールを足す（merge queue のような扱い）。対象は conflict_fix の束の上位のファイル。見込み: 断片化の前でも、同じ秒に起きるような重なった衝突（job 759 と 761 の型）は半分ほど減り、README の束では 15 件中 5〜7 件ほど減る見込み（推測）。繰り返しそう: はい
3. テーマ 4（役割間の言葉と伝達）→ 新しい知見にしない（K-0001 の再現）: 衝突の解消のような付随作業の報告を PR 本文に追記すると、本文の流れが壊れ、本文の手直しのジョブを呼ぶ
   - 出来事（衝突の解消の報告が本文の末尾に足されて見出しが重なり、本文の手直しを呼んだ）は K-0001 の主張そのものの再現。確かさは K-0001 のまま（hypothesis）据え置く
   - K-0001 の evidence に C-0014・PR #301・case.analyzed:775818 を足すのは、この変更セットではしない。K-0001 のファイルに触れると、ci_check・test の解決策 12 件に requires_check を書く必要がある（議決 D-0116・D-0141）。さらにその列は tools/knowledge-enforcement-check/test_check.py が固定で照らしているので、置き場の外のファイルも変えることになる。追記は、それらを直せる次の K-0001 の変更セットで行う
   - 分析役の提案の向き（報告は PR のコメントか handoff にだけ書き、本文は書き換えない）は、K-0030（本文をその時点の要約として書き直す）と K-0001 の担保（記録を「## 工場の記録」の下の ### に置く）に並ぶ 3 つめの向きになる。報告が実装役の書き方と Engine の組み込みのどちらで本文に入ったかも確かめていないので、委員会が向きを決めるまで知見にしない
   - 作用先の候補: role_line_engine。提案（分析役の案）: 実装役への指示に、continue のジョブ（reason=conflict）の報告は PR のコメントか handoff にだけ書き、PR 本文は書き換えない（必要なら本文の「工場の記録」に 1 行だけ足す）ことを足す。見込み: 衝突のあとに起きる body_fix のジョブ（job 353、約 0.08 USD）と、本文の構成を理由にした指摘がなくなる。繰り返しそう: はい

文書だけの衝突でも検査と判定をすべてやり直すこと（真因の 3 の後半）は K-0029 が、tier-large で解く費用は K-0010 が書くので、別の知見にしていない。束の費用がファイルの数で割られている読みは K-0028 と同じなので、知見にしていない。
