# C-0008: 見た目の仮決め 2 件で人の判断を約 6 時間 24 分待ち、その前後で同じ衝突の解消と本文の直しが繰り返された停止（PR #678）

- 出来事の種類: 停止
- 分析の記録: 制御プレーンの events `case.analyzed`（id 370961）。事例型の分析役（Engine ADR 0023）
- 対象: PR #678（Issue #670、デザインシステムの正本 0.2.0 とカタログ）
- 記録日: 2026-11-08
- 知見: K-0015（テーマ 6）、K-0016（テーマ 4）。既存の K-0002 に根拠を足した

## 出来事

PR #678 は、judge が仮決めを人に回したところで停止し、人の判断を約 6 時間 24 分（04:35〜10:59）待った。

- 仮決めは 4 件。judge はそのうち aesthetic の 2 件（catalog-layout・empty-state-catalog-copy。カタログの並びと、カタログに置く空の表示の文言。どちらも確信度 0.5）を、track_record を根拠に escalate した
- 判断した人の答えは「PR の案のまま受け入れ」で、この 2 件を人に回したことは結果として何も変えていない
- 停止に至るまでにも回り道が多かった
  - node_modules を丸ごとコミットした（435 ファイル）。GitHub の差分 API の上限 300 ファイルを超えたので検査が動かなかった。ルートの .gitignore に node_modules/ がなかった
  - その間に、CHANGELOG.md の衝突を機械的に解く（エージェントを使わない）ジョブが 13 回走った（3414〜3822）。PR が CHANGELOG.md を直接書き換えていて、既定ブランチが進むたびに衝突した
  - 続いて review_fix が 1 件ずつ 2 回（3852・3873）走った。3852 で node_modules の混入を直し、3873 で CHANGELOG.md の直接の書き換え（DOC-002）を直した
- judge の後には、PR 本文の並びの崩れ（process の指摘）を直す body_fix のループが 5 回あった（4117〜4144）。毎回同じ指摘が残り、直り切らなかった
  - 本文は「Closes #670」の直後に見出しのない箇条書きで始まり、## 概要 が後ろに来ていた
  - job 3324 の報告（summary.md）は「  - テストで次を確かめます。」から始まり、セッションで書いた ## 概要 と ## 対応内容 の頭が抜けていた。job 3873 の報告にも、## 概要 の前に余計な 1 文が付いていた
  - judge_enqueued の head_sha は 3324・3444 などの古い sha を行き来している

## 観点ごとのなぜなぜ

### spec（確からしさ mid）

1. なぜ人の判断待ちになったか: judge が aesthetic の仮決め 2 件（カタログの並びと、カタログに置く空の表示の文言）を自分で決めず、人に回したから
2. なぜ実装役はこの 2 件を確信度 0.5 の仮決めにしたか: Issue が手本として挙げた 1 版目のカタログ（claude.ai の artifact）が作業環境から見られず、カタログ用の文言も Issue や specs/ に決められていなかったから
3. なぜ見られない手本が入口に残ったか: Issue が外部の成果物を指すだけで、その中身（並び・要素）を specs/ やチケットに書き写していなかったから（推測）
4. なぜ書き写されていなかったか: 見た目の手本を見られる形で渡すという入口の決まりが見当たらないから（記録では確かめられない）

- 真因: 見た目の仮決めのよりどころになる手本（1 版目のカタログ）が作業環境から見られる形でチケットに入っておらず、カタログ用の文言の決まりもなかった

### communication（確からしさ mid）

1. なぜ judge の後に body_fix が 5 回も繰り返されたか: PR 本文が「Closes #670」の直後に見出しのない箇条書きで始まり、## 概要 が後ろに来るという process の指摘が、直した後も毎回残ったから
2. なぜ本文の頭が崩れていたか: job 3324 の報告（summary.md）が「  - テストで次を確かめます。」から始まり、セッションで書いた ## 概要 と ## 対応内容 の頭が抜けたまま本文に組み込まれたから。job 3873 の報告にも、## 概要 の前に余計な 1 文が付いている
3. なぜ body_fix で直り切らなかったか: body_fix（tier-small）が本文を書き換えても、次の judge ではまた同じ指摘が出ており、本文が元の報告から組み直されている可能性がある。judge_enqueued の head_sha も 3324・3444 などの古い sha を行き来している（推測）
4. なぜ同じ指摘が 5 回出ても止まらなかったか: body_fix の結果を判定役に返して、同じ指摘が繰り返されていると気づく仕組みが記録に見当たらないから（推測）

- 真因: 実装役の最終の文から PR 本文を組み立てる受け渡しで頭が欠けたり余計な文が混じったりし、body_fix と judge の間では「直したのに残る」という情報が戻っていなかった

### inspection（確からしさ high）

1. なぜ node_modules の混入が job 3852 まで直らなかったか: PR が 435 ファイルになり、GitHub の差分 API の上限 300 ファイルを超えて検査が動かなかったから
2. なぜ検査の前で止まらなかったか: 実装役が git status や diffstat でコミットの範囲を確かめないまま出したから。ルートの .gitignore に node_modules/ がないことにも気づいていなかった
3. なぜ CHANGELOG.md を直接書き換えたことが 3873 まで残ったか: job 3852 の実装役は規約の変化（changelog.d）に気づいたが、指摘 1 件だけを直す範囲なので見送り、検査がもう 1 周してから DOC-002 として拾われたから
4. なぜ最初の検査で両方を拾えなかったか: 差分が大きすぎて検査が中身を見られない状態だったから。変更ファイル数が上限を超えたら出す前に弾く仕組みもなかった

- 真因: 出す前に差分の範囲（ファイル数や、生成物・依存の混入）を確かめる機械の検査がなく、上限を超えて初めて検査が止まった

### process（確からしさ high）

1. なぜマージまで半日以上かかったか: 衝突を解くジョブ 13 回、review_fix 2 回、body_fix 5 回、人の判断待ち 6.4 時間が順に重なったから
2. なぜ衝突を 13 回も解き直したか: CHANGELOG.md に直接書いた行が既定ブランチの更新のたびに衝突し、エージェントを使わない機械的な解消で毎回両方の行を残すだけだったから
3. なぜ衝突の元を直さなかったか: 機械的な解消は、何回目か・なぜ同じファイルかを見て止める・知らせることをしないから
4. なぜ人の判断を 6.4 時間待ったか: attended モード（mode_basis default）で aesthetic の仮決めを人に回すことになっており、決めてよい範囲が Blueprint に定められていなかったから。人の答えは「PR の案のまま」で、待ちに見合う変更はなかった

- 真因: 同じ原因で同じことが繰り返されても（同じファイルの衝突、同じ本文の指摘）回数に上限や見直しの仕組みがなく、見た目の小さな仮決めも既定で人の判断を待つ設定になっていた

## 真因

- 見た目の小さな仮決め（デザインカタログの並びや見本の文言）を judge が自分で決めてよい範囲が Blueprint に定められておらず、手本も見られなかったため、結局そのまま受け入れられる案のために人を 6 時間以上待った
- 同じ原因で同じことが繰り返されても検知して止める仕組みがなかった（CHANGELOG の衝突 13 回、本文の指摘と body_fix 5 回）。そのため根本の直し（changelog.d への移動、本文の組み立ての修正）が後回しになった
- 出す前の機械の検査（差分のファイル数、node_modules などの混入、報告の見出しの形）がなく、問題が検査の上限や judge の段になって初めて見つかった

## 学び

1. テーマ 6（工程の進め方）→ K-0015: 衝突の元が PR の中に残っているのに、機械的な衝突の解消が同じ PR・同じファイルで繰り返されても上限に数えられず、原因の直しに切り替わらない
   - 学びの候補は「同じファイルの機械的な衝突の解消 13 回」と「同じ本文の指摘への body_fix 5 回」の 2 つの繰り返しを 1 つにまとめていた。仕組みが違う（前者は supervisor と機械的な解消、後者は judge と body_fix）ので、K-0015 は前者だけに絞った（1 件 1 主張）。scope も dev.build・CHANGELOG.md と changelog.d/・supervisor に狭めた（知見の委員会の差し戻しの理由）
   - body_fix の 5 回は知見にしない。C-0008 の communication のなぜなぜでは、本文が元の報告から組み直されている可能性と、judge_enqueued の head_sha が古い sha を行き来していることが挙がっている。これが原因なら回数の上限を入れても直らず、「上限や切り替えの段がないから繰り返した」という因果の反例になる。組み直しの有無を確かめてから別の知見として起こす。それまでは K-0009（body_fix の決まりが次に本文を書く役に渡らない）と K-0016（報告から本文を組み立てる受け渡しで頭が欠ける）の related として読む
   - K-0010 の担保の線（`.factory-config/continuation.yaml` の conflict）との関係: 線は 3 回の上限にエージェントを呼んだ回だけを数え、機械的に解いた回は数えない（2026-11-07 のオーナーの差し戻し、議決 D-0023 の dissent）。そのかわり、機械的な解消は K-0002 の検査（`tools/changelog-check/check.mjs`、mechanical.verify）に通ったときだけとし、通らなければエージェントの回として上限に数える。この PR は CHANGELOG.md を直接書き換えていたので、線どおりなら検査に落ちてエージェントの回になり、3 回で人の判断待ちに上がっていた見込み。線は Engine にまだ配線されていない（continuation.yaml の冒頭）
   - したがって、この 13 回は「段がない」より「段が未配線」と読む方が材料に合う。K-0015 はこの読みで、K-0010 の線のうち「機械的な解消を数えないなら、その前に衝突の元が PR に残っていないことを検査で確かめる」部分が要ることを、事例として示す知見にした。Engine が 13 回の機械的な解消のときに検査を呼んでいなかったことは材料で確かめていない（invalidate_when の 3 つ目）
   - 確かさは hypothesis（事例 1 件）
   - 作用先の候補: role_line_engine。提案（分析役の案）: Engine で、同じ PR の同じファイルの機械的な衝突解消が 3 回を超えたら、エージェントの review_fix に切り替えて原因を見させる（今回なら changelog.d への移動）。同じ指摘への body_fix が 2 回続いたら、ループを止めて指示役に知らせる（後半は上のとおり知見にしていない）。continuation.yaml の線を配線すれば前半の多くは満たされる見込み。繰り返しそう: はい
2. テーマ 4（役割間の言葉と伝達）→ K-0016: 実装役の報告から PR 本文を組み立てるときは、見出しの形を確かめないと本文が崩れる
   - 学びの候補は「本文の頭が欠ける・余計な文が混じる」と「直しても繰り返し指摘される（本文が古い報告から組み直される、head_sha が古い sha を行き来する）」の 2 つの主張を含んでいた。後者は推測で、body_fix の結果が次に本文を書く役に渡らない側は K-0009 と重なり、組み直しが原因なら回数の上限でも直らないので、K-0016 は前者に絞った（1 件 1 主張）。後者は組み直しの有無を確かめてから別の知見として起こす
   - C-0006（PR #821）でも、実装役が会話で書いた ## 概要 と ## 対応内容 が summary.md では抜けていた（C-0006 では抜けた場所が確かめられず知見にしていない）。同じ現象の 2 件目なので、C-0006 も根拠にした。ただし 2 件とも欠けた場所（実装役の書き出しか、Engine の組み立てか）は記録で確かめられていないので、確かさは hypothesis のまま
   - K-0005 は見出しの定義が分かれていること、K-0006 は直しを末尾への追記だけで済ませること、K-0001 は続きのジョブの見出しが重なること。K-0016 は、それらの前の「報告から本文を組み立てる受け渡しで頭が欠ける」に絞る
   - 作用先の候補: improvement_ticket。提案: summary.md から本文を組み立てる処理を調べ、先頭が「## 概要」で始まるかを確かめ、前に混じる文や頭が欠けた断片を検出する。あわせて、body_fix の後に本文が古い報告から組み直されていないか、judge_enqueued の head_sha が古い sha を指していないかを確かめる改善チケットを起こす。繰り返しそう: はい

提案（作用先への変更）はこの記録では実装しない。次の 2 つは分析役が学びの候補に挙げておらず、この記録では知見にしていない。

- spec の観点の真因（見た目の手本が作業環境から見られる形でチケットに入っていない）と、process の観点の後半（aesthetic の小さな仮決めを judge が決めてよい範囲が Blueprint にない）。人の答えが「PR の案のまま」だった事例は 1 件だけで、決めてよい範囲を広げてよいかは、ほかの事例（人が案を変えた例）と並べて見る必要がある
- inspection の観点の真因（出す前に差分のファイル数や node_modules などの混入を確かめる機械の検査がない）
