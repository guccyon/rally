# C-0007: CHANGELOG.md だけの衝突の解消が、窓の費用の約 74% を占めた束（process:conflict_fix:CHANGELOG.md、2026-10-27〜11-03）

- 出来事の種類: 工程の信号の束
- 分析の記録: 制御プレーンの events `case.analyzed`（id 370939）。事例型の分析役（Engine ADR 0023）
- 対象: 束 process:conflict_fix:CHANGELOG.md（窓 2026-10-27〜11-03）。例は Issue #288 の PR #290 と Issue #289 の PR #295
- 記録日: 2026-11-08
- 知見: K-0013（テーマ 6）、K-0014（テーマ 4）。既存の K-0001・K-0002 に根拠を足した
- 材料: case.json だけ。handoff/ はなく、session.txt にも会話の記録がないので、実装役が何を考えたかは確かめられない

## 出来事

窓（2026-10-27〜11-03）の中で、`CHANGELOG.md` の衝突を解く続きのジョブ（conflict_fix）の束が 722 件・109 チケット・2,920.35 ドルあった。

- 窓全体（1,200 件・3,965.07 ドル）に対して、件数で約 60%、費用で約 74% を占め、窓の中で一番大きい束。前の窓は 0 件・0 ドル
- 1 チケットあたり平均 6.6 回、1 回あたり平均約 4.0 ドル
- #288 の例: 実装ジョブ 305（2.78 ドル）が PR #290 を開いた約 1 分後に pr.conflicted（04:43:29）が出た。約 2 分後（04:43:43）に continue.enqueued(reason=conflict) が積まれた。続く衝突解消ジョブ 309 は tier-large で 3.10 ドル（total_tokens 約 107 万）かかり、実装より高くついた。衝突したのは `CHANGELOG.md` だけ（conflict.files。2026-11-03 の backfill）
- ジョブ 309 は PR 本文に「## 既定ブランチの取り込み…」の下に、元と同じレベルの見出し一式を追記した。judge の指摘を受けて body_fix（ジョブ 312）が直した
- #289 の PR #295 は、26 分のうちに 3 回（ジョブ 318・325・338。05:26・05:32・05:52）衝突を解き直した。並行で開いている PR が 1 つマージされるたびに、ほかの PR が同じファイルで衝突し直していると読める
- 衝突解消ジョブの samples の detail はすべて null。衝突したファイル（conflict.files）は 2026-11-03 に後から backfill で足されたもの

この窓はこのリポジトリが `changelog.d/` の断片方式（Engine ADR 0027、`changelog.d/README.md`）に移る前後にあたる。K-0002 の担保（断片方式と `tools/changelog-check/`）の at は 2026-11-03 で、この束の大部分はその前の PR と見られる（PR ごとのマージ日は材料にない）。

## 観点ごとのなぜなぜ

### process（確からしさ high）

1. なぜ CHANGELOG.md の衝突解消が窓の中で 722 回も起きたのか: 109 チケットの PR がそれぞれ CHANGELOG.md を直していて、並行で開いている PR が 1 つマージされるたびに、残りの PR が衝突し直すから（PR #295 は 05:26・05:32・05:52 と 3 回やり直している）
2. なぜマージのたびにやり直しになるのか: supervisor が pr.conflicted を見るとすぐに continue.enqueued(reason=conflict) を出し、その PR のマージ順が来る前に解消してしまうから（PR #290 では PR を開いて約 2 分後の 04:43:43 に積まれている）
3. なぜその場ですぐ解消する作りなのか: 衝突解消を、マージ直前にまとめて 1 回だけやるのではなく、衝突を見つけるたびに個別のジョブを起こす運用パラメータになっているから。並行で開ける PR の数も CHANGELOG の衝突を考えていない（推測）
4. なぜ 1 回あたり約 4 ドルもかかるのか: 追記の並びを直すだけの衝突でも、実装と同じ tier-large・factory-worker:rust で、PR の文脈を全部読み直すジョブとして走るから（309 は total_tokens 約 107 万で 3.10 ドル。実装の 305 は 2.78 ドル）
5. なぜ機械的に解けるものに LLM を使うのか: Engine に、衝突ファイルの種類（追記だけのファイルかどうか）で解き方や tier を分ける分岐がないから

- 真因: 衝突を見つけるたびに、マージ順を待たずに tier-large の LLM ジョブで解消する運用になっている。追記だけで済む CHANGELOG.md の衝突も、機械的に解かずに何度も高い費用で解き直している

### spec（確からしさ low）

1. なぜ 109 チケットのすべてが CHANGELOG.md を直したのか: 製品の規約か実装役への指示で、PR ごとに CHANGELOG.md へ追記することになっていると考えられるから（推測。規約の本文は材料にない）
2. なぜ追記が衝突になるのか: 1 つのファイルの同じ場所（未リリースの節の先頭など）に、各 PR が行を足す形だから（推測）
3. なぜ衝突しない形になっていないのか: 変更ごとの断片ファイルにする、.gitattributes で merge=union にする、といった並行開発向けの作りが、製品の規約に入っていないから（推測）

- 真因: 製品の規約（推測）が、並行で多くの PR が 1 つの CHANGELOG.md に追記する形になっていて、工場がたくさんの PR を同時に開く使い方と合っていない
- 記録者の注: 分析役は規約の本文を材料に持っていなかった。このリポジトリでは、CLAUDE.md と `changelog.d/README.md` が今は断片ファイル（`changelog.d/<Issue 番号>.md`）に書くよう決めていて、`CHANGELOG.md` を直接書き換えた PR は `tools/changelog-check/` で落とす（ワークフローへの配線は建設者が入れる。まだ入っていない）。分析役が挙げた第 2 段の提案（断片ファイル）はすでに入っている。.gitattributes はリポジトリにない

### communication（確からしさ mid）

1. なぜ束が窓の 7 割の費用に育つまで止まらなかったのか: 衝突解消ジョブが出た時点で、どのファイルが衝突したのかが記録されていなかったから（samples の detail はすべて null）
2. なぜ記録されていなかったのか: conflict.files は 2026-11-03 に backfill で後から足されたもので、continue.enqueued や handoff に衝突ファイルを載せる決まりがなかったから
3. なぜそれが問題なのか: 指示役（supervisor）も解消を担う実装役も、毎回「新しい衝突」として扱うだけで、「いつも同じ CHANGELOG.md」という型を役割の間で共有できなかったから
4. また、衝突解消ジョブ 309 は PR 本文に「## 既定ブランチの取り込み…」の下に元と同じレベルの見出し一式を追記した。どれが PR 全体の結論なのか分からなくなり、judge の指摘を受けて body_fix（ジョブ 312）が必要になった。衝突解消の報告をどう書くかの取り決めがないから（推測）

- 真因: 衝突解消ジョブを起こすときと、その結果を報告するときに、衝突ファイルと解消の中身を決まった形で渡す取り決めがない。そのため型が見えず、PR 本文も崩れた

### inspection（確からしさ mid）

1. なぜ検査で止まらなかったのか: CHANGELOG の衝突は品質の欠陥ではなく、CI（pr.ci_passed）もルーブリックも通るので、検査が止める対象ではないから
2. なぜそれでも検査の観点が当てはまるのか: 衝突解消ジョブが本文を崩したことは judge が見つけたが、その修正はマージ直前の body_fix に回り、ジョブがさらに 1 つ増えたから
3. なぜもっと前で止まらなかったのか: 衝突解消ジョブの出口に、「差分が衝突ファイルだけに収まっているか」「本文の見出しを増やしていないか」を機械で確かめる仕組みがないから（推測）

- 真因: 衝突解消ジョブの出口に、変更の範囲と本文の形を確かめる仕組みがない。崩れた本文の修正が judge と body_fix に回り、費用が増えた。ただし、束の費用の大部分は検査では減らせない

## 真因

- 製品の作り: 並行で開く多くの PR が 1 つの CHANGELOG.md に追記する規約（推測）になっていて、merge=union や変更ごとの断片ファイルのように衝突しない仕組みがない（このリポジトリでは断片ファイルにすでに移った。記録者の注を参照）
- 工程の運用: pr.conflicted を見ると、マージ順を待たずに tier-large の LLM ジョブで解消しに行く。ほかの PR がマージされるたびに解消し直し（1 チケット平均 6.6 回）、1 回約 4 ドルかかっている
- 観測と伝達: 衝突ファイルが記録されず（detail は null、conflict.files は事後 backfill）、同じファイルの衝突が繰り返している型を、束が窓の費用の約 74% に育つまで誰も見られなかった

## 学び

1. テーマ 6（工程の進め方）→ K-0002 に根拠を足した: 並行で多くの PR が追記する共有ファイルは、機械的に統合できる形にしておかないと、衝突解消が工程の費用の大半を食う
   - K-0002 の statement（並列の PR がすべて CHANGELOG.md の [Unreleased] の同じ場所に足すと、コードに関係のない衝突が起き、そのたびに重い続きのジョブが走る）と同じ因果なので、新しい知見にせず K-0002 の evidence に C-0007・PR #290・PR #295・case.analyzed:370939 を足した（下の「既存の知見の扱い」）。この事例は因果の大きさ（窓の費用の約 74%）を示す
   - 根拠の窓は K-0002 の担保（断片方式、at 2026-11-03）が入る前後で、担保が効かなかった反例ではない。担保のあとに CHANGELOG だけの衝突が減ったかは、この束では分からない（次の窓の同じ束の件数で確かめる）
   - C-0001（PR #546）・C-0005（PR #659）も同じ窓の前後の出来事で、この束の 109 チケットに含まれている見込みが高い。独立した事例とは数えず、確かさは hypothesis のまま
   - 作用先の候補: improvement_ticket。提案: 第 1 段として .gitattributes に「CHANGELOG.md merge=union」を入れる。第 2 段として変更ごとの断片ファイルに移し、リリース時にまとめる。見込みとして、この束の 722 件・2,920 ドルの 9 割以上が消える。第 2 段はこのリポジトリですでに入っている（changelog.d/）。繰り返しそう: はい
2. テーマ 6（工程の進め方）→ K-0013: 衝突解消は、見つけるたびではなく、マージの順番が来たときに 1 回だけやれば、やり直しの回数が減る
   - K-0010 は「衝突が起きたあとの積み直し方（上限なし・セッションの引き継ぎ・tier-large）」、K-0002 は「衝突が起きる原因（共有ファイルへの追記）」。K-0013 は、そのどちらにもない「衝突を解く時機（マージ順の前に解くと、ほかの PR のマージでまた衝突する）」に絞る
   - 同時に開く PR の数に上限を設ける案は、分析役の推測（なぜなぜの 3）からなので、statement には入れず作用先の候補にだけ残す
   - 根拠は CHANGELOG.md の 1 つの束（PR #290・#295）だけなので、statement は CHANGELOG.md に限った。ほかの共有ファイルには広げない
   - この工場にマージの順番（マージ待ちの列）があるかは材料で示しておらず、PR #295 の 3 回の解き直しがほかの PR のマージで起きたというのも分析役の読み（推測）なので、確かさは hypothesis のまま。K-0010 の担保（CHANGELOG.md だけの衝突を機械的に解く）が効けば、解く時機の痛さは小さくなる見込み（反対の向き）を statement の但し書きと invalidate_when に書いた
   - 作用先の候補: role_line_engine。提案: supervisor の運用パラメータを変え、pr.conflicted を受けても、その PR がマージ待ちの先頭に来るまで衝突解消を保留する。あわせて、同じ共有ファイルを触る PR の同時オープン数に上限を設ける。1 チケットあたり平均 6.6 回の解消が 1〜2 回になる見込み（推測を含む）。繰り返しそう: はい
3. テーマ 4（役割間の言葉と伝達）→ K-0014: 衝突解消ジョブは、衝突したファイルと解消の中身を決まった形で記録すべきである
   - 学びの候補は「衝突したファイルをその場で記録する」と「PR 本文は決まった 1 節にだけ追記する」の 2 つの主張を含んでいた。後者（ジョブ 309 が元と同じレベルの見出し一式を足し、body_fix 312 が要った）は K-0001 と同じ因果なので、K-0001 の根拠に足した。K-0014 は前者に絞る（1 件 1 主張）
   - K-0014 は「記録がないと、同じファイルの衝突の型が集計で見えない」に絞った。communication のなぜなぜの 3（指示役も解く役も毎回を新しい衝突として扱った）は、session.txt に会話の記録がなく役割が何を考えたかを確かめられないので、statement に入れていない
   - 「記録がないと手を打つのが遅れる」は確かめていない。型が見えた日と手を打った日の差は材料になく、CHANGELOG.md の衝突は記録がないままの窓の中で C-0001（記録日 2026-11-03）から K-0002 として見つかり、断片方式（at 2026-11-03）という手が打たれている。これは遅れの反例になりうるので、statement には但し書きとして書き、確かめ方（束ごとに見えた日と手を打った日を並べる）を invalidate_when に足した
   - 作用先の候補: role_line_engine。提案: continue.enqueued と handoff に conflict.files を backfill ではなくその場で載せる。実装役への指示に「衝突解消の報告は本文末尾の 1 節に 1〜3 行で書き、既存の見出しを増やさない」を足す。束の型が出たその日に見えるようになる。繰り返しそう: はい

提案（作用先への変更）はこの記録では実装しない。inspection の観点の真因（衝突解消ジョブの出口に、差分の範囲と本文の形を機械で確かめる仕組みがない）は、分析役が学びの候補に挙げておらず、本文の形は K-0001・K-0006 の担保（`tools/pr-body-check/`）が見る範囲と重なるため、この記録では知見にしていない。

- K-0002（CHANGELOG.md の同じ場所への追記で衝突が起き、重い続きのジョブが走る）: 直す（amend）。学び 1 と同じ因果なので evidence を足し、verified_at と review_by を更新した。related に K-0013 を足した。README の決まり（次にその知見を直す変更セットで配線と確認の状態を書く）に従い、2 つの解決策に wired: false・verified: false を書いた（断片方式は CLAUDE.md と changelog.d/README.md の決まりで、CI の配線先がない。changelog-check の検査はワークフローがまだない。どちらも CHANGELOG だけの衝突が減ったかをまだ数えていない）。statement・確かさは変えない

- K-0004（supervisor が差し戻しを adopt の件数で起こすと、直すもののない差し戻しが記録される）: そのまま（keep）。この事例の続きのジョブは衝突（reason=conflict）で起きていて、差し戻しの条件の話ではない
