## 観点ごとのなぜなぜ

### spec（確からしさ high）

1. なぜ ui-2 が人に回ったか: from・to が直近 30 日の中をさらに絞るのか、30 日の窓に置き換わるのかを judge が決められなかったから
2. なぜ決められなかったか: openapi.yaml の listLowRatedLessonReviews の説明は「両方を省けば今までどおり期間（30 日）の評価すべて」とだけ書いていて、指定したときの範囲を書いていなかったから
3. なぜ指定したときの範囲が書かれていなかったか: #723 で from・to を足したとき、省いたときの振る舞いだけを契約に書いて、30 日の窓との関係（交わりか置き換えか）を決めなかったからと見られる（推測。#723 の記録は材料にない）
4. なぜ食い違いが目立ったか: 期間の欄の上限（MAX_PERIOD_DAYS = 31 日）は一覧の窓（30 日）より長く、仕様の中で二つの数字が揃っていなかったから
5. あわせて: Issue #732 は「いまの絞り込み（競技・対応済みか・コーチ）」がもうある前提で書かれていたが、画面には「未対応だけ」しかなかった。Issue を書くときに、今の画面と照らし合わせていなかった

- 真因: 契約（#723 の listLowRatedLessonReviews）に、from・to と直近 30 日の窓の関係が書かれておらず、期間の上限 31 日とも揃っていなかった。Issue #732 も、画面にない絞り込みがある前提で書かれていた

### communication（確からしさ mid）

1. なぜ judge は ui-2 を自分で裁けなかったか: 実装役の「契約では from・to は直近 30 日の中をさらに絞るだけ」という解釈の根拠が、judge に渡った材料で確かめられなかったから
2. なぜ確かめられなかったか: 仮決めの根拠は画面のファイル（LowRatedReviewList.tsx・CancelledBookingList.tsx）を挙げているだけで、契約や backend の該当の文・振る舞いを引いていなかったから
3. なぜ引いていなかったか: 実装役は openapi.yaml を grep で読んだだけで、backend の実装やテストで振る舞いを確かめていなかったから（session.txt には admin-web 配下と specs の読み取りしかない）
4. なぜ振る舞いを確かめる必要を感じなかったか: 自分の読みを「契約では」と言い切って確信度 0.6 で残し、どちらとも読める点を judge や承認者への問いとして書かなかったから
5. あわせて: Issue の「ほかの期間の欄」「いまの絞り込み」という言葉も、どの画面・どの欄を指すかが決まっておらず、指示役と実装役で指すものがずれていた

- 真因: 実装役が契約の意味を自分で解釈して言い切り、確かめられる根拠（契約の文の引用、backend の振る舞い）を添えずに judge へ渡した。Issue の言葉も、指すもの（どの欄・どの画面）が決まっていなかった

### inspection（確からしさ mid）

1. なぜ検査（CI と rubric）は意味の曖昧さを止めなかったか: CI は 9 つの check がすべて通り、rubric の gate も defects が 0 件だったから
2. なぜ rubric は 0 件だったか: gate は mode=shadow で、見たルール（PR-001 や OV-00x など）に、契約の意味と画面の文言が合っているかを確かめる項目がないからと見られる（推測）
3. なぜ judge まで曖昧さが残ったか: 文言のテストは画面の振る舞い（表示・取り直し・422）だけを確かめていて、backend が返す範囲と表示が合うかはどのテストも見ていないから
4. なぜ judge は backend を確かめずに escalate したか: judge には実装役の報告（self_report）と差分だけが渡り、backend の振る舞いを確かめる手段や材料がなかったから（推測）
5. 結果として: 記録で確かめられる誤りはなく、人の判断で「文言は正しい」と決まった。検査で止め損ねた欠陥ではなく、確かめれば機械で決められた問いが人の待ちに回った

- 真因: 検査にも judge にも、画面の文言が API の実際の返す範囲と合っているかを確かめる手段がなく、確かめられるはずの問いが人の判断に回った

### process（確からしさ mid）

1. なぜマージまで 11 時間かかり、続きのジョブが要ったか: ui-2 の escalate で人の判断を待つ間（11:50〜22:43）に、main と衝突したから（pr.conflicted 17:20）
2. なぜ衝突したか: 待つ間に main 側で同じ headquarters.ts・LowRatedReviewList.tsx に student_id の絞り込みが入ったから
3. なぜ同じファイルの変更が並んだか: plan.serialized は #786 の終わりを待ってから投入したが、人の判断を待っている PR の間は、同じファイルに触る次の変更を止めていなかったから（student_id の変更がどのチケットかは材料にない。推測）
4. なぜ待ちが長かったか: stoppage.opened の waiting_for が人の判断だけで、cause も prevention も空のまま、期限や催促の記録がなかったから
5. あわせて: #723（契約）と #732（画面）に分けた時点で、from・to の意味を #723 で決めきることが前提になっていたが、その前提を確かめる工程がなかった（推測）

- 真因: escalate による人の待ちの間、ホットなファイルへの並行した変更を止めなかったため、待ちが衝突と続きのジョブ（job 4452）を生んだ。契約と画面を分けたチケットの間で、意味を決めきったかを確かめる工程もなかった

## 真因

- 契約（#723 の listLowRatedLessonReviews）に、from・to と直近 30 日の窓の関係（交わりか置き換えか）が定義されておらず、期間の上限 31 日とも揃っていなかった。Issue #732 も、今の画面にない絞り込み（競技・コーチ）がある前提で書かれていた
- 実装役が契約の意味を backend で確かめずに「契約では」と言い切り、確かめられる根拠を添えずに渡したため、judge が裁けず、確かめれば決められた問いが人に回った
- escalate による人の待ちの間も、衝突の多いファイルへの並行した変更が止まらず、待ちが衝突と続きのジョブを生んだ

## 学び

1. テーマ 4（役割間の言葉と伝達）→ K-0019: 契約や API の意味を解釈した仮決めに、backend の実装・テストで確かめた場所を添えず、契約の文がどちらにも読めるのに問いとして書かないと、judge は self_report だけで裁けず人に回す
   - communication の真因（確からしさ mid）を知見にした。根拠はこの 1 件だけなので、確かさは hypothesis
   - 知見の委員会の差し戻し（dissent）に沿って条件を狭めた。分析役の案は「契約の文の引用か backend で確かめた結果」だったが、C-0010 では契約の文そのものが 2 通りに読めたので、文を引くだけでは judge は裁けなかったと見られる（事例の中の反例）。statement の条件を「backend で確かめた場所を添える。契約の文がどちらにも読めて確かめられなければ問いとして書く」にし、文を引くだけでは足りないことも書いた
   - judge に backend を確かめる手段がない（inspection の真因の 4。推測）ことも同じ結果を生む別の仕組みなので、statement には入れず、invalidate_when に「judge が自分で backend を確かめられるようになった」を書いた
   - 作用先の候補: role_line_engine。提案（分析役の案）: 実装役への指示に、「契約・API の振る舞いの解釈を含む仮決めでは、openapi.yaml の該当の文をそのまま引き、backend の実装かテストで確かめた場所（ファイル名と関数名）を根拠に書く。確かめられなければ、確信度を下げて問いとして書く」を足す。繰り返しそう: はい
2. テーマ 6（工程の進め方）→ K-0020: escalate で人の判断を待つ PR が衝突の多いファイルに触っているのに、待つ間に同じファイルに触る次の変更の投入を止めないと、衝突と続きのジョブが生まれる
   - process の真因（確からしさ mid）を知見にした。根拠はこの 1 件の 1 回の衝突だけで、「待ちが長いほど増える」は分析役の見込み（推測）なので、statement には 1 回の衝突の事実と、同じファイルへの次の変更の投入を止める段がないことまでを書いた
   - 知見の委員会の差し戻し（dissent）に沿って、次の 3 点を直した
     - 1 件 1 主張に沿って、原因を「待つ間に同じファイルに触る次の変更の投入を止めない」だけに絞った。催促の期限がないこと（待ちを長くする）と、stoppage の cause・prevention が空なこと（衝突を生む仕組みが示されていない）は statement から外し、この記録の process の 4 に残すだけにした
     - 衝突した変更がどのチケットで、いつ投入されたかは材料にない。escalate（11:50）より前にすでに走っていたなら、待つ間の投入を止めても衝突は防げなかったという反例が残るので、statement と invalidate_when に書いた
     - 主張は supervisor が判断待ちの間に投入をどう扱うかなので、scope.work を dev.review.judge だけに狭めた（dev.build を外した）
   - 作用先の候補: monitoring_runbook。提案（分析役の案）: stoppage.opened（category=human）で、触っているファイルが plan.serialized の hot に当たるときは、承認者への催促の期限（たとえば 2 時間）を手順書に決める。待つ間は同じファイルに触る次のチケットの投入を止めるか、先にマージを済ませる。stoppage の cause・prevention を空のまま開かない。繰り返しそう: はい
3. テーマ 4（役割間の言葉と伝達）→ K-0021: Issue が今の画面を前提に書かれているのに、前提の欄・手本の画面をファイル名で挙げないと、範囲の仮決めが出る
   - spec の真因の後半と communication の 5 を知見にした。分析役の見込みは「繰り返しそう: いいえ」なので、確かさは hypothesis のまま下書きにした
   - 作用先の候補: improvement_ticket。提案（分析役の案）: Issue を起こす指示役の手順に「前提にしている既存の欄・手本の画面を、ファイル名で挙げる」を足す。あわせて、judge が勧めた「コーチの欄（coach_id）を低い評価の画面に足すか」を判断するチケットを起こし、承認者に回す。繰り返しそう: いいえ

提案（作用先への変更）はこの記録では実装しない。次は分析役が学びの候補に挙げておらず、この記録では知見にしていない。

- spec の真因の前半（#723 の契約が from・to と 30 日の窓の関係を決めておらず、上限 31 日とも揃っていなかった）。契約と画面を分けたチケットの間で意味を決めきったかを確かめる工程がない（process の 5）ことも含め、#723 の記録が材料になく推測に留まる
- inspection の真因（画面の文言が API の返す範囲と合っているかを確かめる検査がない）
