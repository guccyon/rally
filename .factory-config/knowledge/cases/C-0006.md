# C-0006: PR 本文の冒頭の見出しが抜け、本文を直した約 1 秒後に再検査なしでマージされた差し戻し（PR #821）

- 出来事の種類: 差し戻し
- 分析の記録: 制御プレーンの events `case.analyzed`（id 370935）。事例型の分析役（Engine ADR 0023）
- 対象: PR #821（Issue #809、お知らせの下書きの一覧を競技と最後に直した期間で絞る変更）
- 記録日: 2026-11-07
- 知見: K-0011（テーマ 4）、K-0012（テーマ 6）。既存の K-0005 に根拠を足した

## 出来事

PR #821 では、検査役（job 4297）の指摘 7 件のうち 6 件が採用された。

- 採用された 6 件のうち 5 件は実装役の仮決めの承認で、差し戻しにあたるのは PR 本文の構成の指摘（PR-002：「概要」「対応内容」の見出しがない）の 1 件だけだった
- コードの中身や利用者への害についての指摘はなかった
- この 1 件は body_fix（job 4299）が本文を機械的に直した（pr.body_amended 14:25:04）。その約 1 秒後（14:25:06）に supervisor.merged となった。supervisor.inspector_approved（14:25:02）は body_fix が終わる前に出ていた
- 会話の記録（session.txt）では、実装役は本文を「## 概要」の段落と「## 対応内容」の見出しで始めていた。ところが handoff の summary.md（PR 本文のもと）は箇条書きから始まり、冒頭の概要の段落と「## 対応内容」の見出しが抜けていた。どこで抜けたか（実装役の書き出しか、Engine の本文の組み立てか）は記録では確かめられない
- 検査役は rubric の「テンプレート」（概要・背景・問題・対応内容）を基準に指摘し、判定役は CLAUDE.md の PR の説明の見出し（必須は概要・対応内容）だけを基準にした。そのため判定役は OV-001（背景・問題を求める指摘）を reject し、PR-002 も背景・問題の部分は必須でないとして扱った。判定役の解釈には「根拠にした rubric の本文もない」とあった
- 実装役が知見に残した「何も絞らない一覧の応答が画面のキャプチャの fixtures になく 404 になり、下書きの欄が『読めなかった』表示のまま撮られる」は、直されず、チケットにもならないままマージされた

## 観点ごとのなぜなぜ

### communication（確からしさ mid）

1. なぜ背景・問題の扱いが分かれたのか: 検査役は rubric のテンプレートの見出し（概要・背景・問題・対応内容）を求め、判定役は CLAUDE.md の PR の説明の見出し（概要・対応内容）だけを基準にした（OV-001 は reject、PR-002 は概要・対応内容の分だけ adopt）
2. なぜ基準が分かれたのか: 同じ「PR 本文の正しい形」が、rubric のテンプレートと CLAUDE.md の 2 か所で別々に決まっていて、どちらが正なのかが揃っていない
3. なぜ判定役は rubric の側をとれなかったのか: 判定役の解釈に「根拠にした rubric の本文もない」とあり、判定役に指摘が引く rubric の本文が渡っていなかった
4. もう一つの伝達の切れ目: 実装役は会話で「## 概要」と「## 対応内容」を書いたが、handoff の summary.md では冒頭の概要の段落と「## 対応内容」の見出しが抜けていた
5. なぜ抜けたのか: 実装役の書き出しなのか、Engine の本文の組み立て（たとえば「## 概要」を別の用途に切り出す処理）なのかは、記録では確かめられない（推測）

- 真因: PR 本文の決まりが rubric のテンプレートと CLAUDE.md に分かれていて、判定役には rubric の本文が渡っていない。さらに、実装役が書いた本文と PR に載った本文の間で冒頭の見出しが失われた

### inspection（確からしさ mid）

1. なぜマージの直前まで止まらなかったのか: 本文の不足を見つけたのは PR を開いたあとの検査役（gate.evaluated 14:23:16）で、それより前には止まらなかった
2. なぜ前で止まらなかったのか: 実装役の工程に、PR を出す前に本文を規約の見出しと照らす機械的な確認がない
3. なぜ実装役が自分で気づかなかったのか: 実装役が書いた本文には見出しがあったので、実装役からは不足が見えなかった。PR に載った本文を出したあとに読み返す確認がない（推測を含む）
4. なぜ直したあとも確かめなかったのか: body_fix（job 4299）が本文を直した（14:25:04）約 1 秒後に supervisor.merged（14:25:06）となっていて、直した本文の再検査の記録がない
5. なぜ基準でも止まらなかったのか: L4 の rubric は shadow のままで、背景・問題を必須とする基準はまだ効いていない

- 真因: PR 本文の構成を機械的に確かめる段が PR を出す前になく、マージ前の検査役に頼っている。直したあとの本文も再検査せずにマージしている

### process（確からしさ mid）

1. なぜ直した結果を待たずにマージへ進んだのか: supervisor.inspector_approved（14:25:02）が body_fix の終わり（14:25:04）より前に出ていて、直した結果を待たずにマージへ進む流れになっている
2. なぜそうなるのか: 採用した指摘を「続きのジョブか差し戻しで直す」とし、直したことの確認をマージの条件に入れていない
3. なぜ実装役の知見が残ったのか: 実装役が知見に残した fixtures の不足（下書きの欄が 404 の表示のまま撮られる）は、直されず、チケットにもならずにマージされた
4. なぜ拾われなかったのか: 実装役の知見を改善のチケットに変える流れがなく、画面のキャプチャの CI は 404 の表示でも通ってしまう（推測）

- 真因: 採用した指摘を直したことの確認を待たずにマージしている。実装役の知見（fixtures の不足）をチケットにする流れもない

## 真因

- PR 本文の決まりが rubric のテンプレート（概要・背景・問題・対応内容）と CLAUDE.md の PR の説明の見出し（概要・対応内容）に分かれている。判定役には rubric の本文が渡っておらず、検査役と判定役で基準が揃っていない
- 実装役が書いた本文（概要と対応内容の見出しあり）と、handoff の summary.md として PR に載った本文（見出しなし）が食い違っている。PR を出す前に、実際に載る本文を規約と照らす確認がない（どこで抜けたかは記録で確かめられない）
- 採用した指摘を直したあと、再検査せずにすぐマージしている。実装役の知見（fixtures の不足で下書きの欄が 404 の表示のまま撮られる）も拾われずに残った

## 学び

1. テーマ 4（役割間の言葉と伝達）→ K-0005 に根拠を足した: 同じ成果物の正しい形を 2 か所で別々に決めると、検査役と判定役の裁きが分かれる
   - K-0005 の statement（見出しの定義が rubric と CLAUDE.md などで揃っていないと、rubric にだけある見出し〈背景・問題〉で指摘され、判定役が決まりの外として退け、判断が割れる）と同じ因果なので、新しい知見にせず K-0005 の evidence に C-0006・PR #821・case.analyzed:370935 を足した（下の「既存の知見の扱い」）
   - CLAUDE.md の側は `tools/pr-body-check/template.json` で 1 つの定義になったが（K-0006 の担保）、Engine の rubric（PR-002・OV-001）のテンプレートはまだ寄っていない。この事例はその残りで割れた例
   - 作用先の候補: term_alignment。提案: PR 本文の見出しの決まりを CLAUDE.md の PR の説明の見出しに一本化し、rubric の PR-002・OV-001 が言う「テンプレート」をその列挙に寄せる。背景・問題を求めるなら CLAUDE.md の側に足す。繰り返しそう: はい
2. テーマ 4（役割間の言葉と伝達）→ K-0011: 判定役が指摘の根拠の rubric の本文を持っていないと、根拠を確かめられず、rubric にだけある要求を決まりの外として退ける
   - この事例の判定役は 7 件中 6 件を adopt し、reject は OV-001（背景・問題を求める指摘）の 1 件だけだった。全体が reject に寄ったのではなく、rubric にだけある要求が退けられた
   - K-0005 が書く「判定役が同じ指摘を決まりの外として退ける」と同じ現象を、原因（判定役の入力に rubric の本文がない）の側から切り直したもの。C-0003（PR #396）にも「検査役から judge への伝達で rubric の本文が欠けていた」とあるので、C-0003 も根拠にした
   - K-0005 は「定義が 2 か所に分かれている」こと、K-0011 は「判定役に rubric の本文が渡らない」ことに絞る。定義を一本化することとは別に、判定役へ本文が渡ることが要る。この線引きは K-0011 の invalidate_when の 2 つ目（本文が渡っても同じように退けたら、原因は K-0005 の定義の分かれだけ）で保つ
   - 作用先の候補: role_line_engine。提案: judge のジョブの入力に、指摘が引く rubric_id（PR-002・OV-001 など）の本文を添える。繰り返しそう: はい
3. テーマ 6（工程の進め方）→ K-0012: 採用した PR 本文の指摘を body_fix が直したことを確かめずにマージすると、直していない本文か、再検査していない本文のままマージされうる
   - C-0005（PR #659）でも、本文直しの body_fix が終わる前にマージされていた（そのときは知見にしていない）。この事例で 2 件目なので、独立した知見にした
   - 2 件とも、直していたのは PR 本文だけ（既定ブランチのファイルではない）。直し漏れや直しの失敗が残った記録は 2 件のどちらにもないので、K-0012 は害が出たという因果ではなく、再検査のないマージになりうるという危険の形で書いた
   - 見えているのは body_fix（本文だけの直し）だけなので、scope は body_fix と supervisor に絞った。コードを直す続きのジョブへ広げるのは、その事例が出てから
   - 確かさは K-0011・K-0012 とも hypothesis のまま。上げる理由はまだない
   - 作用先の候補: role_line_engine。提案: body_fix などの続きのジョブが終わるまで supervisor.merged を待たせ、直した本文を再検査（少なくとも見出しの機械的な確認）してからマージする。繰り返しそう: はい

提案（作用先への変更）はこの記録では実装しない。次の 2 つは分析役が学びの候補に挙げておらず、この記録では知見にしていない。

- 実装役が書いた本文と handoff の summary.md の間で冒頭の見出しが抜けた件。抜けた場所（実装役か Engine の本文の組み立てか）が記録で確かめられないため
- 実装役の知見（fixtures の不足）を改善のチケットに変える流れがない件と、画面のキャプチャの CI が 404 の表示でも通る件（推測を含む）

## 既存の知見の扱い

- K-0001（続きのジョブの報告が PR 本文の末尾に足され、見出しの組が重なる）: そのまま（keep）。この事例に続きのジョブの追記はなく、見出しは重なったのではなく抜けていた
- K-0002（CHANGELOG.md の同じ場所への追記で衝突が起き、重い続きのジョブが走る）: そのまま（keep）。この事例に衝突は出ていない
- K-0003（judge の verdict「adopt」が 2 つの意味で使われる）: そのまま（keep）。採用 6 件のうち 5 件が仮決めの承認という内訳は分析で分けて読めており、数え方の混同は出ていない
- K-0004（supervisor が差し戻しを adopt の件数で起こすと、直すもののない差し戻しが記録される）: そのまま（keep）。差し戻しを起こす条件の知見で、この事例の「直したことを確かめる前にマージした」とは別の線。K-0004 の線（直っていない採用欠陥があれば起こす）と矛盾しない
- K-0005（PR 本文の見出しの定義が rubric・CLAUDE.md・報告の型で揃っていない）: 直す（amend）。学び 1 と同じ因果なので evidence を足し、verified_at と review_by を更新した。related に K-0011 を足した。statement・確かさは変えない
- K-0006（末尾への追記だけで直し、本文全体を組み直す持ち主がいないと崩れる）: そのまま（keep）。この事例の body_fix は本文を機械的に直しており、追記で崩れた形ではない。K-0006 の担保（本文だけの直しもマージ前の必須チェックにする想定の ci_check、未配線）は K-0012 の再検査の手段になりうるので、K-0012 の related に入れた
- K-0007（続きの job が head を確かめずに状態を書くと食い違う）: そのまま（keep）。この事例に続きの job はない
- K-0008（判断待ちの間の衝突の解消が判断の後に回る）: そのまま（keep）。この事例に人の判断待ちも衝突もない
- K-0009（採用済みの指摘と本文の決まりが、次に本文を書き足す役に渡らない）: そのまま（keep）。この事例では body_fix のあとに本文を書き足す役がなく、K-0009 の因果は出ていない
- K-0010（衝突のたびに上限なしで重い続きのジョブを積み直す）: そのまま（keep）。この事例に衝突は出ていない
