# C-0013: 大きい PR が長く開いたまま main に追い越され、衝突の解消と再検査・本文の直しが attempt 8 まで回り直した束（process:conflict_fix:apps/backend/crates/interface/src/lib.rs、2026-10-29〜11-05）

- 出来事の種類: 工程の信号の束
- 分析の記録: 制御プレーンの events `case.analyzed`（id 644601）。事例型の分析役（Engine ADR 0023）
- 対象: 束 process:conflict_fix:apps/backend/crates/interface/src/lib.rs（窓 2026-10-29〜11-05）。例はチケット #348 の PR #362（衝突の解消のジョブ 485〜575）
- 記録日: 2026-11-11
- 知見: K-0028（テーマ 6）、K-0029（テーマ 6）、K-0030（テーマ 4）
- 材料: case.analyzed の分析だけ。handoff/ と session.txt の中身はなく、lib.rs の中で何がぶつかったか（mod 宣言かルートの登録か）は分からない。ジョブ 485〜575 が CHANGELOG の断片方式（changelog.d/。このリポジトリでは 2026-11-03 から）の前か後かも材料にない

## 出来事

- 窓の中で、apps/backend/crates/interface/src/lib.rs が衝突した衝突の解消（conflict_fix）の束は 8 チケットに 10 件、費用は 24.43 USD だった。窓全体（1222 件・3983.52 USD）の約 0.6% で小さい束
- 同じ窓の CHANGELOG.md の束（722 件・2920.35 USD、全体の約 73%）、server/src/lib.rs の束（51.26 USD）、apps/backend/README.md の束（49.17 USD。C-0011）と同じ型の束の一部とみるのが妥当（分析役の読み）
- 例のチケット #348（PR #362）:
  - PR は 26 ファイル・1665 行の hard な PR で、長く開いていた。続きのジョブが衝突を理由に attempt 7・8 まで繰り返された
  - 衝突したファイル（conflict.files）を見ると、ジョブ 485〜575 の 8 回すべてに CHANGELOG.md が入っている。interface/src/lib.rs が入ったのは 519 と 556 の 2 回だけ
  - 衝突を解くたびに head が変わり、inspect・judge・body_fix が一から回り直した（1 周およそ 1 USD。inspect 555→577、judge 558→578）。差分のほとんどは CHANGELOG の追記の取り込みだけだった
  - merge_decided（14:09:33）の後、inspect の最中に main が進み、pr.conflicted（14:11:56）が出た
  - 556 は 9.40 USD、575 は 9.69 USD で、tier-large のモデルが長い会話を引き継いだまま衝突を解いていた
  - PR 本文には取り込みの記録（job 485・496・499・519・531・543・556）が回ごとに節として積み重なり、本文の先頭が見出しのない断片になった。検査役は毎回同じ本文の欠陥を指摘し、body_fix（559・579）が直しても次の衝突の解消でまた追記された
- 束の費用は、1 ジョブの費用を衝突したファイルの数で割った値とみられる（556 は 9.40 USD を約 10 ファイルで割って 0.94 USD。分析役の推測。C-0011 の README の束でも同じ読み）。lib.rs だけを直しても費用は大きくは減らない
- 記録者の補足: C-0011 は #348 を「2 回衝突した」と書いているが、この分析では同じチケットが attempt 7・8 まで続いている。数え方（窓の中の README の束に入った回か、チケットのすべての衝突か）の違いとみられるが、材料では確かめていない

## 観点ごとのなぜなぜ

### communication（確からしさ high）

1. なぜ衝突を解くたびに検査役は同じ欠陥を指摘したか: 実装役が続きのジョブごとに、PR 本文へ「## 概要」「## 対応内容」などの節を追記していき、本文の先頭が見出しのない断片になったから
2. なぜ追記の形になったか: 続きのジョブが前の本文を置き換えずに、job 485・496・499・519・531・543・556 の取り込みの記録を節として足していく作りだったから
3. なぜそれが直らなかったか: body_fix（559・579）が直しても、次の衝突の解消でまた追記されるため、同じ指摘と修正が繰り返されたから（推測を含む）

- 真因: 続きのジョブ（衝突の解消）が PR 本文を「その時点の要約」として書き直さず、回ごとの記録として追記していく。このため本文の欠陥の指摘と body_fix が、衝突のたびに繰り返された

### inspection（確からしさ mid）

1. なぜ衝突が分かったのはマージを決めた後だったか: merge_decided（14:09:33）の後、inspect の最中に main が進み、pr.conflicted（14:11:56）が出たから
2. なぜ inspect の最中に追い越されたか: マージできるかどうかの確認と検査が並行していて、検査が終わるまで main を止める仕組み（merge queue）がないから
3. なぜその分の費用が重なったか: 衝突を解くと head が変わり、inspect と judge が一から回り直す（555→577、558→578）から。ほとんどの中身は CHANGELOG の追記の取り込みだけだった

- 真因: 検査そのものは機能している。ただ、マージ前の検査と main の進みが並行しているので、検査が終わる前に追い越されて衝突の解消と再検査が回る。差分が衝突の解消だけでも、検査は一からやり直しになる

### process（確からしさ mid）

1. なぜ interface/src/lib.rs で衝突が 10 件起きたか: 8 チケットが並列に流れ、同じ lib.rs に手を入れたから（推測: mod 宣言かルート登録の追記）
2. なぜ同じファイルに手を入れるチケットが並列に流れたか: チケットを流す順番を決めるときに、触るファイルの重なり（hotspot）を見ていないから（推測）
3. なぜ 1 つの PR が attempt 8 まで衝突を繰り返したか: PR #362 は 26 ファイル・1665 行の hard な PR で長く開いていて、その間に CHANGELOG.md への追記を含む他の PR が次々とマージされたから
4. なぜ繰り返しが高くついたか: 衝突の解消に tier-large のモデルを使い、長い会話を引き継いだまま 1 回 9 USD 台をかけ、回数の上限も優先してマージする仕組みもなかったから
5. なぜ追記型の共有ファイルがこうなるのか: CHANGELOG.md や crate の lib.rs が、各チケットが同じ場所に 1 行足す作りで、git が自動でマージできないから

- 真因: 追記型の共有ファイル（CHANGELOG.md・crate の lib.rs・README）を、並列のチケットが同じ場所で取り合う作りになっている。そこに、大きい PR を長く開いたまま衝突の解消を無制限に、重いモデルで繰り返す運用が重なっている

## 真因

- 追記型の共有ファイル（CHANGELOG.md・crate の lib.rs・README）を、並列のチケットが同じ場所で取り合う作りになっており、git が自動でマージできない
- merge queue がなく、検査やマージ待ちの間に main に追い越されると、衝突の解消・inspect・judge・body_fix が上限なしで回り直す（PR #362 は attempt 8）
- 衝突の解消を tier-large のモデルが長い会話を引き継いだまま行い、PR 本文にも追記していく運用で、1 回が高く、本文の欠陥も毎回作り直される

## 学び

分析役は 3 つとも「効く範囲（scope）」を書かなかったので、事例の業務から決めた（1 はチケットの実装 dev.build とコード、2 は実装と検査 dev.build・dev.review.inspect とマージの順番を決める supervisor、3 は変更の説明 dev.describe と PR 本文）。どれも根拠はこの束 1 つなので、確かさは hypothesis。

この事例の 3 つの学びは、どれも既存の知見と同じ型の出来事の再現を含む（1 は K-0002・K-0022、2 は K-0010・K-0013・K-0024、3 は K-0001・K-0006・K-0009）。新しい知見の主張は、既存の知見が書いていない点に絞った。

1. テーマ 6（工程の進め方）→ K-0028: ファイルごとの衝突の束は、1 本のジョブの費用を衝突したファイルで割ったものなので、小さい束のファイル（interface/src/lib.rs）だけを直しても費用は減らない。どの回にも入っているファイル（CHANGELOG.md）を先に直す
   - 「共有ファイルを 1 つのファイルのまま残すと衝突する」は K-0022 がすでに書く（server/src/lib.rs など）。この事例は、束の中の 8 回すべてに CHANGELOG.md が入り、lib.rs は 2 回だけだったという材料を足す。K-0022 の「CHANGELOG だけ直してもほかが残ればジョブは残る」の裏側（lib.rs だけ直しても CHANGELOG が残ればジョブは残る）を、直す順番の主張として書いた
   - 作用先の候補: improvement_ticket。提案（分析役の案）: CHANGELOG.md を changelog の断片ファイルに変えるか、.gitattributes に merge=union を書く。interface/server の lib.rs は、mod 宣言やルート登録を 1 行ずつ並べて順番を揃えるか、モジュールごとの登録ファイルに分ける規約にする。見込み: CHANGELOG の束 722 件・2920 USD の大半（8〜9 割）が消え、lib.rs の束も 10 件のうち半分以上が減る（推測）。繰り返しそう: はい
   - CHANGELOG の断片方式はこのリポジトリに 2026-11-03 から入っている（K-0002 の担保）。この事例のジョブがその前か後かは材料にない
2. テーマ 6（工程の進め方）→ K-0029: マージを決めた後も検査と main の進みが並行していると、検査の最中に追い越されて衝突し、衝突の解消だけの差分でも inspect・judge が一から回り直す
   - 衝突の解消の回数の上限とセッションの引き継ぎは K-0010、CHANGELOG の衝突を解く時機は K-0013、よく衝突するファイルを共有するチケットの投入の並べ方は K-0024 が書く。この知見は、それらが書いていない「マージの判断から実際のマージまでの間に main を止めない（merge queue がない）」ことと「衝突の解消だけの差分でも再検査が全部やり直しになる」ことに絞った
   - 作用先の候補: role_line_engine。提案（分析役の案）: merge queue（検査に通った PR を 1 本ずつ rebase して CI を回し、マージする）を入れる。衝突の解消が 3 回を超えた PR は優先してマージする（同じファイルを触る他の PR のマージを一時止める）。同じ hotspot ファイルを触るチケットは並列にせず、順番に流す。見込み: attempt 7〜8 の繰り返しがなくなり、lib.rs の束 10 件は 3 件前後になる（推測）。繰り返しそう: はい
3. テーマ 4（役割間の言葉と伝達）→ K-0030: 続きのジョブが PR 本文を「その時点の要約」として書き直さずに回ごとの取り込みの記録を足していくと、body_fix が直しても次の衝突の解消で崩れ直す
   - 本文に同じ見出しの組が重なることは K-0001、追記だけで直して組み直す持ち主がいないことは K-0006、body_fix の決まりが次の書き手に渡らないことは K-0009 が書く。この事例は 8 回の衝突の解消でその型が再現した材料で、この知見の主張は「取り込みの記録は本文に置かず、本文はその時点の要約として書き直す」という直し方の向きに絞った
   - 作用先の候補: role_line_engine。提案（分析役の案）: 続きのジョブへの指示を変え、PR 本文は追記せず、その時点の「概要・対応内容・動作確認」として書き直させ、取り込みの記録は handoff か PR コメントに残させる。見込み: 衝突の解消 1 回ごとに出ていた本文の欠陥の指摘と body_fix（1 回 0.1〜0.15 USD、指摘を含む judge で 0.44 USD）がなくなる。繰り返しそう: はい
   - K-0001 の担保（「## 工場の記録」の下の ### に続きのジョブの記録を置かせる関所）は、記録を本文の中に残す向きで、この知見の向き（本文の外に出す）とは違う。どちらにするかは委員会が決める

tier-large で長い会話を引き継いだまま解く費用（真因の 3 の前半）は、分析役が学びの候補に挙げておらず、既存の K-0010 の主張と同じなので知見にしていない。
