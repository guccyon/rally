# C-0013: PR 本文の前半が受け渡しで落ち、採用した検査の指摘を直す前に auto でマージした差し戻し（PR #982、Issue #979）

- 出来事の種類: 差し戻し
- 分析の記録: 制御プレーンの events `case.analyzed`（id 644507）。事例型の分析役（Engine ADR 0023）
- 対象: PR #982（Issue #979: デザインシステム 0.4.0 で日付の欄とスロットの状態の色を足す）
- 記録日: 2026-11-11
- 知見: K-0027（テーマ 4）、K-0026（テーマ 6）
- 材料: case.analyzed の分析と、2026-11-11 の手元の Engine（34a53af）の orchestrator/worker/entrypoint.sh・orchestrator/dispatcher/supervisor.py。ジョブが動いた時点の Engine の版、本文を取り出す処理の記録、design_system ジョブ 4938 の入力は材料にない

## 出来事

- PR #982 は CI を通り、判定役（judge）が検査の指摘 8 件をすべて採用したうえで 14:47:58 にマージされた
- 採用した指摘のうち 3 件（inspection）は「続きのジョブか差し戻しで直す」扱いで、マージ後に直す宿題として残った。これが今回の差し戻しにあたる
- 指摘は 2 つの系統に分かれる
  - (1) PR 本文の前半（## 概要 と ## 対応内容 の前半）が抜けていた。実装役の会話の記録（session.txt）では、最後の文は見出しのそろった本文になっている。一方 handoff の summary.md は「  - カタログにスロットの状態の見本を足した」という箇条書きの途中から始まっている
  - (2) admin-web のカタログ（catalog.tsx）が、既存のスロットの状態のラベルと期間の上限の定数を使わずに同じ値を手で書き直しており、期間の確かめ（2 つの関数）も並んでいる。実装役はどちらの既存の定義のファイルも読んでいた
- rubric のゲートは shadow で動いており、マージの判断（supervisor.merge_decided、code_change=auto）は検査の前の 14:44:39 に出ていた。マージは inspector_approved から 4 秒後
- admin-web のキャプチャで期間の空の画面ほか 4 画面が撮れず（failed）、カタログの画像も古い版のままだったが、どちらもマージを止める条件になっていなかった
- PR は 18 ファイル・仮決め 5 件で、正本の改定（specs/design）と 2 つのアプリ（admin-web・student-app）への反映を 1 つのチケットで扱っていた

## 観点ごとのなぜなぜ

### spec（確からしさ mid）

1. なぜ期間の確かめが 2 つ並び、11 の部品の置き換えが残ったか: 実装役が仮決め（scope date-field-replace）で、画面の置き換えを別のタスクに回したから
2. なぜ仮決めが要ったか: Issue の「画面の作り替えは別のタスク」と、同じ Issue に載っていた governance.yaml の 0.4.0 の migration（11 の部品の置き換えと公開の欄の状態の表示の置き換え）が食い違っていたから
3. なぜ食い違いのまま渡ったか: design_system ジョブ 4938 が正本の差分（components・governance・tokens）を渡したが、この Issue でどこまでやるかを migration と突き合わせて決めていなかったから（推測）
4. なぜ同じ migration なのに判断が分かれたか（日付の欄は先送り、状態の表示はこの PR）: 入口に「migration のうちどれをこのチケットでやるか」の線引きがなく、実装役が 1 項目ずつ決めたから

- 真因: Issue 本文の範囲の指示と、同じ Issue に載せた正本の migration の列挙が食い違っており、どの移行をこのチケットでやるかが決まっていなかった

### communication（確からしさ mid）

1. なぜ検査役は PR 本文に ## 概要・## 背景 がないと指摘したか: 検査役に渡った本文が Closes #979 の直後から、student-app の項の途中の箇条書きで始まっていたから
2. なぜ本文が途中から始まっていたか: handoff の summary.md も同じ所から始まっている。実装役の最後の文には ## 概要 から書かれていたので、本文を受け渡すときに前半が落ちた
3. なぜ前半が落ちたか: 分析役は、最後の文が複数のテキストの塊に分かれ、取り出す処理が後ろの塊だけを拾ったと読んだ（推測。取り出す処理の記録はない）
   - 記録者の補足: 2026-11-11 の手元の Engine（34a53af）の orchestrator/worker/entrypoint.sh は、summary.md の元（SUMMARY）を `jq -r '.output' | tail -80` で作っており、最後の文が 80 行を超えると頭が落ちる。仮決め 5 件（1 件 7 行ほど）を含む本文は 80 行を超えやすい。ジョブが動いた時点の Engine が同じだったかは確かめていないので、分析役の読みと並ぶもう 1 つの候補として残す
4. なぜ誰も気づかなかったか: 実装役は PR に載った本文を見直しておらず、Engine にも、本文が実装役の書いた見出しの数とそろっているかを確かめる段がないから（K-0016 の関所はまだ配線されていない）
5. あわせて: judge の interpretation に「OV-001 の本文は rubric に渡されていない」とあり、検査の基準の文も判定役に渡っていなかった（K-0011 と同じ型）

- 真因: 実装役が書いた PR 本文が、handoff から PR に渡る間に前半を失った。その欠けを確かめる段がなく、検査役と判定役は欠けた本文を前提に裁いた

### inspection（確からしさ high）

1. なぜ二重の定義（ラベル、期間の上限、2 つの期間の確かめ）を持ったままマージされたか: 検査役は OV-005 として見つけたが、rubric のゲートが shadow なので止める力がなかったから
2. なぜ見つけたのに止まらなかったか: judge が「保守性だけの問題」として採用し、supervisor が「採用した指摘は続きのジョブか差し戻しで直す」としてそのままマージしたから
3. なぜマージがそれほど速く進んだか: supervisor.merge_decided（code_change=auto）が検査の前の 14:44:39 に出ており、検査と裁きは、本文の直し（body_fix）のほかはマージを止める条件になっていないから
   - 記録者の補足: 手元の Engine の supervisor.py の merge_step は、PR が clean になった時点で変更のファイルの分類（表）から merge_decided を出しており、検査の結果はその入力にない
4. なぜ実装役の段で防げなかったか: 実装役は既存の定義のファイルを読んでいたのに、新しい定数と手書きのラベルを作った。既存の定義を使い回しているかを lint やテストで確かめる仕組みがないから
5. あわせて: admin-web のキャプチャで 4 画面が撮れず、カタログの画像も古い版のままだった。どちらもマージを止める条件になっていなかった

- 真因: rubric のゲートが shadow で、採用した should の指摘はマージ後に回す決まりになっていた。そのうえ既存の定義の二重持ちを機械で検出する仕組みもなく、検査で見つけても止まらなかった

### process（確からしさ mid）

1. なぜ指摘が差し戻し（マージ後の宿題）になったか: 直すジョブを挟まずに、inspector_approved から 4 秒でマージしたから
2. なぜ直すジョブを挟まなかったか: 工程で自動に直すのは本文（body_fix）だけで、コードの should の指摘は続きのジョブに回す流れだから
3. なぜ PR が大きく、判断の分かれ目が多かったか: 正本の改定（specs/design）と 2 つのアプリへの反映が 1 つのチケット（18 ファイル、仮決め 5 件）にまとまっていたから（K-0018 と同じ型）
4. なぜ実装役はローカルで確かめきれなかったか: 作業の環境に Flutter と Chromium の依存がなく、student-app のテストとキャプチャを CI 任せにしたから

- 真因: 正本の改定と、それを使う側の変更を 1 つのチケットで扱った。加えて、採用した指摘を直す前に auto でマージする流れだったため、宿題が後に残った

## 真因

- PR 本文を handoff から PR に渡すときに前半が落ち、それを確かめる段がなかった（伝達。取り出す処理の細部は推測。手元の Engine の `tail -80` がもう 1 つの候補）
- rubric のゲートが shadow で、採用した should の指摘は直す前に auto でマージされる。既存の定義の二重持ちを機械で見つける検査もない（検査と工程）
- Issue の範囲の指示と、同じ Issue に載せた正本の migration が食い違ったまま渡り、移行の線引きを実装役が 1 項目ずつ決めた（仕様）

## 学び

分析役は 2 つとも「効く範囲（scope）」を書かなかったので、事例の業務から決めた（1 は変更の説明を書く dev.describe と PR 本文、2 は検査と裁き dev.review とマージを決める supervisor）。どちらも根拠はこの 1 件なので、確かさは hypothesis。

1. テーマ 4（役割間の言葉と伝達）→ K-0027: 実装役が書いた PR 本文は途中の受け渡しで欠けることがあるので、PR に載った本文が実装役の書いたものと一致しているかを確かめる必要がある
   - 既存の K-0016（本文の頭の欠けを確かめる段がない）と同じ出来事の型。K-0016 が「どこで欠けたか（実装役の書き出しか Engine の組み立てか）は確かめられていない」としていた点に、この事例は実装役の会話の記録で「実装役は頭から書いていた」という材料を足す。そのため K-0027 の主張は、欠ける場所が実装役の報告から summary.md を作る取り出しの側にあることと、元の文と照らす確かめが要ることに絞った
   - 作用先の候補: role_line_engine。提案（分析役の案）: handoff の summary.md を作るとき、実装役の最後の文のテキストの塊をすべてつなぐ。PR を開いた後は、本文の先頭の見出し（## 概要）と見出しの数が元の文とそろっているかを Engine が確かめ、ずれたら body_fix の前に元の文から書き直す。繰り返しそう: はい
2. テーマ 6（工程の進め方）→ K-0026: 採用した指摘を「続きのジョブか差し戻しで直す」としてすぐマージすると、直す作業が後に残る
   - inspection と process の真因を知見にした。本文の指摘について同じ型を書いた既存の K-0012（body_fix の終わりを待たずに承認する）を、コードの指摘に広げた別の主張として書いた
   - 作用先の候補: role_line_engine。提案（分析役の案）: merge_decided を検査と裁きの後に出す。採用した inspection の指摘のうち機械的に直せるもの（judge が「機械的に直せる」と書いたもの）は、本文に限らずコードも fix ジョブで直してからマージする。繰り返しそう: はい

spec の真因（Issue の範囲と正本の migration の食い違い）と、process の 3（正本の改定と使う側を 1 チケットにまとめた。K-0018 と同じ型）は、分析役が学びの候補に挙げなかったので知見にしていない。

提案（作用先への変更）はこの変更セットでは実装しない。
