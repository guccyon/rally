# C-0011: 共有ファイル server/src/lib.rs を触る並列のチケットが、依存なしで投入されて衝突し、続きのジョブが 15 件走った束（束 process:conflict_fix:apps/backend/crates/server/src/lib.rs）

- 出来事の種類: 工程の信号の束
- 分析の記録: 制御プレーンの events `case.analyzed`（id 523039）。事例型の分析役（Engine ADR 0023）
- 対象: 束 process:conflict_fix:apps/backend/crates/server/src/lib.rs（窓 10/28〜11/04）。例のチケットは #336（PR #345）
- 記録日: 2026-11-11
- 知見: K-0022（テーマ 6）、K-0023（テーマ 6）、K-0024（テーマ 6）、K-0025（テーマ 4）
- 時期: 窓（10/28〜11/04）は K-0010 の設定（2026-11-05）と K-0014 の担保（2026-11-08）が入る前なので、ジョブ 433 が tier-large だったことと continue.enqueued に衝突ファイルがなかったことは、担保の前の記録である
- 材料: case.analyzed の分析だけ。handoff/ はなく、session.txt にも会話の記録がないので、実装役の判断は確かめられない。lib.rs の衝突の中身（ルートの登録）はファイル名と contract_diff からの推測

## 出来事

- 束は窓の中で 9 チケット・15 件・51.26 ドル。窓全体（1210 件・3947.18 ドル）の約 1.3% で、前の窓は 0 件だった
- 例のチケット #336 の流れ
  - 実装ジョブ 429 は依存なし（supervisor.enqueued の deps が []）で 09:10 に始まり、tier-large で 13 分、3.30 ドルかかった
  - その 13 分の間に main が 7febe8646609 から 05ad53a07f89 へ進み、PR #345 は開いた直後（09:23:42）に衝突した
  - 続きのジョブ 433（reason: conflict）も tier-large のまま走り、3.88 ドルで解消した。解消のあと、CI も検査も通ってマージされた
  - 衝突したファイルは 4 つ（CHANGELOG.md・apps/backend/README.md・server/src/lib.rs・student-app の openapi.yaml）
- 束の 1 件の費用 0.97 ドルは、ジョブ 433 の 3.88 ドルを 4 ファイルで割った額に一致する。1 回の衝突解消ジョブが、ファイルごとの束に分けて数えられている
- 同じ日に #336・#340・#348・#352・#378 などが並列に走り、どれも新しいエンドポイントを足すために lib.rs の同じ集約箇所を書き換えて、同じ型の衝突がくり返した（「ルートの登録」という中身は推測）

## 観点ごとのなぜなぜ

### process（確からしさ high）

1. なぜ lib.rs の衝突解消が 9 チケットで 15 回起きたか: 同じ窓で、lib.rs に手を入れるチケットが依存なしで並列に走り、先にマージされたものが後の PR の土台を古くしたから
2. なぜ並列に走ったか: supervisor.enqueued の deps が [] で、同じファイル（共有点）を触るチケット同士を順に並べたり、1 本にまとめたりする仕組みがないから
3. なぜ PR を開いた直後に衝突が見つかったか: 実装ジョブ 429 が 13 分走る間に main が進み、push の前に最新の main に追従する手順がないから
4. なぜ衝突のたびに費用が大きいか: 続きのジョブ 433 は tier-large で始まり、3.88 ドルかかった。最初の実装の 3.30 ドルより高い
5. なぜ衝突の大きさに合わせてモデルを選ばないか: 続きのジョブの model_tier が続きの理由（conflict か review_fix か）で変わらず、実装と同じ設定を引き継いでいるから（運用設定そのものは記録になく推測）

- 真因: 共有ファイルを触るチケットを依存なしで並列に投入し、push の前に main に追従する手順もない。衝突解消を実装と同じ tier-large でやり直すので、件数も 1 件あたりの費用も膨らむ

### spec（確からしさ mid）

1. なぜ各チケットが同じ lib.rs を書き換える必要があったか: エンドポイントやモジュールの登録が server/src/lib.rs の 1 か所に集まっているから（ファイル名・contract_diff: true・new_files 12 からの推測）
2. なぜ集約点が 1 か所のままか: 機能ごとに登録を分ける規約（ルートを機能モジュールの側で組み立て、lib.rs は merge を 1 行足すだけにする、など）が specs/ や規約にないから（推測。規約の資料は材料にない）
3. なぜチケットにそれが書かれていないか: チケットに「触る共有ファイル」の欄がなく、並べ方の判断に使えないから（推測）

- 真因: server/src/lib.rs が全機能の登録をまとめる共有点になっていて、機能ごとに分けて登録する規約がない（推測）

### communication（確からしさ mid）

1. なぜ衝突解消のジョブが毎回、大きなモデルで全体を読み直すか: continue.enqueued に渡る情報が branch・reason: conflict・pr_number だけで、どのファイルがどう衝突したかを渡していないから
2. なぜ衝突したファイルを渡せないか: 制御プレーンが衝突ファイルを当時に記録しておらず、conflict.files は 2026-11-03 に backfill で後から足されたものだから
3. なぜそれが問題か: 指示役（supervisor）が衝突の範囲を知らないので、小さなモデルで済む機械的な解消かどうかを判断できないから

- 真因: 指示役から実装役への続きの指示に衝突ファイルの一覧と種類が含まれていない。そのため衝突の大きさに合った対応を選べない

## 真因

- 製品の作り: server/src/lib.rs（と CHANGELOG.md・openapi.yaml などの集約ファイル）が全機能の登録を 1 か所に集めている。並列のチケットが同じ行を書き換えて衝突する（lib.rs の中身は推測）
- 並べ方と投入: 共有ファイルを触るチケットを依存なし（deps: []）で並列に投入し、push の前に最新の main に追従しない。実装中に main が進むと、PR を開いた瞬間に衝突する
- 運用パラメータと伝達: 衝突解消の続きのジョブに衝突ファイルの情報を渡さず、実装と同じ tier-large で走らせる。1 回の解消が 3.88 ドルと、元の実装（3.30 ドル）より高くつく

## 学び

1. テーマ 6（工程の進め方）→ K-0022: 衝突解消を実装と同じ tier-large で走らせると、衝突 1 回の費用が元の実装の費用を上回る
