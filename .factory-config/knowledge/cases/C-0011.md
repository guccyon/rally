# C-0011: 並列のチケットが同じ共有ファイルに追記し合い、開いた直後の PR の衝突を tier-large の続きのジョブで解いた束（process:conflict_fix:apps/backend/README.md、2026-10-29〜11-05）

- 出来事の種類: 工程の信号の束
- 分析の記録: 制御プレーンの events `case.analyzed`（id 644407）。事例型の分析役（Engine ADR 0023）
- 対象: 束 process:conflict_fix:apps/backend/README.md（窓 2026-10-29〜11-05）。例はチケット #336 の PR #345（実装の job 429、衝突の解消の job 433）
- 記録日: 2026-11-11
- 知見: K-0022（テーマ 6）、K-0023（テーマ 6）、K-0024（テーマ 6）
- 材料: case.analyzed の分析だけ。例のチケット以外の 10 チケットの流れ、窓の中で断片方式（changelog.d/）と投入の並べ方（plan.serialized）がいつから効いていたか、リポジトリの設定（.gitattributes など）は材料で確かめていない

## 出来事

- 窓の中で、apps/backend/README.md が衝突した衝突の解消（conflict_fix）の束は 11 チケットに 17 件、費用は 49.17 USD だった。前の窓では 0 件で、新しく出た型
- 例のチケット #336:
  - 実装の job 429 は product_sha 7febe8646609 から始まり、13 分後（09:23:38）に PR #345 を開いた（pr.opened）
  - 4 秒後の 09:23:42 に continue.enqueued(reason=conflict) が出た。実装の間に main が 05ad53a07f89 に進み、PR は開いた時点で衝突していた（pr.conflicted は 09:24:35）
  - 衝突したファイル（conflict.files）は CHANGELOG.md・apps/backend/README.md・server/src/lib.rs・student-app/openapi.yaml の 4 つ
  - 衝突の解消の job 433 は tier-large（opus）で 3.88 USD かかり、実装の job 429（3.30 USD）より高かった
- README の束の 1 件の費用 0.97 は 3.88 を 4 ファイルで割った値と同じで、束の費用は、ジョブの費用を衝突したファイルの数で均等に割ったものと見られる（分析役の読み）
- 窓の conflict_fix の束 15 本の費用は、合計 3,983 USD のうち約 3,800 USD。CHANGELOG の束だけで 2,920 USD（722 件）、server/src/lib.rs の束は 15 件・51 USD
- 同じチケットで衝突が繰り返した例もある（#348 は 2 回衝突した）
- 仕様や役割の間の伝達に問題があったことを示す記録はない

## 観点ごとのなぜなぜ

### process（確からしさ mid）

1. なぜ PR #345 に衝突の解消のジョブが走ったか: PR が開いた時点で main と衝突していたから（pr.opened 09:23:38、continue.enqueued reason=conflict 09:23:42）
2. なぜ開いた直後に衝突していたか: job 429 が実装していた 13 分の間に、ほかのチケットが main にマージされ、同じファイルに触っていたから（product_sha が 7febe8646609 から 05ad53a07f89 に進み、conflict.files には README を含む 4 つの共有ファイルが並ぶ）
3. なぜ複数のチケットが同時に同じファイルに触ったか: README・CHANGELOG・lib.rs・openapi のような共有ファイルにそれぞれ追記するチケットが、依存も順番もなく並列に投入されたから（supervisor.enqueued deps=[]）
4. なぜ投入の列が重なりを見なかったか: チケットが触るファイルを見込み、よく衝突するファイルを共有するチケットを並べたり間を空けたりする段が投入になかったからと見られる（推測）
5. なぜ 1 回の衝突がこれほど高いか: README や CHANGELOG への追記のような機械的な取り込みでも、衝突の解消が tier-large の実装のジョブとして丸ごと走るから（job 433 は tier-large、3.88 USD）

- 真因: 共有のよく衝突するファイルに追記するチケットが、重なりを見ずに並列に流れ、生じた衝突のたびに大きいモデルのジョブ 1 本で解いている

### inspection（確からしさ low）

1. なぜ衝突の解消のジョブが始まる前に衝突を捕まえられなかったか: PR を開く前に最新の main へ機械的に取り込み直したり、衝突を確かめたりする段がなく、衝突は開いた後に見つかったから（pr.conflicted 09:24:35）
2. なぜ機械的な直しでなく LLM のジョブになったか: 追記だけのファイルに取り込みの方式（.gitattributes の merge=union や changelog の断片など）がなく、ささいな衝突も人かモデルに任されるから（推測。リポジトリの設定は確かめていない）

- 真因: 共有ファイルに追記の衝突を機械的に解く手段がなく、PR を開く前に衝突を確かめる段もない

## 真因

- 製品の共有ファイル（apps/backend/README.md・CHANGELOG.md・server/src/lib.rs・openapi.yaml）が、チケットごとに同じ場所へ追記する作りになっていて、並列に流れるチケットどうしが必ずぶつかる
- チケットの投入と並列の実行が、チケットどうしが共有するよく衝突するファイルを見ていない（deps=[]）。13 分の実装の間に main が進み、PR は開いた時点で衝突する
- 衝突の解消が、機械的な追記の取り込みでも tier-large の実装のジョブとして丸ごと走る。そのため 1 回の衝突の解消が実装より高くつく（3.88 USD 対 3.30 USD）

## 学び

分析役は 3 つとも「効く範囲（scope）」を書かなかったので、事例の業務（チケットの実装 dev.build と、その投入）から決めた。どれも根拠はこの束 1 つなので、確かさは hypothesis。

この事例の窓（2026-10-29〜11-05）は、Engine ADR 0027 の 1（CHANGELOG の断片方式 changelog.d/。このリポジトリでは 2026-11-03 から）と 2（よく衝突するファイルに触るタスクを並べて投入する plan.serialized）が入った時期とまたがっている。例の #336 がそれらの前か後かは材料になく、知見にはその限りを書いた。

1. テーマ 6（工程の進め方）→ K-0022: どのチケットも追記する共有ファイルを 1 つのファイルのまま残すと、並列の数とともに衝突の解消が増える。後から解くより断片に分けるほうが効く
   - process の真因（確からしさ mid）と、費用がファイルで割られていること（1 本のジョブは、衝突したファイルがすべて衝突しなくなって初めて消える）を知見にした
   - CHANGELOG.md の部分は既存の K-0002（断片方式で担保済み、効き目は未確認）と重なるので、この知見の主張は CHANGELOG 以外の共有ファイル（apps/backend/README.md・lib.rs・openapi.yaml）と「まとめて直さないとジョブが消えない」ことに絞った
   - 作用先の候補: improvement_ticket。提案（分析役の案）: CHANGELOG.md をチケットごとの断片にする。apps/backend/README.md の、どのチケットも追記する部分（エンドポイントの一覧など）を機能ごとに分けた節か生成物にする。つなぎに .gitattributes で CHANGELOG.md と 2 つの README に merge=union を付ける。見込み: README の束は 17 件・49 USD からほぼ 0 に。繰り返しそう: はい
2. テーマ 6（工程の進め方）→ K-0023: PR を開く前に最新の main に取り込み直して衝突を確かめないと、PR は開いた直後に衝突し、別の続きのジョブ（tier-large）で解くことになる
   - inspection の真因の 1（確からしさ low）を、事例の事実（開いて 4 秒後の continue.enqueued、実装より高い解消の費用）に寄せて知見にした。Engine の worker/entrypoint.sh は、続きのジョブでは既定ブランチを取り込むが、新しい PR では取り込まずに push して gh pr create している（手元の Engine で確かめた）
   - 作用先の候補: role_line_engine。提案（分析役の案）: 実装のジョブの終わり（pr.opened の直前）に最新の main を取り込み、失敗したら同じセッションで解く。文脈を持ったセッションで解けば、別のジョブを起こさずに済む。見込み: #336 のように開いて数秒で continue.enqueued(conflict) が出る場合と、その後の PR 本文の食い違い（PR-002 の body_fix）がなくなる。繰り返しそう: はい
3. テーマ 6（工程の進め方）→ K-0024: よく衝突するファイルを共有するチケットを並列に流すと、同じチケットで衝突が何度も戻ってくる
   - process の真因の 3・4（4 は推測）を知見にした。Engine にはすでに、よく衝突するファイル（7 日に 3 回以上・解消の費用 5 USD 以上、CHANGELOG.md は除く）に触るタスクを並べて投入する段（orchestrator/dispatcher/serialize.py、SUPERVISOR_SERIALIZE は既定で有効）がある。README の束（17 件・49 USD）はその閾値を超えるので、窓の中でその段が効いていたか、効いていたのに見込みのファイルが外れたかが、この知見を確かめる鍵になる。既存の K-0013（CHANGELOG の解き直しの時機）・K-0020（判断待ちの間の並べ方）とは別の仕組みとして書いた
   - 作用先の候補: improvement_ticket。提案（分析役の案）: 投入の時に、領域とチケットの本文から触るファイルを見込み、同じよく衝突するファイル（backend の README・server/src/lib.rs・openapi.yaml）に当たるチケットを並べるか、並列の数を絞る。見込み: #348 の 2 回の衝突のような同じチケットの繰り返しがなくなり、コードのファイルの衝突（lib.rs の束、15 件・51 USD）が半分ほどに減る（推測）。繰り返しそう: はい

提案（作用先への変更）はこの変更セットでは実装しない。
