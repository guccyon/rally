# C-0001: 差し戻し — 新しい型の可視性と契約の不変条件の食い違い、PR 本文の基準の揺れ（PR #373）

- 種類: 差し戻し（`sendback.filed` 13:33:42、差し戻し #392）
- 対象: PR #373（Issue #363: listMyBookings の 1 件ごとにキャンセルの見込み `cancel_consumes_quota` / `free_cancel_until` を足す）
- 分析: 事例型の分析役（ADR 0023）。制御プレーンの events `case.analyzed`（id 39223）
- 記録: 2026-10-31（Issue #399）

## 出来事

PR #373 は CI（fmt・clippy・test・contract など 9 種）を全部通った（`pr.ci_passed` 13:18:16）。そのあと judge 530 が rubric の指摘 CODE-001 を採用し、差し戻し #392 になった。

- 指摘（CODE-001）: 新しい型 `CancellationPreview` の項目がすべて `pub` なのに、doc コメントには「`CancellationPolicy::preview` だけが作る」と書いてあった。実装役が契約に自分で書いた不変条件（`free_cancel_until` が null なのは `cancel_consumes_quota` が null か false のときだけ）に反する組 `(true, None)` も型の上では作れる。しかも `preview` 自身も `checked_sub` が失敗したときにこの組を返す
- CI ではこの種の食い違いは見つけられない。止めたのはマージ後の段の rubric 検査（shadow）で、方針どおりマージ（13:45:45）と差し戻しに分かれた
- 並行して PR 本文の構成が 2 回指摘された（PR-002）。「## 概要」の見出しが消えたこと、「背景」「問題」を求めるかどうか、続きのジョブの英語の段落と重複した見出しで、body_fix を 2 回回した

## 観点ごとのなぜなぜ

### inspection（確からしさ high）

1. なぜマージ前の CI で止まらなかったか → CI は可視性と doc コメントの食い違いや、型で表していない不変条件を見ないから
2. なぜ実装役の自己確認でも止まらなかったか → 確認は fmt・clippy・test・yq だけで、新しい型の可視性が doc コメントや契約と合っているかを見る手順がなかったから
3. なぜ型が `pub` のままになったか → application のテスト（`list_my_bookings.rs` の `fn preview`）が `CancellationPreview` を直接作っていて、作りやすさを優先したと見られるから（推測。セッションの記録には判断の理由がない）
4. なぜ `checked_sub` が失敗したときの `(true, None)` が残ったか → domain のテストは境目の前後・開始後・キャンセル済みしか見ておらず、契約の不変条件そのものを確かめるテストがなかったから
5. なぜ rubric の検査で見つかったのに差し戻しになったか → gate が shadow モードで、judge はこれをマイナー（利用者に影響なし）と裁き、方針（採用した指摘は続きのジョブか差し戻しで直す）でマージと分けたから

- 真因: 実装役の自己確認とこの工場の CI に、「契約の不変条件が型（可視性・生成口）とテストで守られているか」を見る段がない。そのため、マージ後の段の rubric 検査で初めて見つかった

### communication（確からしさ mid）

1. なぜ PR 本文が 2 回指摘されたか（PR-002）→ 本文の冒頭に「## 概要」の見出しがなく、「背景」「問題」も求められたから
2. なぜ「## 概要」がなかったか → 実装役の最後の文では「## 概要」が付いていたのに、handoff の summary.md と PR 本文では見出しが落ちて段落だけが残っていたから。Engine が本文を作るときに先頭の見出しを落としたと見られる（推測）
3. なぜ「背景」「問題」の扱いが揺れたか → rubric の OV-001/PR-002 は「背景」「問題」の見出しを求める。一方でリポジトリの CLAUDE.md のテンプレートにはなく、judge 530 は OV-001 を reject した。それでも body_fix 533 は「背景」「問題」を本文の末尾に足した（judge 540 の evidence）
4. なぜ body_fix が judge の reject を受けなかったか → body_fix の入力に、採用した PR-002 の remediation_hint（「背景」「問題」を足す）がそのまま渡り、judge の解釈（「背景」「問題」は求めない）が渡っていなかったから
5. なぜ 2 回目は見出しが重複したか → 続きのジョブ 532 の要約（英語の段落と「## 概要」「## 対応内容」…）が節として本文に足され、body_fix 533 も並べ替えずに末尾に足したから

- 真因: PR 本文の基準（rubric・CLAUDE.md のテンプレート・judge の解釈）が役割の間でそろっていない。しかも本文を作る段（Engine・body_fix）が、見出しの欠落や追記によって構成を崩している

### process（確からしさ mid）

1. なぜ検査と judge が 2 周したか → judge 530 が裁いている間に、既定ブランチとの衝突で続きのジョブ 532 が並行して走り、head が変わったから（`pr.conflicted` 13:21:25 → `pr.head_updated` 13:38:54）
2. なぜ衝突の解消が高くついたか → CHANGELOG.md の 1 か所の衝突を、tier-large で、再開した大きなセッション（812k トークン、3.05 USD、5 ターン）で解いたから
3. なぜ body_fix 542 の前にマージされたか → judge 540 が終わると、body_fix 542 の終わり（13:46:08）を待たずに inspector_approved と merged（13:45:45）が出る順番だったから
4. なぜ CHANGELOG で衝突したか → 並行のチケット（student-app の「お知らせ」の画面）も同じ `[Unreleased]` の「追加」に行を足したから。CHANGELOG を毎回足す運用では、並行の PR とぶつかりやすい

- 真因: 同じ head で検査が終わる前に衝突の続きのジョブが並行して走り、検査と judge が 2 周した。機械的な CHANGELOG の衝突にも大きなモデルと大きなセッションを使った。マージが body_fix の終わりを待たない順番になっている

## 真因

- 実装役が自分で決めた契約の不変条件を、domain の型（非公開の項目・生成口・enum）とテストに移す手順がない。CI もそれを見ないので、マージ後の段の rubric 検査でしか見つからない
- PR 本文の基準が rubric（背景・問題を求める）、リポジトリの CLAUDE.md のテンプレート、judge の解釈でそろっていない。そのうえ Engine と body_fix が見出しを落としたり末尾に追記したりして、構成を崩している
- 衝突の続きのジョブを、検査中の同じ PR で並行して大きなモデルで走らせ、検査と judge が 2 周した。マージと body_fix の順番も揃っていない
