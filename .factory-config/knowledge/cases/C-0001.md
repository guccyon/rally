# C-0001: 衝突解消の追記と body_fix が打ち消し合い、差し戻しが per_pr_limit に達して止まった

- 出来事の種類: 停止
- 対象: PR #657（チケット #646、ブランチ factory/issue-646-job-2377）
- 分析の記録: 制御プレーンの events `case.analyzed`（id 274311）。事例型の分析役（ADR 0023）
- 起票: Issue #823
- 記録した日: 2026-11-03

## 出来事

PR #657 で、差し戻しが per_pr_limit に達して流れなくなり、指摘 1 件を残したまま止まった（11:22〜15:15）。

- 止まったあとの timeline では、既定ブランチとの衝突（`pr.conflicted`）と衝突解消の continue（attempt 11・12）が繰り返されている
- 衝突を直す実装ジョブは、そのたびに PR 本文へ『取り込みの記録』を足していた。記録には本体と同じ見出し（## 概要・## 対応内容など）が付き、読み方の案内も 6 つ積み重なった
- 検査（`gate.evaluated` rubric、mode=shadow）は毎回 PR-002 の本文構成の欠陥を挙げた
- judge は body_fix（tier-small、job 3202・3238）を出して本文を直したが、次の衝突解消でまた記録が足され、欠陥が戻った。とくに body_fix 3238 と衝突解消 3240 は 18:07〜18:11 に同時に動いている
- 最後は judge 3254 が inspection を escalate し、18:23 に別の停止（judge: 人の判断待ち）が開いた
- CI は毎回通っており、本文の構成は CI では見ていない
- handoff/ と session.txt には中身がないため、実装役の意図は確かめられない

## 観点ごとのなぜなぜ

### spec（確からしさ low）

1. なぜ人の判断を待ったか: judge が毎回 category=ui の 1 件を human_decided にしたから（job 3196・3234・3254、confidence 0.6〜0.65）
2. なぜ ui の項目を自動で決められなかったか: チケットや仕様に UI の決め方が書かれておらず、実装役の self_report しか根拠がなかったからと見られる（basis=self_report）
3. なぜ仕様に足りないと言えるか: 同じ ui の項目が 3 回の裁きで同じように人へ回り、繰り返しても決まらなかったから。ただしチケット #646 の本文は材料にないので、ここは推測

- 真因: チケット #646 の入口の情報に UI の決め方がなく、ui の仮決めを自動で採るか決める根拠がなかった（推測）
- 確からしさが low で材料も足りないため、この観点からは知見を起こさない

### communication（確からしさ high）

1. なぜ検査が同じ指摘を出し続けたか: PR 本文で本体の「## 概要」「## 背景」「## 問題」が job 2484 の記録のあとに埋もれ、同じ見出しが取り込みのたびに出てくるから
2. なぜ同じ見出しが何度も出るか: 衝突を直す実装役が、取り込みの記録を本体と同じ見出し（## 概要・## 対応内容・## 影響範囲・互換性など）で本文に足しているから
3. なぜ本体と同じ見出しを使ったか: 本体の節と取り込みの記録をどう分けて呼び、どこに置くかが、実装役・body_fix・検査役のあいだで決まっていなかったから
4. なぜ直してもずれたままか: body_fix は案内の節を足して直そうとし、その案内が 6 つ積み重なって互いに食い違ったから。直す側が本文の決まった形を受け取っていなかった
5. なぜ止まったあとの記録も伝わりにくいか: 停止の記録で cause と prevention が空のままだから。さらに remedy は #657 ではなく別の PR を流す判断を指し、日付も ended_at より後になっている

- 真因: PR 本文の決まった形（本体の節と取り込みの記録の分け方と置き場所）が定められておらず、実装役・body_fix・検査役が同じ見出しの名前を別の意味で使っていた

### inspection（確からしさ high）

1. なぜマージ前に直らなかったか: 検査（rubric）は PR-002 の欠陥を毎回見つけたが、mode=shadow で、直す道は body_fix だけだったから
2. なぜ body_fix で直らなかったか: tier-small の body_fix は本文の一部（1249 字・962 字）を書き換えただけで、次の衝突解消の記録で欠陥がまた戻ったから
3. なぜもっと前で止まらなかったか: 本文の構成は CI の checks（admin-web〜student-app）に入っておらず、CI は毎回通っていたから
4. なぜ欠陥がここまで大きくなったか: 衝突解消のジョブ（continue）が終わって本文に記録を足すとき、見出しの重なりを見る安い検査がなかったから。11 回ぶん積み重なってから rubric が見ていた

- 真因: 本文の構成の欠陥を捕まえるのが、マージ判断の直前に動く shadow の rubric だけだった。衝突解消のたびに本文が崩れる点で止める検査も、根本から直す道もなかった

### process（確からしさ mid）

1. なぜ差し戻しが per_pr_limit に達したか: 同じ PR で、衝突解消 → 検査 → judge → body_fix の流れが何度も回ったから
2. なぜ何度も回ったか: 既定ブランチが動き続けて PR が衝突を繰り返し（17:49・18:05・18:24）、continue が attempt 12 まで続いたから
3. なぜ回るたびに欠陥が戻ったか: body_fix（job 3238、18:08:16〜18:08:38）と衝突解消（job 3240、18:09:48〜18:11:25）が同じ PR の本文に続けて書き込み、片方の直しを片方が上書き・追記したから
4. なぜ続けて書き込めたか: 同じ PR の本文を書き換えるジョブを順に並べる決まりがなく、衝突解消の回数にも上限や人への引き継ぎがなかったから
5. なぜ長く開いたままだったか: ブランチ名 job-2377 から job 3240 まで、1 枚のチケットを長く開いたまま既定ブランチを取り込み続けた。チケットの分け方が大きかった可能性があるが、記録で確かめられないので推測

- 真因: 同じ PR の本文を書き換えるジョブ（衝突解消と body_fix）を順に並べる決まりがなかった。衝突解消の繰り返しにも上限と人への引き継ぎがなく、直しと崩れが回り続けて per_pr_limit に達した

## 真因

- PR 本文の決まった形が定められていなかった。衝突を直す実装役が、本体と同じ見出しで取り込みの記録を本文に足し続け、本文の構成が崩れた
- 同じ PR の本文を書き換えるジョブ（衝突解消の continue と body_fix）を順に並べる決まりがなかった。直しても次の追記で欠陥が戻り、差し戻しが per_pr_limit に達した
- 本文の構成の欠陥を捕まえるのが、マージ判断の直前に動く shadow の rubric だけだった。衝突解消の回数に上限も人への引き継ぎもなく、11 回ぶん崩れが積み重なった

## 学び

提案（作用先への変更）はこの事例記録と知見に残すだけで、実装は別に回す。

1. テーマ 4（役割間の言葉と伝達）→ K-0001
   - 学び: 本文の節と追記の記録を同じ見出しで呼ぶと、書く役・直す役・見る役で意味がずれ、本文が読めなくなる
   - 作用先の候補: term_definition
   - 提案: PR 本文の決まった形を定める。本体の節（## 概要・## 背景・## 問題・## 対応内容…）は先頭に 1 回だけ置き、既定ブランチの取り込みは末尾の『## 取り込みの記録』1 つの下に 1 行ずつ足す。本体の見出しは使わない
   - 繰り返しそう: はい
2. テーマ 6（工程の進め方）→ K-0002
   - 学び: 同じ成果物を書き換えるジョブを並べずに動かすと、直しと崩れが打ち消し合い、上限に達するまで同じ流れが回る
   - 作用先の候補: role_line_engine
   - 提案: 同じ PR の本文を書き換えるジョブ（implement の continue と body_fix）は PR ごとに順に並べる。衝突解消の実装役には、本文を追記ではなく決まった形で組み直すよう指示する
   - 繰り返しそう: はい
3. テーマ 6（工程の進め方）→ K-0003
   - 学び: 長く開いた PR の衝突解消には上限がなく、費用と待ちが静かに膨らむ
   - 作用先の候補: monitoring_runbook
   - 提案: 同じ PR の continue（reason=conflict）が決めた回数（例 5 回）を超えたら、人に知らせ、PR を作り直すかチケットを分け直すかを選ぶ手順を書く。per_pr_limit の停止では cause・prevention を必ず埋め、remedy は対象の PR 番号を指して書く
   - 繰り返しそう: はい
