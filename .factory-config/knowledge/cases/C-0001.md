# C-0001: 続きのジョブの報告が PR 本文に足されて見出しが重なった差し戻し（PR #546）

- 出来事の種類: 差し戻し
- 分析の記録: 制御プレーンの events `case.analyzed`（id 113682）。事例型の分析役（Engine ADR 0023）
- 対象: PR #546（Issue #541、本部が予約 1 件の詳細を見る `getBooking`）
- 記録日: 2026-11-03
- 知見: K-0001（テーマ 4）、K-0002（テーマ 6）

## 出来事

PR #546 は、job 1499 の実装が 12:35 に出たあと、既定ブランチとの `CHANGELOG.md` の衝突（pr.conflicted 12:38:32）で続きのジョブ job 1504 が走った。
job 1504 は報告を「## 概要」「## 対応内容」「## 影響範囲・互換性」「## 動作確認」「## 知見」という新しい PR と同じ見出しの組で書き、それが PR 本文の末尾にそのまま足された（handoff.saved 12:41:09、pr.head_updated 12:42:19）。その結果、同じレベルの見出しが 2 回出てきた。

検査（job 1507）はこれを PR-002 で指摘し、判定役（job 1508）は採用して body_fix（job 1509）に回した。これが今回の差し戻しで、本文の修正（pr.body_amended 12:49:33）のあとにマージされた。

- 実装の 4 つの仮決めはすべて採用された。コードや仕様の欠陥はない
- 検査のほかの指摘 2 件は reject された。OV-001（「背景」「問題」の見出しがない）はリポジトリの決まりの外の要求、CODE-002（単数形と複数形のずれ）は偽陽性
- 検査の rubric とリポジトリの決まり（CLAUDE.md の PR の説明の見出し）がずれていることも分かった

## 観点ごとのなぜなぜ

### communication（確からしさ mid）

1. なぜ: PR 本文で同じレベルの見出しが 2 回出てきたのは、job 1504 の報告が PR 本文の末尾にそのまま足されたからだ
2. なぜ: 足された報告が重なる見出しを持っていたのは、続きのジョブの実装役が、新しい PR の本文と同じ見出しの組（概要・対応内容・影響範囲・互換性・動作確認・知見）で報告を書いたからだ
3. なぜ: そう書いたのは、続きのジョブの報告が既存の PR 本文の「追記」になる（「## 工場の記録」や「## 補足」の下の ### に入れるべき）ということが、実装役に伝わっていなかったからだと考えられる（推測。指示文は材料にない）
4. なぜ: 伝わらなかったのは、Engine が新しいジョブと続きのジョブで同じ報告の型を求め、本文に組み込むときに見出しの階層を変えていないからだと考えられる（推測）
5. なぜ: 並行して、検査役の rubric（OV-001 の「背景」「問題」、CODE-002 のルーター名）がリポジトリの CLAUDE.md の決まりとずれていて、判定役が 2 件を reject した。検査役と判定役は、PR 本文の決まりとして同じ定義を参照していない

- 真因: 続きのジョブの報告が「既存の PR 本文への追記」だということが、役割の間（Engine→実装役）で渡されていない。そのため実装役は新しい PR の見出しの組をそのまま使った。また、検査の rubric と CLAUDE.md の PR の決まりが同じ定義に揃っていない

### inspection（確からしさ mid）

1. なぜ: 見出しの重なりは、マージの前に検査（job 1507）で止まり、body_fix（job 1509）で直された
2. なぜ: もっと前で止まらなかったのは、job 1504 の報告を PR 本文に足す時点（handoff.saved 12:41:09、pr.head_updated 12:42:19）で、本文の構造を見る機械的な検査がなかったからだ
3. なぜ: CI（pr.ci_passed）の 10 個の検査はコードだけを見て、PR 本文を見ないので、見出しの重なりは CI で検出できない
4. なぜ: そのため、本文の構造の欠陥は検査役（LLM）と判定役まで流れ、tier-judge の 2 ジョブと body_fix の 1 ジョブを使って直すことになった
5. なぜ: さらに検査役は rubric の外の要求（OV-001）や偽陽性（CODE-002）も出していて、判定役の手間を増やした。rubric のゲートが shadow mode で、まだ精度を調整している途中だからだと考えられる（推測）

- 真因: 続きのジョブの報告を PR 本文に組み込むところに、見出しの重なりや「## 工場の記録」の外にはみ出す行を見る機械的な検査がない。そのため、直すのが簡単な欠陥が検査役と判定役まで届いた

### process（確からしさ mid）

1. なぜ: job 1504 が走ったのは、PR が既定ブランチと衝突したからだ（pr.conflicted 12:38:32）
2. なぜ: 衝突したのは、並行して進んだ別の変更と、この PR が、同じ `CHANGELOG.md` の `[Unreleased]` の「追加」に 1 行ずつ足していたからだ
3. なぜ: どの PR も CHANGELOG の同じ場所に行を足す運用なので、並列で進めると、コードに関係のない衝突が繰り返し起きやすい
4. なぜ: その衝突のたびに tier-large の続きのジョブが走る。今回は 5 ターンの作業で cost_usd 2.59 かかり、本文の追記で次の欠陥（見出しの重なり）も生まれた

- 真因: 並列で進む PR がすべて `CHANGELOG.md` の同じ場所に追記する運用なので、コードに関係のない衝突が起きる。その解消に、重い続きのジョブ（tier-large、本文の追記つき）を使う工程になっている

## 突き合わせ（真因）

- 続きのジョブ（continue）の報告が既存の PR 本文への追記になることが、実装役に渡されていない。また Engine も見出しの階層を調整せずに末尾に足すので、同じレベルの見出しが重なる（推測を含む）
- PR 本文の構造（見出しの重なり、「## 工場の記録」の外の行）を見る機械的な検査がなく、検査の rubric も CLAUDE.md の PR の決まりと揃っていない。そのため、直すのが簡単な欠陥と、決まりの外の指摘が、検査役と判定役まで流れる
- 並列の PR がすべて `CHANGELOG.md` の `[Unreleased]` に追記するので、コードに関係のない衝突が起きる。その解消が重い続きのジョブになる

## 学び

1. テーマ 4（役割間の言葉と伝達）→ K-0001: 続きのジョブの報告は、新しい PR の本文ではなく既存の本文への追記だと、役割の間ではっきり伝えないと、同じ見出しの組が重なる
   - 作用先の候補: role_line_engine（人の承認）
   - 提案: continue のジョブ（reason: conflict など）への指示で、報告は「### 続きのジョブ（job N）の記録」の 1 つの小見出しの下に書き、## の見出しを使わないことを求める。Engine も本文に組み込むときに ## を ### に下げ、「## 工場の記録」の中に入れる
   - 繰り返しそう: はい
2. テーマ 6（工程の進め方）→ K-0002: 並列の PR がすべて同じ CHANGELOG の場所に追記すると、コードに関係のない衝突が起き、そのたびに重い続きのジョブが走る
   - 作用先の候補: improvement_ticket
   - 提案: CHANGELOG を断片ファイル方式（changelog.d/ に PR ごとの 1 ファイル）にするか、マージの時に行を足す方式にするチケットを起こす。それまでは、CHANGELOG だけの衝突は tier-small の機械的な解消（両方の行を残す）で処理し、PR 本文には 1 行の記録だけを足す
   - 繰り返しそう: はい
   - 記録の時点の状況: 断片ファイル方式は、この出来事のあとに Engine ADR 0027 とこのリポジトリの `changelog.d/`（`changelog.d/README.md`）で入っている

学びの提案（作用先への変更）は、この記録では実装しない。
