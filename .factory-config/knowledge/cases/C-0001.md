# C-0001: 衝突のジョブの報告が積み重なり、PR 本文が崩れたまま merge された

- 出来事: 差し戻し
- 対象: PR #362（Issue #348、生徒が受けたレッスンの一覧 API）
- 分析の記録: 制御プレーンの events `case.analyzed`（id 40354）。事例型の分析役（ADR 0023）
- 記録日: 2026-10-31

## 出来事

コードと CI に問題はなく、差し戻しの理由は PR 本文の構成の崩れだった。

- 最初のジョブ 474 では、エージェントの最後の出力に「## 概要」から始まる本文がそろっていた（session.txt）。ところが handoff/jobs/474/summary.md は「対応内容」の application の途中の行から始まり、先頭が切れていた（7263 バイトで、全文より短い）
- その後、既定ブランチとの衝突を解くジョブが 8 回続いた（ジョブ 485〜575、continue attempt 8）。ジョブごとに「## 概要」「## 対応内容」を持つ報告が PR 本文に積み重なった
- 本文の直し（body_fix 541・559・579）は「読み方」の節を書き足すばかりで、本文を作り直さなかった
- PR-002 の指摘は検査のたびに adopt され、累計 41 件（同じ PR で 7 回 adopt）。ただ検査は shadow で merge を止める力がなかった
- 最後は body_fix 579（14:40:59 開始）が終わる前の 14:41:21 に、人が merge した
- ゴルフを除くかの仮決めは、escalate が 4 回出たあと adopt に戻っており、判定もぶれていた

## 観点ごとのなぜなぜ

### communication（伝達。確からしさ mid）

1. なぜ本文が崩れたか: PR 本文が見出しのない断片（「  - 完了記録の元…」）から始まり、後ろに衝突のジョブの「## 概要」「## 対応内容」が 7〜8 回重なっていたから
2. なぜ先頭が断片になったか: ジョブ 474 の summary.md が、エージェントが書いた本文の途中から始まっていたから（session.txt には「## 概要」から始まる全文がある）
3. なぜ途中から始まったか: 推測だが、handoff へ渡すときに長さの上限があり、本文の頭を落として後ろを残したとみられる（summary.md は 7263 バイトで、全文より短い）
4. なぜ衝突のジョブの報告が本文に重なったか: 衝突のジョブも PR 全体の本文と同じ形（## 概要〜## 補足）で報告を書き、それが PR 本文に足されたから。「ジョブの報告」と「PR 本文」を言葉でも置き場所でも分けていなかった
5. なぜ body_fix で直らなかったか: 判定役の remediation_hint が「置き換えること」と明言したのは後の回だけだった。body_fix（tier-small）は本文を書き直さず、読み方の節を追記していた（本文自身が「本来は先頭から書き直すべき状態」と書いている）

- 真因: 実装役の「ジョブの報告（summary）」と「PR 本文」が同じ形・同じ言葉で扱われ、さらに handoff へ渡すときに先頭が切れた。そのため本文を作り直す責任をどの役割も持たず、追記だけが重なった

### inspection（検査。確からしさ high）

1. なぜ崩れた本文のまま merge されたか: 本文を検査する rubric ゲートが mode: shadow で、PR-002 の should の指摘が merge を止めなかったから
2. なぜ指摘が止める力を持たなかったか: judge が adopt しても「採用した指摘は続きのジョブか差し戻しで直す」という扱いで、inspector_approved と merged が先に進む作りだったから
3. なぜ同じ指摘が何度も出たのに上に上がらなかったか: 同じ PR で PR-002 が 7 回 adopt されても、繰り返しを数えて止めたり人に知らせたりする規則がなかったから
4. なぜもっと前に止まらなかったか: ジョブ 474 の summary が handoff に保存された時点で、本文の先頭が見出しで始まるかを機械的に確かめる検査がなかったから。CI（rules・snapshot など）は本文を見ていない

- 真因: PR 本文の検査が shadow で merge を止める力を持たず、同じ指摘の繰り返しや本文の切れも機械的に検出していなかった

### process（工程。確からしさ high）

1. なぜ本文が何度も書き足されたか: 既定ブランチとの衝突で、continue ジョブが 8 回（attempt 8 まで）走ったから
2. なぜ衝突がこれほど続いたか: どの PR も CHANGELOG.md の [Unreleased] と apps/backend/README.md の構成の表の長い行に書き足すので、main が進むたびに必ず衝突したから
3. なぜ衝突のたびに本文が膨らんだか: 衝突のジョブの報告を、本文を作り直さずに PR 本文へ足す流れだったから
4. なぜ merge と本文の直しが食い違ったか: body_fix 579（14:40:59 開始）が終わる前の 14:41:21 に人が merge したから。本文の直しを待つ決まりがなかった

- 真因: 全員が書き足すファイル（CHANGELOG.md・README の表）が衝突の常連になって衝突のジョブが繰り返し、その報告を足していく工程と、本文の直しを待たない merge が重なった

## 真因

- ジョブの報告（summary）と PR 本文が区別されていない。衝突のジョブの報告が PR 本文と同じ見出しで足され、最初の本文も handoff で先頭が切れたまま使われた（切れた仕組みは推測）
- PR 本文の rubric ゲートが shadow なので、同じ PR-002 の指摘が 7 回 adopt されても merge を止めず、繰り返しを知らせる仕組みもなかった
- CHANGELOG.md と README の表に全員が書き足すため衝突が繰り返し、衝突のジョブが 8 回走った

## 学び

1. テーマ 4（役割間の言葉と伝達）→ K-0001: 続きのジョブ（衝突の解消など）の報告は、PR 本文と同じ見出しで書くと本文に重なって読めなくなる
   - 作用先の候補: role_line_engine（人の承認）
   - 提案: continue ジョブの報告は「## 工場の記録」の下に 1 つの小節（衝突したファイル・解き方・走らせた検査）として書くよう、実装役への指示を変える。PR 本文は Engine が毎回テンプレートどおりに組み直し、追記はしない
   - 繰り返しそう: はい
2. テーマ 6（工程の進め方）→ K-0002: 全員が書き足すファイル（CHANGELOG.md の [Unreleased]、README の構成の表の長い行）があると、main が進むたびに衝突のジョブが繰り返し、費用と本文の乱れが増える
   - 作用先の候補: improvement_ticket
   - 提案: CHANGELOG を PR ごとの断片ファイル（changelog.d/ など）に分け、README の構成の表は 1 項目 1 行の形に直す改善のチケットを起こす
   - 繰り返しそう: はい

提案（作用先への変更）はここでは実装せず、知見の下書きとして残すだけにする。

## 知見にしなかったもの

- inspection の真因（rubric ゲートが shadow で止める力がない、同じ指摘の繰り返しを数えない）は、分析の学びの候補に挙がっていないため知見にしていない。再発したら別の事例として扱う
- 仮決めの判定のぶれ（escalate 4 回のあと adopt）は、この 1 件では原因まで掘れていない
