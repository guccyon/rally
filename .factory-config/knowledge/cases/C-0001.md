# C-0001: PR #548 の差し戻し（PR 本文の見出しの不足と重複、CHANGELOG の決まった衝突）

- 出来事の種類: 差し戻し
- 対象: PR #548（Issue #543、本部のレッスンメニュー一覧に recent_booking_count を足す）
- 分析の記録: 制御プレーンの events `case.analyzed`（id 113678）。事例型の分析役（Engine ADR 0023）
- 記録した日: 2026-11-02
- 関係する知見: K-0001、K-0002

## 出来事

PR #548 は、コードと CI では問題が出なかった。それでも judge が 5 件を採用し、差し戻しの記録になった。

- 実装役の仮決め 3 件（system_interface・data・implementation）。3 件とも判断どおり採用された
- PR 本文への指摘 2 件
  - OV-001: 「背景」「問題」の見出しがない
  - PR-002: 衝突を解消したジョブ 1506・1511 の報告が、本文の後ろに同じレベルの「##」見出しで繰り返し付いている

本文の指摘は body_fix のジョブ 1516 が直し（`pr.body_amended`、defects 1）、その 28 秒後にマージされた。

本文が崩れた理由は 2 つある。

1. 実装役の報告の書式に、PR テンプレートの「背景」「問題」がない
2. `CHANGELOG.md` の `[Unreleased]` で衝突が 2 回起き、そのたびに続きのジョブが自分の報告を本文の後ろに同じ書式で足した

## 観点ごとのなぜなぜ

### spec（確からしさ mid）

1. なぜ仮決めが 3 件も出て、judge に裁いてもらう必要があったのか → Issue の「直近 30 日に入った予約の数（キャンセルを除く）」から、何を基準に数えるかが一通りに決まらなかったから
2. なぜ一通りに決まらなかったのか → 「入った」が予約を作った時刻（created_at）なのか枠の開始時刻（starts_at）なのかを、Issue も specs も決めていなかったから。期間の両端を含むか、キャンセルを今の状態で見るかも決めていなかった。既存の SlotSupply は starts_at で測っている
3. なぜ specs に決まりがなかったのか → 「直近 N 日」の数え方が、low_rated_review_criteria.rs など規則ごとのコードにしか書かれておらず、業務の言葉として定義されていないから（推測）
4. 互換ポリシーについても、なぜ判断が要ったのか → openapi.yaml の互換ポリシーの「必須項目の追加」が、リクエストだけの話なのか応答も含むのかを字面で区別していないから。judge も「ポリシーの字面と少しずれて見える」と書いている

- 真因: 「直近 N 日に入った予約」の数え方（基準の時刻、両端、キャンセルの扱い）と、互換ポリシーの「必須項目の追加」の範囲が specs で定義されていなかった。そのため実装役が確信度 0.65〜0.7 で仮決めするしかなかった。ただし差し戻しの直接の原因ではない（3 件とも判断どおり採用されている）

### communication（確からしさ mid）

1. なぜ PR 本文に「背景」「問題」がなかったのか → 実装役の報告（summary.md）の見出しが「概要／対応内容／影響範囲・互換性／動作確認／補足／仮決め／知見」で、それがそのまま PR 本文になったから
2. なぜ報告の見出しにテンプレートの「背景」「問題」がなかったのか → 実装役が報告を書くときの書式と、検査役の rubric（OV-001・PR-002）が求める PR テンプレートの見出しが揃っていなかったから。session.txt には、実装役が PR テンプレートを読んだ記録がない
3. なぜ見出しが二重・三重になったのか → 衝突を解消した続きのジョブ（1506・1511）が、最初のジョブと同じ書式（## 概要／## 対応内容／## 動作確認）で報告を書き、Engine がそれを「## 既定ブランチの取り込みと衝突の解消（job N）」という節にして本文の後ろに足したから
4. なぜ Engine は同じレベルのまま足したのか → 続きのジョブの報告を「本文の一部」ではなく「工場の記録」として入れ子にする決まりが、Engine と実装役への指示のどちらにもないから（推測）
5. また、なぜ judge は OV-001 の確信度を下げたのか → shadow の指摘では rubric の本文が judge に渡っておらず、検査役から judge への伝達が欠けていたから

- 真因: 実装役の報告の書式・Engine が報告を PR 本文にするやり方・検査役の rubric が求める PR テンプレートの見出しの 3 つが、同じ構成を指していなかった。加えて、shadow の rubric の本文が judge に渡っていなかった

### inspection（確からしさ mid）

1. なぜ本文の不備が検査役（13:03 の inspect）まで見つからなかったのか → CI のチェック（admin-web・backend・compat など 10 件）が見るのはコードと契約だけで、PR 本文の見出しは誰も機械的に確かめていなかったから
2. なぜ実装役のジョブの中で止まらなかったのか → 実装役が自分で確かめたのは fmt・clippy・test・typecheck・lint・gen:api だけで、本文がテンプレートに合っているかを確かめる手順がなかったから
3. なぜ衝突を解消するたびに本文が崩れていくのを、途中で止められなかったのか → `pr.head_updated` のたびに走るのは CI だけで、本文を見る rubric は merge_decided のあとに 1 回しか走らないから
4. なぜマージの前に直した本文をもう一度確かめなかったのか → body_fix（13:06:03）のあと head_sha が変わらないので inspect が走り直さず、そのまま inspector_approved（13:06:31）と merged（13:06:35）に進んだから。`pr.body_amended` の defects が 1 件なので、OV-001 も直ったかは記録では分からない
5. なぜ OV-001 は止める力がなかったのか → rubric の gate が mode: shadow で動いており、止めるかどうかは judge の判断に任されていたから

- 真因: PR 本文の構成を確かめる検査が、実装役のジョブの中にも CI にもなく、マージ直前の shadow の rubric にしかなかった。直したあとの再検査もなかった

### process（確からしさ high）

1. なぜ続きのジョブが 2 回も走ったのか → 既定ブランチに、別のチケットの PR（「受付の記録」の欄、予約 1 件の詳細を見る API）が続けてマージされ、そのたびに `CHANGELOG.md` でこの PR と衝突したから
2. なぜ毎回 `CHANGELOG.md` で衝突したのか → 並行しているチケットがみな `[Unreleased]` の「### 追加」の同じ場所に 1 行ずつ足す運用で、追記どうしが必ずぶつかるから
3. なぜ 1 行の追記の衝突で重いジョブになったのか → 衝突の理由に関係なく、kind implement・tier-large の続きのジョブが走ったから。費用は 3.29 と 3.54 USD で、最初の実装（2.97 USD）より高い
4. なぜそれが差し戻しにつながったのか → 続きのジョブは毎回、報告を PR 本文の節として足していくので、衝突の数だけ本文の見出しが増えて PR-002 の指摘になったから

- 真因: `CHANGELOG.md` の `[Unreleased]` が、並列のチケットどうしの決まった衝突の場所になっていた。そのうえ、機械的に直せる追記の衝突にも tier-large の続きのジョブを割り当て、そのジョブの報告が本文に足されていく流れだった

## 真因

- 実装役の報告の書式・Engine が報告を PR 本文にするやり方・検査役の rubric が求める PR テンプレートが揃っていなかった。本文に「背景」「問題」がなく、続きのジョブの報告も同じ「##」レベルで足されていった
- `CHANGELOG.md` の `[Unreleased]` への追記が、並列のチケットどうしの決まった衝突の場所になっていた。衝突のたびに tier-large の続きのジョブが走り、本文の節も増えた
- PR 本文の構成を確かめる検査が、実装役のジョブにも CI にもなく、マージ直前の shadow の rubric にしかなかった。body_fix のあとの再検査もなかった

## 学び

1. テーマ 4（役割間の言葉と伝達）→ K-0001
   - 実装役の報告がそのまま PR 本文になる流れでは、報告の書式と検査役の rubric が求める PR テンプレートを同じものにしておかないと、毎回同じ指摘が出る
   - 作用先の候補: role_line_engine
   - 提案（この PR では実装しない）: 実装役への指示の報告の書式を、PR テンプレートの見出し（背景・問題・対応内容…）と同じにする。「背景」「問題」は Issue から 1〜2 文を写して埋めるよう明記する。あわせて、shadow の rubric の本文（OV-001・PR-002）を judge の入力に入れる
   - 繰り返しそう: はい
2. テーマ 6（工程の進め方）→ K-0002
   - `CHANGELOG.md` の同じ場所に追記する運用では、並列のチケットが増えるほど決まった衝突が起き、そのたびに重いジョブが走る
   - 作用先の候補: improvement_ticket
   - 提案（この PR では実装しない）: CHANGELOG を changelog.d/ などのチケットごとの断片ファイルに分け、リリースのときにまとめる。または `CHANGELOG.md` に union マージを設定する。あわせて、衝突が `CHANGELOG.md` の追記だけのときは、tier-small の機械的なジョブか supervisor の自動解消に回す
   - 繰り返しそう: はい

## 知見にしなかったもの

- spec の観点（「直近 N 日」の数え方と互換ポリシーの「必須項目の追加」の範囲が未定義）は、差し戻しの直接の原因ではなく、分析役の学びの候補にも挙がっていないので、この事例では知見にしない。業務ルールの定義はテーマ 3（ドメインの理解）の作用先で、人の承認が要る
- inspection の観点（本文の検査が shadow の rubric にしかなく、body_fix のあとの再検査がない）は、K-0001 の背景として扱い、別の知見にはしない
