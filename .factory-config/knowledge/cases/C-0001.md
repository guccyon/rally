# C-0001: 直すもののない差し戻し（PR #395）

- 出来事: 差し戻し（sendback）
- 対象: PR #395（Issue #366、コーチのホームに今月と先月の実績を出す）
- 分析の記録: 制御プレーンの events `case.analyzed`（id 40376）。事例型の分析役（ADR 0023）
- 知見の下書き: K-0001（テーマ 4）、K-0002（テーマ 6）
- 記録日: 2026-11-01

## 出来事

PR #395 は「差し戻し」（sendback、adopted: 3）として記録されたが、中身を見ると直すべき欠陥は 1 件もなかった。

- judge が採用（adopt）した 3 件は、実装役の仮決め（ui-1・ui-2・eh-1）で、どれも `defect: null`
- 欠陥として挙がった 2 件（OV-001 と PR-002。どちらも PR 本文に「## 背景」「## 問題」がない、という同じ指摘）は judge が退けた（reject）
- CI は全部通り、PR はマージ済み
- supervisor.inspector_approved の basis は「採用 3。採用した指摘は続きのジョブか差し戻しで直す」

差し戻しになったのは、仮決めを認める「採用」と、欠陥を直すべきものと認める「採用」が、同じ言葉と同じ数（adopted）にまとめられていたためと読める。あわせて、実装役が PR テンプレートの見出し（背景・問題）を使わなかったこと、検査のルール 2 本が同じずれを二重に数えたことも見つかった。

## 観点ごとのなぜなぜ

### communication（伝達、確からしさ mid）

1. なぜ差し戻しとして記録されたか: incident の adopted が 3 で、supervisor.inspector_approved の basis が「採用 3。採用した指摘は続きのジョブか差し戻しで直す」と書いているから
2. なぜ採用 3 が「直す指摘」と扱われたか: judgment.judged の `verdict: adopt` が、仮決めを認める裁き（`defect: null` の 3 件）と欠陥を認める裁きの両方に同じ言葉で使われ、区別されずに数えられたから
3. なぜ区別されなかったか: judge の出力は、仮決めの裁きか欠陥の裁きかを defect が null かどうかでしか表しておらず、数える側（supervisor）がそこを見ずに adopt の数を合計したと考えられるから（集計のロジックは材料にないので推測）
4. なぜ同じ言葉なのか: 「採用」の意味（仮決めを承認する／欠陥を是正の対象にする）を役割の間で分けて定義した用語がないから（推測）

- 真因: judge の verdict「adopt」が「仮決めを認める」と「欠陥を直す対象にする」の 2 つの意味で使われ、supervisor がその合計を「直すべき指摘」の数として差し戻しを起こした

### process（工程、確からしさ mid）

1. なぜ直すものがないのに差し戻しの出来事ができたか: マージの後でも、adopted の数だけを見て sendback の出来事を起こしているから
2. なぜ数だけで起こすのか: 「採用した欠陥が 1 件以上あり、まだ直っていない」という条件ではなく、adopt の件数を条件にしていると読めるから（推測）
3. なぜそれが問題か: 見せかけの差し戻しが分析や指標にまざり、続きのジョブや差し戻しを無駄に起こすおそれがあるから

- 真因: 差し戻しを起こす条件が「defect があり adopt された件数」ではなく「adopt の件数」になっており、マージ済みかどうかも見ていない（推測）

### inspection（検査、確からしさ mid）

1. なぜ検査は欠陥を 2 件挙げたか: PR 本文にテンプレートの「## 背景」「## 問題」がなく、それを OV-001（L4、shadow）と PR-002 の 2 本のルールが別々に見たから
2. なぜ同じずれが 2 件になったか: OV-001 と PR-002 が同じもの（PR 本文の見出しの構成）を見ていて、重なりをまとめる仕組みがないから（judge も「中身は index 1 と同じ」と書いている）
3. なぜ judge は 2 件とも退けたか: PR-002 は当てはまらない見出しを削除してよいと書いており、検査役は削除した旨まで書けと読んだので、ルールの読み方が検査役と judge でずれていたから
4. なぜ実装役の段階で見出しが揃わなかったか: 実装役は PR 本文を自分の型（概要・対応内容・…・仮決め・知見）で書いており、テンプレートを読んだ跡が session にないから

- 真因: PR テンプレートに沿っているかを実装役が出す前に確かめる手順がなく、検査では同じ観点のルール 2 本（OV-001・PR-002）が重なっていて、解釈もそろっていない

### spec（仕様、確からしさ low）

1. なぜ仮決めが 3 件出たか: Issue の「コーチのホーム（いちばん最初に見る画面）」が、どの画面・どのタブを指すのか決まっておらず、0 件のときと失敗したときの表示も書かれていなかったから
2. なぜ決まっていなかったか: 「コーチのホーム」という言葉の定義が specs/ や README にないので、実装役は README の「開いたときは『対応待ち』」から読み取るしかなかったから
3. なぜそれでも問題にならなかったか: 実装役が根拠を示して仮決めを残し、judge が 3 件とも欠陥なしと認めたから

- 真因: 「コーチのホーム」という画面の言葉に定義がなく、入口の情報が少し足りなかった。今回は仮決めで補えたので、実害はない

## 真因

- judge の「adopt」が「仮決めを認める」と「欠陥を直す対象にする」の 2 つの意味で使われ、supervisor はその合計（adopted: 3）を直すべき指摘の数とみなし、マージ後に直すもののない差し戻しを起こした
- 実装役が PR テンプレートの見出し（背景・問題）に沿っているかを確かめないまま PR を出し、検査では同じ観点のルール 2 本（OV-001・PR-002）が同じずれを二重に数えた。しかも検査役と judge で PR-002 の読み方が違った
- 「コーチのホーム」という画面の言葉に定義がなく、置き場所・0 件の表示・失敗したときの表示は仮決めに頼った（今回は実害なし）

## 学び

1. テーマ 4（役割間の言葉と伝達）→ K-0001
   - 同じ「採用」という言葉が仮決めの承認と欠陥の是正の両方を指すと、数える側が取り違えて、直すもののない差し戻しが生まれる
   - 作用先の候補: term_definition
   - 提案: judge の verdict を、仮決めには approve_provisional、欠陥には adopt_defect と分けて定義する。incident の adopted も adopted_defects と approved_provisionals の 2 つに分けて記録する
   - 繰り返しそう: はい
2. テーマ 6（工程の進め方）→ K-0002
   - 差し戻しは「採用した欠陥があり、まだ直っていない」ときだけ起こすべきで、件数の合計やマージ後の状態で起こすと記録が汚れる
   - 作用先の候補: role_line_engine
   - 提案: supervisor が sendback を起こす条件を「defect が null でなく、verdict が adopt の件数が 1 以上」にする。PR がマージ済みで採用した欠陥がないときは起こさない。inspector_approved の basis の文も、その 2 つの数を分けて書くようにする
   - 繰り返しそう: はい

提案（作用先への変更）は、この事例記録と知見の下書きでは実装しない。委員会の審査と、承認の線（ADR 0023・0024）に従って別に扱う。

inspection と spec の観点の真因（PR テンプレートの確かめ・検査ルールの重なり・「コーチのホーム」の定義）は、分析役が学びの候補に挙げていないので、この事例では知見にしていない。
