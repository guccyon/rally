# C-0001: PR 本文の見出しの欠けと、並列の直しによる 2 回の差し戻し

- 出来事の種類: 差し戻し（2 回）
- 対象: PR #396（Issue #364。生徒アプリの「自分の予約」に、無料でキャンセルできる期限の案内を出す変更）
- 分析の記録: 制御プレーンの events `case.analyzed`（id 40381）。事例型の分析役（ADR 0023）
- 記録した日: 2026-11-01
- 根拠から出した知見: K-0001（テーマ 4）、K-0002（テーマ 6）

## 出来事

PR #396 は 2 回差し戻されてからマージされた。採用された指摘は 3 件。コードとテストは CI（8 チェック）を通っていて、利用者に影響する欠陥はなかった。指摘の中心は PR 本文の構成。

1. 1 回目の検査（job 560、14:15:47）: 実装役の本文に PR テンプレートの「## 背景」「## 問題」がなかった（PR-002）。あわせて、labels の単体テストを画面テストに置いていた nit（CODE-003）も採用された
2. judge はこの 2 件を body_fix（job 563）と続きの implement（job 564）に分けて投入し、2 つは同時に走った
   - 563 は背景・問題・結論を、本文の末尾（「## 工場の記録」の後ろ）に足した
   - 564 は自分の報告を「## 検査の指摘の直し（job 564）」の下に、同じ ## の見出しのまま足した
3. 2 回目の検査（job 570、14:21:30）: 「見出しの順が違い、二重になっている」と、また PR-002 で差し戻された
4. 最後の body_fix（job 572）の後は、head_sha が変わらないまま検査をもう一度通さずにマージされた（14:23:30）
5. ほかに、検査役は同じ欠陥を OV-001 と PR-002 で 2 重に数えていた。judge には OV-001 の本文が渡っていなかった

## 観点ごとのなぜなぜ

### 伝達（communication、確からしさ mid）

1. なぜ初回の本文に背景・問題がなかったか: 実装役の報告（summary.md）が「概要・対応内容・影響範囲・互換性・動作確認・補足・仮決め・知見」の型で書かれていて、それがそのまま PR 本文になったから
2. なぜその型だったか: 実装役が受け取る報告の型と、検査役が PR-002 で見るテンプレート（概要・背景・問題・対応内容・影響範囲・動作確認・補足）が揃っていないから（推測。実装役への指示そのものは材料にない）
3. なぜ揃っていないと分かるか: 報告は 2 回とも同じ型で書かれていて、2 回目も背景・問題を自分では書かず、## の見出しのまま別の見出しの下に足されたから
4. なぜ検査役の指摘が 2 重になったか: 検査役が同じ欠陥（背景・問題がない）を OV-001 と PR-002 で別々に数え、judge には OV-001 の本文が渡っていなかったから

真因: 実装役が使う報告の型と、検査役が使う PR テンプレート（PR-002）の見出しが揃っていない。どちらも「PR 本文」だが、別の型で扱われている。検査役から judge への伝達でも、rubric の本文が欠けていて、指摘が重複していた。

### 検査（inspection、確からしさ high）

1. なぜマージ前の CI で止まらなかったか: CI の 8 チェックはコードだけを見ていて、PR 本文の見出しは見ないから（pr.ci_passed 14:15:14）
2. なぜ検査より前で止まらなかったか: 実装役にも Engine にも、本文を PR テンプレートと機械的に照らす自己点検がないから（推測。セッションの記録に照合の操作がない）
3. なぜ直しのあとにまた同じ PR-002 で止まったか: body_fix（job 563）が見出しを末尾に足すだけで、本文全体をテンプレートの順に並べ直さず、それを確かめる仕組みもなかったから
4. なぜ最後の直し（job 572）は検査を通らなかったか: 本文だけの直しは head_sha を変えないので、検査がもう一度起動されず、inspector_approved と merged が同じコミットのまま続いたから

真因: 本文の構成（必須の見出し、順番、重複）を機械的に確かめる検査がない。そのため、検査役の LLM 検査でしか拾えず、検査が工程の後ろに偏っている。さらに、本文だけの直しは検査し直す条件に入っていない。

### 工程（process、確からしさ high）

1. なぜ 2 回目の差し戻しが起きたか: 本文を body_fix（job 563）と続きの implement（job 564）の 2 つのジョブが、同じ時間帯に別々に書き換えたから
2. なぜ別々に書き換えたか: judge が本文の指摘を body_fix に、コードの指摘を implement に分けて同時に投入し、本文をまとめて組み直す役を決めていなかったから
3. なぜ並び順が壊れたか: どちらのジョブも本文の末尾に足す作りで、563 は背景・問題・結論を、564 は報告を ## のまま「## 検査の指摘の直し（job 564）」の下に足したから（足し方の作りは推測。結果は検査の evidence で確かめられる）
4. なぜ同時に走ったと分かるか: 563 が advisory_lock_held で一度戻され、564 が終わる前に終わっているから

真因: 差し戻しの直しを、本文用とコード用の 2 つのジョブに分けて並列で走らせている。本文の持ち主は決まっておらず、それぞれが末尾に足すので、テンプレートの順と見出しの階層が崩れる。

## 真因

- 実装役の報告の型が PR テンプレート（PR-002）の見出しと揃っておらず、報告がそのまま PR 本文になるので、背景・問題が最初から欠ける
- 差し戻しの直しを body_fix と続きの implement に分けて並列で走らせ、どちらも本文の末尾に足すだけで、本文全体をテンプレートの順に組み直す役がいない
- 本文の構成を機械的に確かめる検査がなく、本文だけの直し（head_sha が変わらない）は検査し直されずにマージされる

   - 作用先の候補: role_line_engine（人の承認）
   - 提案（この記録では実装しない）: 実装役の summary.md の型を PR-002 のテンプレート（概要・背景・問題・対応内容・影響範囲・動作確認・補足）に揃える。仮決め・知見・工場の記録は、その後ろの決まった位置に置くよう、実装役への指示に書く
   - 繰り返しそう: はい
2. テーマ 6（工程の進め方）→ K-0002: 同じ PR 本文を複数のジョブが並列に末尾へ追記すると、見出しの順と階層が崩れて、新しい差し戻しを生む
   - 作用先の候補: role_line_engine（人の承認）

   - 繰り返しそう: はい
