# C-0001: PR 本文の見出しの欠けで差し戻し（生徒アプリのお知らせ画面）

- 出来事: 差し戻し
- 対象: PR #372（Issue #353、生徒アプリのお知らせ画面）
- 分析の記録: 制御プレーンの events `case.analyzed`（id 39249）。分析役は事例型（ADR 0023）
- 記録日: 2026-10-31

## 出来事

PR #372 は CI を通った。judge が 8 件を裁いて 7 件を採用した（仮決め 6 件と PR-002）。欠陥として差し戻しになったのは PR-002 の 1 件だけ。
PR 本文に「## 概要」「## 背景」「## 問題」「## 対応内容」がなく、本文が見出しのない箇条書きから始まっていた。body_fix ジョブ 527 が本文を直し、そのまま merge された。

記録を突き合わせると、原因は 2 つ。

1. 本文の冒頭が途中で欠けた。session.txt の実装役の最後の文には「## 概要」「## 対応内容」と、`lib/api/`・`lib/state/notifications.dart` の箇条書きがある。handoff の summary.md（PR 本文の元）は、4 番目の箇条書き「`FlowStep.notifications` を足し…」から始まっている。最後の文から PR 本文を作る途中で冒頭が落ちた
2. 実装役が「## 背景」「## 問題」をそもそも書いていない。session.txt に PR テンプレートを読んだ跡がない

L4 の rubric は shadow で動いていて、CI も本文を確かめないため、merge の直前まで止まらなかった。

ほかに目についた点:

- worker のイメージが factory-worker:rust で、Flutter SDK がなかった。実装役は自分で SDK を取ってきて検証した
- 前の段 #352 の契約に行き先の ID がなく、行から個別の画面へ進めなかった
- 仮決めの ID の頭（ui-1）と区分（system_interface）が合っていない
- judge の手元に OV-001 の rubric の本文がなかった

## 観点ごとのなぜなぜ

### 仕様（spec、確からしさ mid）

1. なぜ行から個別の予約・添削結果・スレッドへ進めず、一覧の画面への遷移で妥協したのか → 契約の `Notification` に行き先の ID（booking_id / video_id / thread_id）がなかったから
2. なぜ契約に ID がないまま #353 に入ったのか → 前の段の #352 で契約を決めたとき、#353 の受け入れ条件「種類に応じて予約・添削結果・メッセージの画面へ」に要る項目を確かめていなかったと見られる（推測）
3. なぜ #353 の中で契約を足せなかったのか → Issue #353 に「やらないこと: backend と契約」とあり、契約の変更を禁じていたから

- 真因: チケット #353 の受け入れ条件（種類に応じた画面へ進む）と、前の段 #352 で決めた契約（行き先の ID がない）が噛み合っていなかった。今回の差し戻しの直接の原因ではなく、judge はワーニングとして採用した

### 伝達（communication、確からしさ mid）

1. なぜ PR 本文に「## 概要」「## 対応内容」がなかったのか → 実装役の最後の文にはあったが、summary.md には 4 番目の箇条書きより前が入っていなかったから
2. なぜ途中で冒頭が落ちたのか → 最後の文から handoff の summary を取り出す仕組みが、本文の冒頭を切り落としたと見られる。切り方（字数・区切り・何かの目印）は記録からは分からない（推測）
3. なぜ「## 背景」「## 問題」もなかったのか → 実装役は「## 概要」「## 対応内容」から書き始めていて、session.txt に PR テンプレートを読んだ跡がないから
4. なぜテンプレートの見出しが実装役に届かなかったのか → 実装役への指示に、テンプレートの必須の見出しがはっきり渡っていなかったと見られる（推測）
5. あわせて、judge は OV-001 を「根拠の rubric の本文がない」として退けた。検査役から判定役へ rubric の本文が渡っていなかった

- 真因: 役割の間の受け渡しで情報が欠けた。(1) 実装役の最後の文から PR 本文へ移すときに冒頭が落ちた。(2) PR テンプレートの必須の見出し（背景・問題）が実装役に伝わっていなかった。(3) 検査役から判定役へ OV-001 の rubric の本文が渡っていなかった

### 検査（inspection、確からしさ high）

1. なぜ CI で止まらなかったのか → CI の checks（admin-web, backend, floor, l3, mutation, rules, snapshot, student-app）はコードだけを確かめ、PR 本文の構成は見ないから
2. なぜ検査の段まで本文の欠けに気づかなかったのか → 実装役の側にも handoff の保存（handoff.saved）の側にも、本文がテンプレートの見出しをそろえているか、最後の文と本文が一致しているかを機械で確かめる段がないから
3. なぜ検査で見つけても merge の前に直し切ることになったのか → L4 の rubric は mode=shadow で、見つけた欠陥は judge に回り、body_fix で直してから merge する流れだったから
4. なぜ PR が出る前に止まらなかったのか → 見出しの有無のような機械で判定できる項目まで、PR を出したあとの LLM の検査に任せていたから

- 真因: PR 本文の構成（テンプレートの見出し）を確かめる、機械で判定できる検査が PR を出す前にない。L4 の rubric も shadow なので、PR を出したあとの検査と judge に頼る形になっていた

### 工程（process、確からしさ mid）

1. なぜ実装役は Flutter SDK を自分で取ってきたのか → worker のイメージが factory-worker:rust で、Flutter SDK が入っていなかったから
2. なぜ Flutter のアプリの変更に rust のイメージが選ばれたのか → チケットが変える場所（apps/student-app）からイメージを選ぶ仕組みがなかったと見られる（推測）
3. なぜそれが問題になるのか → 実装役が SDK を取りに行ったり unzip の代わりを作ったりして時間を使い、検証の環境も CI と同じとは限らなくなるから
4. あわせて、#352 → #353 の順で契約を先に決めたのに、次の段で要る項目（行き先の ID）が契約になく、別のチケットが要る形になった

- 真因: 工程の設定がチケットが変える場所に合っていなかった（Flutter の変更に rust のイメージ）。また、契約を先に決める段（#352）で次の段（#353）の受け入れ条件を確かめていなかった。どちらも今回の差し戻しの直接の原因ではない

## 真因

- 実装役の最後の文から PR 本文（handoff の summary.md）へ移す途中で、冒頭の「## 概要」「## 対応内容」と最初の箇条書きが落ちた。それを確かめる仕組みもない
- PR テンプレートの必須の見出し（概要・背景・問題・対応内容）が実装役に伝わっていなかった。PR を出す前に見出しを機械で確かめる段もなく、shadow の rubric と judge に頼っていた
- チケットに対して工程の設定がずれていた。Flutter の変更に rust のイメージを当て、契約の段 #352 では次の段の受け入れ条件に要る ID を確かめていなかった
