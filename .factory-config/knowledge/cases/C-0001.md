# C-0001: 指摘を直す続きのジョブが PR の状態の確認で止まり、直す前に PR がマージされた

- 種類: 停止
- 分析の記録: 制御プレーンの events `case.analyzed`（id 39242）
- 対象: PR #327（Issue #321、生徒アプリのチャットの状態を ChatState / ChatNotifier に切り出す作業）、続きのジョブ job 395（review_fix）
- 起票: Issue #400
- 学びのテーマ: 6（工程の進め方）

## 出来事

PR #327 で、検査の指摘 CODE-001 を直す続きのジョブ（job 395、review_fix）が exit 6 で失敗した。

- 実装役は直しを終えていた。flutter analyze は問題なしで、テストは 240 件すべて通った（session.txt の 233〜252 行）
- 失敗したのはその後の entrypoint の最後の手順。gh pr view で PR の状態を確かめたときに api.github.com への接続が一時的に失敗し、状態が空のまま返った。それを「PR が開いていない」と判定し、push しないまま exit 6 で止まった（stoppage の remedy から）
- 実際の PR #327 は開いたままで、job.finished（08:06:38）の約 50 秒後の 08:07:29 に supervisor がマージした
- 直しは差し戻し #328 として出し直された（sendback.filed 08:06:59）ので、成果物に害はなかった

重なっていたこと:

1. entrypoint が「通信の失敗」と「状態が開いていない」を区別しない
2. 続きのジョブが動いている間も、マージがそれを待たずに進む作りになっている
3. 失敗が「未分類」で上がり、worker.err にも手がかりが残っていない

どれも工場（制御プレーン・エントリポイント）側の問題で、チケットや実装役の仕事が原因ではない。

## 観点ごとのなぜなぜ

### 伝達（communication、確からしさ mid）

1. 検査役の指摘 CODE-001 は「切り出す前の StudentFlowState は一覧を写して持つ作りだった」を前提にしていた。実装役は、この前提が一部しか正しくないと報告した（写していたのは myVideos と myBookings だけで、threads と messages は前から写していなかった）
2. 前提がずれたのは、検査役が StudentFlowState のコメント（一覧を写して持つ）を、すべての一覧に当てはまる規則として読んだためと見られる。フィールドごとに確かめた跡はない（推測）
3. 判定役がそのまま採用したのは、judgment.judged の basis が self_report で、指摘の前提を確かめる手順がないため（推測）
4. もう一つの伝達の欠け: 停止は「未分類。人が分類を直す」で上がり、prevention も空だった。worker.err も空で、gh pr view の接続エラーが人の読める形で残っていなかった。原因の記録は後から remedy に人が書き足している
5. 残らなかったのは、entrypoint の exit 6 が「PR が開いていない」という意味だけを持ち、接続の失敗の内容を watcher や stoppage に渡す仕組みがないため（推測）

- 真因: ジョブの最後の手順で起きた外部 API の失敗が、終了コードの意味（PR が開いていない）にまとめられ、本当の原因が watcher や stoppage に伝わらない。あわせて、検査役の指摘の前提（直す前の作り）がフィールドごとに確かめられないまま渡されている

### 検査（inspection、確からしさ mid）

1. プロダクトの欠陥（CODE-001）は、マージ前の検査（gate.evaluated 08:03:28）で見つかり、判定役も採用した。プロダクト側の検査は働いていた
2. それでも停止したのは、直しを push する前の entrypoint.sh の PR の状態の確認で起きたため。工場のコードの欠陥である
3. その欠陥が前もって見つからなかったのは、gh pr view が接続エラーで空を返すときの扱い（やり直す、開いていないと区別する）を確かめるテストや検査の跡がないため（推測）
4. 空の値を「開いていない」と読んだのは、状態の文字列が open でないことだけで判定しており、取れなかったことと閉じていることを分けていないため（remedy の記述から）

- 真因: entrypoint.sh の PR の状態の判定が、外部 API の一時的な失敗（空の応答）を考えていない。このような失敗を想定したテストが工場側にない

### 工程（process、確からしさ mid）

1. 直しは PR #327 に入らず、差し戻し #328 に回り、PR #327 は指摘が直らないまま 08:07:29 にマージされた
2. 直らないままマージされたのは、supervisor.inspector_approved の basis が「採用した指摘は続きのジョブか差し戻しで直す」で、マージが続きのジョブ（job 395）を待たない作りになっているため
3. これが問題になりうるのは、job 395 が 08:04:43 から 08:06:38 まで動いており、マージはその 50 秒後だったから。今回は失敗が先に起きたが、push がマージより遅れれば、マージ済みの PR に push しに行く競合が起きうる（推測）
4. 続きのジョブが 2 分ほど長く動いたのは、ジョブの間で /tmp が消えるので、Flutter の SDK と unzip の shim を毎回入れ直していたため（cost_usd 2.85、job 390 とほぼ同じ）
5. 毎回入れ直すのは、作業機のイメージ factory-worker:rust に Flutter の作業に要る道具が入っていないため。arm64 の作業機では配布の tar も使えない

- 真因: 採用した指摘を直す続きのジョブと、PR のマージが並んで走り、どちらが先かを決める決まりがない。そのうえ、Flutter のチケットに Flutter のない作業機の像が割り当てられ、続きのジョブが長くなって外部 API に触れる回数と時間が増えている

## 真因

- entrypoint.sh が gh pr view の接続の失敗（空の応答）を「PR が開いていない」と同じに扱い、やり直さずに exit 6 で終わる（工場のコードの欠陥）
- 続きのジョブ（review_fix）と supervisor のマージが並んで進み、採用した指摘の直しを PR に入れてからマージするのか、差し戻しに回すのかの順番が決まっていない
- 終了コードの意味が粗く worker.err にも原因が残らないため、停止が「未分類」で上がり、原因を知るのに人の調べが要る

## 学び

1. テーマ 6（工程の進め方）→ K-0001: 採用した指摘を続きのジョブで直している間は、その PR のマージを待たせるか、差し戻しに回すかをはじめに決め、両方が同時に進まないようにする
   - 作用先の候補: role_line_engine（人の承認）
   - 提案: supervisor のマージ判定に「同じ PR の continue（review_fix）のジョブが動いている間はマージしない」を足す。もしくは、マージを先にするなら review_fix を起こさず、はじめから sendback に回すと決めて、どちらかの道だけを通す
   - 繰り返しそう: はい
2. テーマ 6（工程の進め方）→ K-0002: アプリの種類に合う道具の入った作業機の像を割り当てないと、毎回の道具の入れ直しで時間と費用が増え、失敗の機会も増える
   - 作用先の候補: improvement_ticket
   - 提案: apps/student-app（Flutter）の変更には、Flutter SDK（arm64 対応）と unzip の入った worker image を用意して割り当てる。用意できるまでは、SDK をジョブの間で残る場所（ticket volume など）に置く
   - 繰り返しそう: はい

提案（作用先への変更）は Issue #400 の範囲では実装しない。知見の下書きとして残すだけにする。
